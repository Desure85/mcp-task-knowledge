# /end-session

Завершающий ритуал сессии. Выполни последовательно:

## 1. Quick Snapshot

- Прочитай `.omo/boulder.json` если существует
- `git status --porcelain` — незакоммиченные изменения
- `todoread()` — незавершённые задачи

## 2. Draft Consolidation (сбор дельты по ходу → факты/паттерны)

### 2.0 Сбор драфтов сессии + сабагентов (ОБЯЗАТЕЛЬНО перед консолидацией)

Сабагенты (explore/librarian/general/Sisyphus-Junior/...) пишут в СВОЙ
`draft-ses_<subagent-id>.md` — без сбора они теряются. Определи Session ID
этой сессии (injected session-draft инструкции — файл `draft-ses_<ID>.md`,
или env `OPENCODE_SESSION_ID`) и собери ТОЧНЫЙ список своих драфтов:

```bash
~/.config/opencode/scripts/collect-subagent-drafts.sh "$SESSION_ID" --list
```

Скрипт определяет корневую сессию (поднимается по parent_id), находит всех
сабагентов (`parent_id = <root>`), ищет их драфты в `<directory>/.omo/memory/`
(directory сессии из opencode.db — работает для любого проекта/пользователя)
и в `~/.omo/memory/` (глобальный). Опция `--list` печатает пути по одному
на строку — этот список и есть ЕДИНСТВЕННОЕ, что можно консолидировать
и архивировать. Для чтения содержимого: тот же скрипт с
`--out /tmp/subagent-drafts.md`.

> ⚠️ **ЗАПРЕЩЕНО трогать драфты чужих сессий:** никаких `ls/mv draft-*.md` по
> глобу — это живые буферы параллельных сессий. Инцидент 01.09.2026: Bitrix-сессия
> свипнула глобом живой драфт другой сессии на середине записи — хвост фактов
> потерян. В контейнере `~/.omo/memory` — общий хост-маунт, поэтому эта защита
> критична вдвойне.

Легаси `draft.md` (общий, без session ID) — прочитать если есть.

Дальше обрабатывай строки из собранных драфтов (дедуп, классификация, запись
в facts/patterns). Каждый файл уникален на сессию — это исключает гонку
параллельной записи. Каждая строка — кандидат. Для каждой выполни:

1. **Дедуп по смыслу** (не по тексту): пересечение draft × реальная сессия × существующие
   facts.md/patterns.json. Отсеки: уже записанное, рутину, дубли.
2. **Классификация сигнала** (по сути, не по префиксу draft):
   - **DOMAIN** (механика/архитектура Albato) → консолидация в `facts.md` + кандидат
     в `albato_domain.md` (предложить пользователю, не вносить молча)
   - **DIAGNOSTIC** (как расследовать баг) → кандидат на улучшение `task-research-extended`
   - **PROCESS** (рецепт/правило работы) → кандидат на улучшение конкретного скилла
   - **INFRA** (окружение) → кандидат в AGENTS.md
   - **META** (поведение агентов) → правило для AGENTS.md
   - **SUSPICIOUS** (подозрительный код/баг) → кандидат в YouTrack-тикет, краткое
     описание с `файл:строка`
   - **SUBAGENT** (неэффективное делегирование) → кандидат на улучшение соответствующего
     skill'а или правила AGENTS.md
3. **Анти-инфляция matches** (для patterns.json): однодневные батчи (N задач серии
   = 1 подтверждение), тикеты-дубли (BT-XXXX = DEV-XXXX одного инцидента) НЕ считаются
   независимыми подтверждениями.
4. Запиши доменные факты (importance ≥ 6) в `facts.md` в существующем формате.
5. Запиши паттерны (с анти-инфляцией) в `patterns.json`.
6. **Верификация записей draft (verifier gate — ОБЯЗАТЕЛЬНО перед записью).**
   draft — саморефлексия агента, он может содержать ошибки (глюки, неверные
   выводы, неточные сигнатуры). Каждую запись, претендующую на статус факта,
   паттерна или `suspicious`, ПРОВЕРЬ перед записью:
   - Файл/класс/метод, о котором говорит запись, реально существует (glob/grep);
   - Цифры и сигнатуры совпадают с кодом (не со слов агента);
   - Вывод о «мёртвом коде/удалённом классе» подтверждён отсутствием файла;
   - `suspicious`-сигналы, которые нельзя подтвердить — пометь «непроверено»,
     не превращай в факт. Ошибочное знание в базе хуже отсутствия знания.

## 2.5 Synthesis: Предложения для продолжения

Для каждого сигнала из draft, который не просто факт, а указывает на действие,
сформируй ранжированный список предложений. Запиши их в **очередь предложений**
(`~/.omo/memory/proposals.md` или `<repo>/.omo/memory/proposals.md`, найди через
glob):

- `[ ] skill: <имя>` — краткое обоснование, какой паттерн/edge case не покрыт.
- `[ ] AGENTS.md: <раздел>` — что изменить/добавить и почему.
- `[ ] ticket: <проект-заголовок>` — `файл:строка`, что подозрительного/баговое.
- `[ ] investigate: <кратко>` — то, что требует доисследования.

Правила:

- Однотипные сигналы за день — группируй в одно предложение, не плоди дубли.
- SUSPICIOUS → ticket-кандидат (приоритет высокий, если можно воспроизвести).
- SUBAGENT → либо улучшение существующего skill, либо новое правило в
  `AGENTS.md`/`session-draft.ts`.
- Не применяй молча — всё через human gate на шаге 3 (Skill-Evaluator).

Покажи пользователю **топ-3 предложения** в Report. Остальное остаётся в
`proposals.md` для последующего ревью.

6. **Ворнинги: выделение и вопрос человеку (human gate).**
   Собери из всех draft-файлов строки с пометкой `[WARNING]` (формат из
   session-draft.ts: `- [suspicious][WARNING] <файл>:<строка> — суть (приоритет)`).
   Покажи пользователю полный список одним блоком (файл:строка, суть, приоритет).
   Спроси по каждому ворнингу (или группой, если их много):
   - создать тикет в YouTrack (уточни проект/приоритет),
   - отбросить (не баг / неактуально),
   - отложить в `proposals.md` как `[ ] investigate:` для доисследования.
   Ворнинг считается обработанным только после ответа человека. Не создавай
   тикеты и не записывай ворнинги куда-либо вне draft без явного решения.

7. **Очисти draft — он ТРАНЗИТНЫЙ буфер, а не хранилище.**
   draft-файлы никогда не должны расти бесконечно: после консолидации каждый
   обработанный draft-файл (СТРОГО из списка шага 2.0 — чужие сессии не трогаем)
   обнуляется до шапки (заголовок + комментарий
   «обработано»), а содержимое архивируется в `draft-archive/` в том же каталоге,
   где жил файл (проектный → `<repo>/.omo/memory/draft-archive/`,
   глобальный → `~/.omo/memory/draft-archive/`) на случай «а вдруг». Если draft
   не очищен — следующая сессия начнёт с устаревшего содержимого и будет
   консолидировать его повторно.

   **Retention архива:** в конце шага 7 удаляй из `draft-archive/` (обоих
   скоупов) файлы старше 90 дней: `find <draft-archive-dir> -name "*.md" -mtime +90 -delete`.
   Архив — страховка «а вдруг», не хранилище: факты уже в facts.md/patterns.json.

**Контрольный слой (reasoning-скан):** прочитай reasoning-части текущей сессии из
opencode.db (part.type = "reasoning") и поищи сигналы дельты, которые агент НЕ записал
в draft: маркеры «не знаю/нет идей/попробую наугад/не уверен», 2+ неудачных
tool.execute подряд, смены подхода, долгий поиск перед действием. Найденное — дополни
в draft перед обработкой.

## 3. Skill-Evaluator (анализ паттернов)

- Загрузи скилл `skill-evaluator`
- Проанализируй консолидированные паттерны (из draft + сессии)
- Категория сигнала определяет маршрут рекомендации (DOMAIN → albato_domain,
  PROCESS → скилл, и т.д.) — см. патч skill-evaluator
- ROI ≥ 2 → предложи пользователю создать/улучшить скилл (через human gate)
- ROI < 2 → объясни почему

## 4. Save Facts (семантическая память)

Основной механизм — файл `.omo/memory/facts.md` (каноническое хранилище).
Плагин `memory-sync.ts` автоматически синхронизирует его в mcp-task-knowledge
(HTTP :3001) — напрямую в MCP писать не нужно.

Запиши ключевые факты сессии в `~/.omo/memory/facts.md` (или `<repo>/.omo/memory/facts.md` —
найди через glob), дописывая в конец в существующем формате:

### arch: архитектурные решения

Пример:

```
## 2026-08-21 — <краткое описание>
### fix: <суть> (importance: 8)
- <детальное описание с контекстом>
```

### fix: решения проблем

Аналогично, importance 7-8.

### pattern: найденные паттерны

Аналогично, importance 5-7.

### decision: важные решения

Аналогично, importance 6-8.

### conversation: что сделано

Аналогично, importance 4-5.

**Важно**:

- `importance` от 1 до 10 (8-10 = критично, 5-7 = важно, 1-4 = справочно)
- В каждый факт добавь достаточно контекста чтобы было понятно через полгода
- Формат: `## YYYY-MM-DD — <тема>` → `### <тип>: <суть> (importance: N)` → `- <детали>`
- НЕ перезаписывай файл — только дописывай в конец
- `facts.md` — каноническое хранилище; mcp-task-knowledge — производный индекс
  (sync автоматический через memory-sync.ts)

## 5. Boulder State

- Активный boulder → обнови `ended_at`, поставь `completed` или `paused`

## 6. Git State

- Dirty → покажи файлы, спроси коммитить

## 7. Handoff

- Остались задачи/boulder paused → создай handoff summary (формат: USER REQUESTS, GOAL, WORK COMPLETED, PENDING TASKS, KEY FILES)

## 8. Cleanup

- Cancel фоновые задачи
- compress закрытые блоки если контекст перегружен

## 9. Report

```
✅ Session End
Draft: {N строк обработано, M доменных фактов → facts.md, K паттернов → patterns.json}
Skill-Evaluator: {кандидаты или "нет паттернов"}
Memory: {N facts saved}
Boulder: {completed/paused/none}
Git: {clean/dirty}
Handoff: {создан/не требуется}
Proposals: {топ-3 из proposals.md, с типом и обоснованием}
```

После отчёта выведи **блок «Предложения для продолжения»** последним — это
гарантирует, что они не потеряются наверху:

```
### Предложения для продолжения (топ-3)
1. [skill|AGENTS.md|ticket|investigate] <имя/заголовок> — <файл:строка или причина>
2. ...
3. ...

Полный список см. в proposals.md.
```

Спроси: "Что-то ещё нужно сделать перед завершением? Или хочешь сразу взять
какое-то из предложений?"

## 10. Саммари-рефлексия (обязательно, в самый конец) — САМОРАЗВИТИЕ агента и экосистемы

Эта секция НЕ про «что сделано в задаче» (это уже в Report / фактах). Она про
улучшение процессов, скиллов, LoopX-целей, AGENTS.md и памяти — ответ на вопрос:
«какой опыт сессии превратить в знание/действие, чтобы следующий агент не наступал
на те же грабли и экосистема становилась умнее».

Формат — НЕ фиксированное число строк. Запиши СТОЛЬКО пунктов, СКОЛЬКО реально
ценных улучшений накопилось за сессию (может быть 3, может быть 30). Каждый пункт
должен вести к действию. Категории (по сути, как в Draft Consolidation):

```
## 🔄 Саммари-рефлексия (саморазвитие экосистемы)
- **[process]** <грабли/урок процесса> → куда внести (скилл X / AGENTS.md / loopx-правило)
- **[skill]** <пробел в скилле, который не покрыл случай> → улучшить скилл Y
- **[domain]** <новая механика/архитектура Albato> → facts.md / albato_domain.md
- **[infra]** <окружение/инструмент> → AGENTS.md / known limitation
- **[suspicious]** <подозрительный код/баг> → кандидат в тикет (файл:строка)
- **[subagent]** <неэффективное делегирование> → усилить/новый скилл
- **[meta]** <поведение агентов> → правило для AGENTS.md
```

Правила:

- **Честность данных ВСЕГДА, не только в коротких сессиях:** пиши только то,
  что реально произошло/выяснил. НЕ выдумывай улучшения ради полноты отчёта.
  Лучше 2 честных пункта, чем 10 надуманных. «Не выдумывай» — это правило для
  любой сессии, а не исключение.
- **Не ломай работающее — улучшай инкрементально.** Каждое изменение скилла/
  процесса/памяти — минимальное и точечное, через согласование с человеком
  (human gate). Перед синком/копированием проверяй встречное направление
  (remote/репо может быть новее — не затирай чужое). Цель — улучшить экосистему,
  а не переписать её.
- Каждый пункт — конкретное действие («добавить в скилл», «записать в facts»,
  «внести в proposals»), чтобы из него можно было извлечь выгоду.
- Не дублируй полный Report и не пересказывай факты из facts.md — фокус на
  экосистему и извлекаемые улучшения.
- Записанные в шагах 2.5 (proposals.md) и 4 (facts.md) пункты — здесь ссылкой,
  не дублируй целиком.
- Анализ/приоритизация накопленных улучшений — ОТДЕЛЬНЫЙ этап, по утверждению
  человека (например, через skill-evaluator), не автоматически в конце сессии.
- Это ПОСЛЕДНИЙ блок сообщения — после него ничего не добавляй.
