# /resume-backlog — довести репозиторий до продакшн-уровня

Аргумент: `$ARGUMENTS`. Пустой аргумент означает `status`.

Это надстройка над `/devcycle`. Она не заменяет цикл и не дублирует тик: она восстанавливает
цикл после паузы, добавляет к нему критерии готовности и проход по предложениям улучшений.
Роли, лимиты и запреты: `docs/dev-cycle/rules.md`. Критерии и формат предложений:
`docs/dev-cycle/production-grade.md`. Один тик по-прежнему делает ровно одно действие
(`docs/dev-cycle/tick.md`).

## status (по умолчанию)

Только чтение, ничего не меняет и не делает `git fetch`.

1. `node scripts/devcycle.mjs status --json` и `node scripts/devcycle.mjs state get --json`.
2. `git worktree list` и для каждого worktree проекта `git -C <путь> status --short | wc -l`:
   в заметке о паузе (`project_pause-handoff-*`) перечислены ветки с незапушенной работой,
   сверить с ней.
3. `node scripts/devcycle.mjs next --limit 5`.
4. Если есть `.devcycle/proposals.md`, посчитать записи по статусам.
5. Ответить коротко: цикл включён или нет, что требует внимания (красный CI, PR с конфликтом,
   зависшая сессия, незапушенная работа), следующий пункт, число предложений в статусе `new`.

## readiness

Снять готовность по таблице gates из `docs/dev-cycle/production-grade.md`.

1. Создать worktree от свежего `origin/master` для тяжёлых проб (`git fetch origin`, затем
   `git worktree add <каталог> -b probe/readiness-<дата> origin/master`; зависимости через
   симлинки по `rules.md`). Рабочий каталог владельца для проб не использовать.
2. Прогнать пробы R1..R14. Каждую пробу записать как `зелёный`, `красный` или `n/a` с причиной
   и выводом одной строкой. Падение, не связанное с кодом (занят порт 4001 чужим процессом,
   нет сети), это `n/a`, а не `зелёный`.
3. Таблицу выдать владельцу целиком. Каждый красный gate и каждый `n/a` без причины в
   `decisions-log.md` оформить как предложение (см. «proposals»).
4. Вердикт «прод-грейд достигнут» не выносить: только перечислить, что осталось.

## go

Восстановить цикл после паузы и запустить режим.

1. Выполнить `status`. Остановиться и спросить владельца, если: `origin/master` красный; есть
   незапушенная работа в worktree без решения, что с ней делать; открыто больше одного
   своего PR.
2. Убедиться, что исполнитель может работать. Лимит токенов OpenCode мог закончиться во время
   паузы; поручение в этом случае останется без результата. Проверить по БД
   (`oc-pulse.sh <session_id>`, чтение только `-readonly`) и по последней записи `part`
   сессии; если признаков нет, спросить владельца один раз.
3. Включить цикл так же, как `/devcycle resume`: `node scripts/devcycle.mjs state get --json`,
   `CronList`. Расписание с промптом `/devcycle tick` создавать только если его нет
   (второе расписание запрещено: два тика подряд дают два merge). Если `enabled=false`,
   спросить владельца, а не включать молча.
4. Выполнить `readiness`, если последнего снимка нет или ему больше суток.
5. Порядок выбора работы в этом режиме:
   1. красный CI master или красный gate безопасности и данных (R1, R7, R8, R12);
   2. PR в полёте по случаям A..D из `tick.md`;
   3. следующий пункт `node scripts/devcycle.mjs next`;
   4. принятые предложения класса `auto`.
   Функциональность не обгоняет надёжность: пока есть красный gate из п.1, новые фичи не
   диспетчатся.
6. Дальше работают обычные тики `/devcycle tick`. К каждому тику добавляется проход по
   предложениям (раздел «proposals»), после основного действия.
7. Записать в лог: `node scripts/devcycle.mjs log "resume-backlog go: <что увидел, что включил>"`.

## proposals

Проход по предложениям. Выполняется после основного действия тика и по запросу владельца.

1. Что искать. Пока читаешь состояние и проверяешь результат исполнителя, замечай: красный
   gate, повторяющееся падение теста, расхождение документации и кода, пункт `done` без теста,
   дубль между этапами бэклога, пробел в пробах (`n/a`), отложенный технический долг из
   `AGENTS.md` §9.
2. Оформить находку по правилам `docs/dev-cycle/production-grade.md`: только с пробой,
   сначала поиск пересечений в `BACKLOG.md`, `docs/adr`, `decisions-log.md`, не больше трёх
   новых за тик, запись в `.devcycle/proposals.md`.
3. Класс `auto`: принять решение, записать его в `docs/dev-cycle/decisions-log.md` в формате
   журнала (вопрос, решение, почему, чем проверено, как откатить) и поставить поручение
   исполнителю в свободную сессию. Контролёр `BACKLOG.md` сам не правит.
4. Класс `owner` или сомнение: не ставить поручение. Показать владельцу в отчёте с
   рекомендацией («я бы сделала X, потому что Y, цена Z»), а не списком вариантов.
5. `node scripts/devcycle.mjs log "proposals: +<n> new, <m> accepted"`.

## stop

1. Выполнить `/devcycle stop` (удаляет расписание, отключает цикл, отдаёт отчёт).
2. Добавить к отчёту сводку: таблица gates, принятые предложения, предложения в статусе
   `owner` с рекомендациями, что осталось до прод-грейда.

## Границы

Всё из `docs/dev-cycle/rules.md` действует без изменений. В частности:

- Push, PR и merge контролёр делает только по постоянному разрешению владельца для этого
  репозитория (merge при зелёном CI по текущему `headRefOid` и `mergeStateStatus=CLEAN`, по
  одному PR за раз). Если разрешения в явном виде нет, спросить.
- Не трогать: force-push, удаление веток и worktree, YouTrack и смену статусов, действия
  вне репозитория, дев-стенд на портах 3000, 3001, 3300, `--force` в мосте, `pkill -f`.
- Предложения не повод расширять задачу исполнителя: каждое идёт отдельным пунктом и отдельной
  веткой (одна задача, один PR).
- Контролёр не пишет код по задаче и не объявляет прод-грейд достигнутым.
