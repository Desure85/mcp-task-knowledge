### Added

- SC-03c FTS5 read path: `search_tasks` and `search_knowledge` pull up to 500 candidate ids from `search_fts` and rank them through the existing `hybridSearch`/`promoteExactMatches` rules instead of tokenising the whole corpus per call, so lexical floor, RRF and verbatim identifier promotion stay identical. The index is used only when completeness is proven: the metadata index reports the project complete, the FTS dirty flag is clear, and the FTS row counts equal the metadata counts with `archived = 0 AND trashed = 0` on both sides. Otherwise the request keeps the file scan, starts one background fill per project (metadata fill, then FTS project rebuild) and reports `source: 'fts'|'scan'` plus `indexing: true`, so a fallback is never presented as a complete index; `totalExact: false` and `candidates` describe a capped pool. Type-filtered `search_tasks` stays on the file path because the filter applies to the corpus before ranking. `reindex --data` now applies DATA_DIR schema migrations, so the next server boot skips its post-migration rebuild; that rebuild marks projects complete and rebuilds the search index. Measured on 100k tasks + 100k docs (`EMBEDDINGS_MODE=none`): `search_tasks` median 544 ms / p95 598 ms, `search_knowledge` 42 ms / 636 ms, cold start 625 ms, RSS 156 MB (previously 23.6 s and 4.1 GB). Tests: 7 tool-level cases in `tests/search-fts.test.ts`; `node scripts/kb-bench.mjs retrieval --via-tool` runs the real tool, fails when any query is answered by the scan, and reports hit@1 77.8 / MRR 0.838 vs 77.8 / 0.830 for the old path (530 chunks, embeddings off)
- SC-03b FTS5 write path: task and document mutations (`createTask`, `updateTask`, `moveTasksToType`/`moveTasksToStatus`, `deleteTaskPermanent`, `createDoc`, `updateDoc`, `deleteDocPermanent`, `project_delete`) keep the `search_fts` table in step, called from the storage layer next to the metadata-index hooks so bulk tools and `project_purge` are covered without their own hooks. Indexed text comes from `buildTextForTask`/`buildTextForDoc`, the same builders BM25 uses; rows are keyed by `(store, kind, id)` with `store` = `resolveStoreId(TASKS_DIR|KNOWLEDGE_DIR)`. Archived and trashed rows leave the searchable corpus and return on restore. A failed index write never fails the mutation: it logs and sets `search_meta.dirty`. `reindex --data` rebuilds the search index (fully or for `--project`) and no longer skips when it is missing or dirty; `reindex --verify` exits 1 on row/term drift; `doctor` reports `fts-unavailable`/`fts-dirty`/`fts-drift`/`fts-stale-terms` with per-store counts.
