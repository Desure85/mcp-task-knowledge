# Масштабируемость mcp-task-knowledge: 1k → 100k → 1M (2026-10-31)

> Замеры, а не оценки. Все цифры получены на реальном сервере (`dist/index.js`) через настоящий
> MCP-клиент (`@modelcontextprotocol/sdk` 1.17.4) и реальный браузер (Chrome через `playwright-core`).
> Код приложения не менялся. Скрипты: `scripts/bench/` (`seed-scale.mjs`, `run-scale.mjs`,
> `ui-bench.mjs`, `graph-bench.mjs`), запуск — `npm run bench:scale`.

## 1. Методика

**Данные.** Генератор `scripts/bench/seed-scale.mjs` пишет файлы напрямую в изолированный `DATA_DIR`
в том же формате, что и приложение: задачи — `tasks/<project>/<uuid>.json` (`JSON.stringify(data, null, 2)`,
как `writeJson` в `src/fs.ts:30-42`), документы — `knowledge/<project>/<uuid>.md` с YAML-frontmatter
через `gray-matter` (как `createDoc`, `src/storage/knowledge.ts:58`), граф памяти —
`memory/temporal-graph.json` (`{facts, version}`, `src/memory/temporal-graph.ts:125-128`).
Профиль: статусы `pending/in_progress/completed/closed/blocked` с весами 38/22/24/12/4, приоритеты
low/medium/high 25/55/20, 0–4 тега из пула 30, подзадачи у ~15 %, зависимости у ~10 % (1–3 ребра),
архив 2 %, корзина 1 %, документы 1–8 КБ, иерархия у ~20 % документов. Генерация детерминирована
(`--seed`), поэтому прогоны воспроизводимы.

**Прогон.** `scripts/bench/run-scale.mjs`: спавнит сервер на свободном порту (`MCP_TRANSPORT=http`,
`MCP_HOST=127.0.0.1`), ждёт `GET /healthz` → 200, логинится через `POST /auth/login`, открывает
Streamable HTTP сессию, вызывает `mcp.authenticate`, затем гоняет операции по 3 повтора и берёт
медиану и p95. Размер ответа — `Buffer.byteLength` от `content[0].text`, то есть ровно те байты,
что улетают в контекст агента и в браузер.

**Изоляция от фонового шума.** `SECURITY_STACK=0` (иначе `AuditLogger` делает `appendFileSync` на
каждый вызов — `src/audit/logger.ts:118-126`, а token bucket 60/100/1 rps режет длинные циклы —
`src/core/rate-limiter.ts:190-194`), `EMBEDDINGS_MODE=none` (векторный канал отключён — все цифры
поиска это **BM25 без векторов**), `TASK_CLAIM_SWEEP_MS=0`, `CATALOG_ENABLED=false`,
`CURRENT_PROJECT=bench`. Аутентификация при этом включена: `AuthManager` создаётся независимо от
security stack (`src/core/app-container.ts:493-530`).

**ФС.** `/tmp` на этой машине — **tmpfs (RAM-backed)** с ~1.0M свободных inodes, поэтому основной
прогон сделан на ext4 (`/dev/sda2`, как в проде), а tmpfs использован как контроль: разница 5–20 %
(см. §3.5). Для 1M файлов в `/tmp` не хватало запаса inodes (1.0× при требовании ≥3×), поэтому
1M измерен как 1M пустых файлов-заглушек на ext4 в одном каталоге + экстраполяция.

**Окружение.** 72 vCPU, 47 GiB RAM (доступно ~14 GiB), zram-swap, Node v26.8.1 (сервер),
MCP SDK 1.17.4, ext4 на `/dev/sda2` (97 % занято на момент прогона), Chrome `/usr/bin/google-chrome`.

**Ограничения методики.** Машина общая: разброс между повторами достигает 2–6× на 100k
(GC и page cache), поэтому в таблицах есть и медиана, и p95, а выбросы отмечены. Первый вызов
операции всегда дороже последующих (прогрев JIT и кэшей) — это видно в `allMs` в JSON-результатах.

## 3. Где именно уходит время (корневые причины)

### 3.1 Сканирование всех файлов на каждый запрос

`listTasks` (`src/storage/tasks.ts:120-156`) делает `readdir` каталога проекта и **последовательно**
(`await` в `for`) читает и парсит каждый `.json`, а фильтры `status`/`tag` применяет уже после
чтения файла (`:148-149`). `listDocs` (`src/storage/knowledge.ts:66-106`) делает то же через
`fast-glob` + `readText` + `gray-matter` для каждого `.md` — YAML-парсинг дороже `JSON.parse`.

In-process на 100k (без транспорта):

| Шаг | Время | RSS |
|---|---|---|
| `listTasks` | 4 272 мс (n=97 070 после фильтра archive/trash) | 189 MB |
| `listTasksTree` | 4 636 мс | 275 MB |
| `JSON.stringify` конверта (59 MB) | 291 мс | — |
| `listDocs` (100k метаданных) | 11 614 мс | 1 969 MB |
| `readDoc` × 97 944 | 5 828 мс | 2 961 MB |
| BM25 по 100k задачам | 1 734 мс | 2 083 MB |
| BM25 по 100k документам (~400 MB текста) | **23 631 мс** | **4 128 MB** |

То есть 38 с `tasks_list` по HTTP = 4.3 с сканирования + 0.3 с сериализации + **~33 с на стороне
клиента/транспорта** (см. §3.2).

### 3.2 Квадратичное обрамление сообщений в MCP SDK — главный убийца больших ответов

`ReadBuffer.append` в `@modelcontextprotocol/sdk` 1.17.4 (`dist/esm/shared/stdio.js:6-13`) на каждый
чанк делает `Buffer.concat([buffer, chunk])`. Для одного сообщения это O(n²). Прямой замер на
сообщении 64.6 MB (тот же `tasks_list` на 100k):

| Шаг | Время |
|---|---|
| `Buffer.concat` 64 KiB-чанками (как в SDK) | **22 434 мс** |
| `JSON.parse` | 150 мс |
| `JSONRPCMessageSchema.parse` (zod) | 2 мс |

Итог: **размер ответа стоит не «токенов», а квадратичного времени у получателя**. 5.9 MB (10k)
→ ~0.5 с, 59 MB (100k) → ~22 с, 590 MB (1M) → ~37 минут только на склейку буфера. Это касается
любого MCP-клиента, включая агентов, а не только нашего теста.

### 3.3 Дефолтный таймаут MCP SDK — 60 секунд

`Client.callTool` без явного `timeout` падает с `MCP error -32001: Request timed out` на
`knowledge_list(100k)` и `tasks_dag(100k)`. В первом прогоне это выглядело как «транспортная ошибка»,
а не как «операция медленная». Для бенчмарка пришлось передавать `{ timeout }` третьим аргументом
(`scripts/bench/run-scale.mjs`). Для агента это означает: всё, что дольше 60 с, недоступно вообще.

### 3.4 Поиск пересобирает индекс на каждый запрос

`bm25Search` (`src/search/bm25.ts:33-92`) на каждый вызов токенизирует весь корпус
(`docs.map(d => ({...d, tokens: tokenize(d.text)}))`, `:42`) и строит `df` с нуля (`:46-54`).
Инвертированного индекса нет. Плюс `search_knowledge` (`src/register/search.ts:63-101`) сначала
вызывает `listDocs` (полный обход 100k файлов), затем `readDoc` **для всех** документов
(`Promise.all` без ограничения конкурентности — риск `EMFILE` на больших N), и только потом BM25.
Кэш `rankedCache` (TTL 60 с) спасает повторы, но `listDocs` всё равно вызывается до проверки кэша
(`:65`), то есть каждый поиск платит полное сканирование.

### 3.5 ФС не виновата: tmpfs vs ext4

| Операция (10k) | ext4 | tmpfs | Дельта |
|---|---|---|---|
| `tasks_list` | 897 мс | 735 мс | −18 % |
| `knowledge_list` | 968 мс | 922 мс | −5 % |
| `knowledge_tree` | 1 029 мс | 1 017 мс | −1 % |
| `search_knowledge` | 676 мс | 545 мс | −19 % |

Даже RAM-диск даёт считанные проценты — значит доминирует CPU (парсинг JSON/YAML, токенизация),
а не I/O. **Но холодный кэш страниц меняет картину на порядок:** 1000 случайных файлов на 100k
читаются 25 846 мс холодными и 233 мс тёплыми (25.8 мс против 0.23 мс на файл). При холодном
кэше первый `tasks_list` на 100k может занять десятки минут; замеренные 38 с — это **тёплый** кэш.

### 3.6 Блокировки: одна запись на проект

`withFileLock` (`src/fs.ts:51-65`) — in-process `Map` промисов, без межпроцессной координации.
Ключи: `workflow:<project>` и `task:<project>/<id>`. `createTask` и `updateTask` берут
`workflow:<project>` (`src/storage/tasks.ts:66`, `:392`), то есть **все записи задач одного проекта
сериализуются**, даже если правятся разные задачи. Два сервера на одном `DATA_DIR` не
скоординированы вообще (это записано в комментарии `src/fs.ts:47-50`).

### 3.7 Память графа: перезапись всего файла

`TemporalGraph.save()` (`src/memory/temporal-graph.ts:155-162`) пишет весь `temporal-graph.json`
(`JSON.stringify(..., null, 2)`) на каждую мутацию. 100k фактов = 48 MB файла: `add` = 451 мс,
`query` = 439 мс. Линейно и терпимо до ~500k, но при 1M это ~480 MB файла и ~4–5 с на каждую запись,
плюс пиковая память на сериализацию.

### 3.8 Git-слой истории (MU-03) не реализован

`rg "simple-git|git commit"` по `src/` не находит ничего; MU-03 в `BACKLOG.md:1087` — `pending`.
Версионирование документов сейчас — файловые снапшоты в `knowledge/<project>/.versions/<id>/` на
каждое обновление (`src/storage/knowledge.ts:144-149`), то есть каталог растёт от числа правок,
а не от числа документов. Замерить «git-коммит на операцию при 100k файлах» невозможно — слоя нет;
прогноз в §5.

## 5. Пределы комфортной работы и прогноз для 1M

**Предел = N, при котором операция перестаёт быть интерактивной (> 1 с).** Линейная экстраполяция
подтверждена замерами в двух точках (10k и 100k) для всех списочных операций.

| Направление | > 1 с начиная с | 100k (замер) | 1M (прогноз) |
|---|---|---|---|
| `tasks_list` | **~11 000** | 38 с, 56 MiB | ~43 с compute + **~37 мин** на обрамление, 590 MB ответ |
| `tasks_tree` | ~13 000 | 41 с, 60 MiB | то же + построение дерева |
| `knowledge_list` | **~10 000** | 60 с, 41 MiB | ~116 с compute, 430 MB ответ → таймаут/падение |
| `search_tasks` | ~18 000 | 6.9 с | ~69 с (пересборка индекса на запрос) |
| `search_knowledge` | ~15 000 | 44 с (первый), 6.9 с (повтор) | ~410 с, RSS ~41 GB → **OOM** (heap 4.2 GB) |
| `dashboard_stats` | ~14 000 | 9.7 с | ~97 с |
| `briefing` | ~15 000 | 8.7 с | ~87 с, 25 MB ответ |
| `tasks_get/create/update` | не деградирует | 4–6 мс | ~5 мс (O(1)) |
| `memory_temporal_query` | — | 439 мс на 100k фактов | ~4.4 с на 1M |
| UI `/tasks` | **~2 000** | 6 с, 105k DOM | ~1M DOM → вкладка умирает |
| UI `/knowledge` | ~2 000 | 6.8 с, 86k DOM | то же |
| Граф | **~300** | 1000 = 2.3 с; 5000 = 13.7 с | неприменимо без кластеризации |

**1M файлов на ФС (заглушки, ext4, один каталог):**

| Операция | 1M |
|---|---|
| Создание 1M файлов | 103 с |
| `readdir` (тёплый) | 1 063–1 089 мс (dir_index работает) |
| `stat` × 1000 | 17 мс |
| `readFile` × 1000 (пустые) | 72–151 мс |
| `rm -rf` 1M | 24.8 с |

То есть **сам каталог на 1M файлов переживаем**, но приложение на нём — нет: каждый списочный
вызов читает и парсит 1M файлов, а ответ в сотни мегабайт убивает клиента квадратичным обрамлением.

## 6. Решения: варианты, стоимость, порядок

Оценки — в человеко-днях одного разработчика, включая тесты; без UI-полировки, если не указано.

### (а) Серверный индекс метаданных (SQLite + FTS5)

**Что:** таблица `tasks(id, project, status, priority, updated_at, parent_id, tags, …)` и
`docs(...)` + FTS5 по тексту; файлы остаются источником истины, индекс перестраиваемый.
Обновление на записи (в той же критической секции, что и `writeJson`), сверка при старте
(быстрый `stat`-проход или ленивая проверка), полная перестройка по команде.
**Почему:** убивает и O(N)-скан, и холодный кэш (один B-tree вместо 100k `open`), и пересборку BM25
на запрос. `better-sqlite3` уже в зависимостях.
**Стоимость:** 8–12 дней (схема, миграция/бэкфилл, инвалидация, сверка, FTS5-поиск, тесты на
эквивалентность текущему поведению). Риск: рассинхрон индекса и файлов при внешних правках —
закрывается сверкой при старте и `doctor`.

### (б) Пагинация, `fields`, `count`, серверные фильтры (U-04)

**Что:** `limit`/`cursor` (opaque base64 от `(updatedAt desc, id)`), `fields: string[]`,
`count`/`count-only`, `maxBytes` с `{items, nextCursor, truncated}`, фильтры `status/tag/type/parentId`
на сервере для всех list/search-инструментов. Контракт breaking, клиентов пока нет.
**Почему:** самый дешёвый способ убрать мегабайтные ответы — а именно они дают квадратичное время
и разрушают контекст агента. Даже без индекса (а) это снижает 38 с до ~5 с: скан остаётся, но
транспорт и обрамление исчезают.
**Стоимость:** 5–7 дней (единый пост-фильтр + курсор + тесты `tests/response-economy.test.ts`).
Связано с U-04 (`BACKLOG.md:1143`) — можно делать как U-04, расширенный курсором.

### (в) UI: серверная пагинация и виртуализация

**Что:** доска грузит по колонкам (`status` + `limit`), счётчики — из `count`/`dashboard_stats`,
карточки виртуализируются; список знаний — серверная пагинация + виртуализация; фильтры уходят на
сервер.
**Почему:** 105k DOM на 10k задач и 6 с до отрисовки; при 100k вкладка нежизнеспособна.
**Стоимость:** 5–8 дней (доска 3–4, знания 2–3, счётчики 1). Зависит от (б): без серверных
`limit/count` виртуализация не поможет — данные всё равно придут целиком.

### (г) Граф: лимит, кластеризация, окрестность, уровень детализации

**Что:** жёсткий лимит узлов (200–300) с явным «показано N из M», режим окрестности выбранного узла
(`depth=1..2`), кластеризация по типу/тегу с раскрытием, легенда и LOD (подписи только у крупных
узлов, остальные — точки).
**Почему:** 1000 узлов = 2 с и 2 с Long Tasks, 5000 = 13.7 с и 16.3 с блокировки; подписи на 1000
уже нечитаемы.
**Стоимость:** 3–5 дней (лимит+окрестность 1–2, кластеризация 2–3).

### (д) Архивирование, ретеншн и шардирование каталогов

**Что:** автоархив закрытых задач старше T (по умолчанию не удалять), вынос архивных в отдельный
каталог/шард, шардирование `tasks/<project>/<ab>/` и `knowledge/<project>/<ab>/` по первым двум
символам id при > 50k файлов в проекте, фоновая компакция.
**Почему:** `readdir` на 1M тёплый — 1.07 с, но холодный обход 1M файлов и `rm -rf` (24.8 с) —
это операции обслуживания; шардирование уменьшает и то, и другое, и снимает «один каталог на всё».
**Стоимость:** 2–4 дня (миграция с обратной совместимостью чтения обоих layouts — паттерн уже есть
в `listTasks`/`listDocs`).

### (е) Влияние на MU-03 (git-история)

**Что:** если MU-03 будет делать коммит на каждую операцию, то при 100k+ файлов каждый коммит — это
`git add`/`status` по рабочему дереву, то есть O(N) на запись. При 1M файлов это гарантированный
стоп. **Рекомендация:** пакетный коммит (очередь изменений + коммит по таймеру/размеру пачки),
либо отдельный git-репозиторий только для истории с узким набором путей, либо хранить историю в
SQLite-таблице ревизий, а не в git.
**Стоимость:** +1–2 дня к дизайну MU-03 (сам MU-03 в бэклоге, `pending`).

### (ж) Что делать в первую очередь

1. **(б) пагинация/`fields`/`count`/серверные фильтры** — 5–7 дней. Максимальный эффект на единицу
   работы: убирает мегабайтные ответы и квадратичное обрамление, чинит и агента, и UI, и не требует
   индекса.
2. **(а) SQLite-индекс** — 8–12 дней. Убирает O(N)-скан, холодный кэш и пересборку BM25; после него
   `limit`-запросы становятся O(log N) вместо O(N).
3. **(в) UI-пагинация/виртуализация** — 5–8 дней (после б).
4. **(д) шардирование/ретеншн** — 2–4 дня (можно параллельно с (в)).
5. **(г) граф** — 3–5 дней (независимо).
6. **(е) решение по MU-03** — до начала реализации MU-03.

Итого критический путь до «100k комфортно»: **(б) → (а) → (в)** ≈ 18–27 дней; до «1M возможно» —
плюс (д) и пересмотр формата хранения (индекс обязателен, файлы — только источник истины).

## 7. Что не удалось измерить и почему

| Что | Почему |
|---|---|
| Полный датасет 1M файлов (задачи+доки) | `/tmp` — tmpfs с ~1.0M inodes (запас 1.0× при требовании ≥3×) и RAM-backed; 1M на ext4 измерен заглушками, приложение на 1M не запускалось |
| Векторный поиск / гибрид | `EMBEDDINGS_MODE=none` по условию задачи; все цифры поиска — BM25 без векторов. ONNX-индексация 100k доков не мерилась (по прошлому отчёту 146 чанков ≈ 40 с CPU → 100k ≈ 7.6 ч) |
| Git-слой истории (MU-03) | Не реализован в этом коммите (`BACKLOG.md:1087` — pending); прогноз в §6(е) |
| Холодный старт на 100k с полностью холодным page cache | Требует `drop_caches` (нужен root) или перезагрузки; измерен частично (1000 файлов холодно = 25.8 с) |
| Конкурентная нагрузка (несколько агентов) | Бенчмарк последовательный: одна сессия, один вызов за раз; `withFileLock` сериализует записи, но конкурентность не измерялась |
