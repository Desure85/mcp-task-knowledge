# AUD-18: аудит data-path (storage → sync → search → memory)

- **Дата:** 2026-11-12
- **Статус:** research done, remediation — отдельными пунктами (AUD-18d/AUD-18e и новые)
- **Метод:** чтение кода + существующие тесты; без нагрузочных замеров и без записи в прод-данные.

## 1. Скоуп и инварианты

Скоуп: путь записи и чтения задач, документов знаний, FTS/метаданных, памяти агента, sync-стека.

Инварианты, которые проверялись:

1. **I1 — файл = истина.** После успешного ответа MCP файл сущности содержит новое состояние.
2. **I2 — атомарность.** Падение процесса между шагами не оставляет полу-записанный JSON/Markdown.
3. **I3 — согласованность индекса.** FTS/metadata index не отдаёт удалённую/старую сущность после restart+rebuild.
4. **I4 — один писатель на сущность.** Конкурентные write не теряют поля (LWW допустим только явно).
5. **I5 — детерминированный порядок.** Курсоры/страницы не пропускают и не дублируют записи при равных mtime.
6. **I6 — память не теряет факт.** Append факта либо полностью применён, либо не применён.
7. **I7 — sync-стек подключён или удалён.** Мёртвый код не создаёт ложного ощущения синхронизации.
8. **I8 — логи не растут неограниченно.**

## 2. Наблюдения по слоям

### 2.1 Storage (tasks/docs)

- `src/fs.ts:30` `writeJson`: tmp-файл + `rename` — **I2 выполнен** для одного файла, но **нет `fsync`** ни файла, ни каталога:
  при отключении питания возможна потеря последнего rename. Для file-профиля это документированное ограничение, не баг.
- `src/storage/tasks.ts:131,557,840` пишут файл, затем `indexTaskWrite` и `noteTaskWritten`.
  Порядок «файл → индекс» корректен, но **`indexTaskWrite` не ретраится**: ошибка индекса оставляет файл новым,
  индекс старым. `ensureProjectIndexed` лениво чинит страницу, но не гарантирует rebuild после падения.
  → **I3 частично нарушен** (self-healing отложенный, не гарантированный).
- `withFileLock` (`src/fs.ts:51`) — **in-process Map**, не межпроцессный. Два процесса/два stdio-сервера на одном
  `DATA_DIR` не сериализуются; тест «два писателя» проверяет очередь внутри одного процесса.
  → **I4 ограничен**; это записано в MU-07.
- `writeJson` не делает merge: два конкурентных read-modify-write теряют поля без `expectedVersion` (MU-02 LWW).
  CAS с `expectedVersion` закрывает только явный конфликт, не слепые patch-и.

### 2.2 Metadata index

- `indexTaskWrite` вызывается после записи файла; при ошибке — WARN/пропуск, файл уже виден.
- Ключ страницы — `mtimeMs` + id (`tasks.ts:175`); при равных mtime используется id, порядок детерминирован
  → **I5 выполнен** для файлового пути; SQLite-индекс использует свои mtime, возможна рассинхронизация.
- Индекс не является истиной: rebuild возможен, но **не автоматический** при расхождении (есть doctor/CLI).

### 2.3 FTS

- `noteTaskWritten`/`noteTaskRemoved` — очередь в памяти процесса; при крэше между файлом и flush событие теряется.
- FTS — производный слой; потеря события означает stale-поиск до rebuild. Automatic rebuild не зафиксирован.
  → **I3 частично**; для поиска допустимо, для «задача исчезла из поиска» — нет.

### 2.4 Memory

- `src/memory/layers.ts:76` — `writeFileSync` без tmp+rename: **I2 нарушен** для layered memory.
- `entity-graph.ts:460` использует `writeFileAtomicSync` — атомарно, но без fsync.
- Граф фактов переписывается целиком (~750 КБ на факт) — **I6** зависит от атомарности; при неатомарной записи
  возможен частичный JSON. Это же — причина AUD-18d (EventLog) и MU-06.
- Мультиклиентность: файловая очередь in-process, межпроцессной блокировки нет.

### 2.5 Sync-стек

- `src/sync/` не подключён к рантайму: `threeWayMerge` не вызывается из register/storage.
  `AUD-18e` фиксирует LWW без tiebreaker и `null` при ручных правках.
  → **I7 нарушен**: код есть, поведение не определено. Решение: либо wire, либо удалить (AUD-18e).

### 2.6 Логи

- EventLog `persist()` переписывает весь лог на каждый append; `compactThreshold` не используется.
  Лог растёт неограниченно → **I8 нарушен** (AUD-18d).

## 4. Рекомендации (не выполнены в этом пункте)

1. **D1:** перевести `layers.ts` на `writeFileAtomicSync`.
2. **D2:** при ошибке `indexTaskWrite` помечать проект `dirty` и планировать rebuild на следующем старте.
3. **D3:** либо документировать «один процесс на DATA_DIR», либо ввести lock-файл с PID/таймаутом.
4. **D4:** FTS-очередь — durable JSONL или rebuild по mtime при старте.
5. **D5:** решить AUD-18e: wire с tiebreaker или удалить `src/sync/`.
6. **D6:** EventLog — компакция по threshold или переход на append-only JSONL.
7. **D7:** оставить как ограничение file-профиля; для SQLite/Postgres атомарность БД.

## 5. Что проверено тестами, а что нет

- Проверено: атомарная запись tasks (`writeJson` tmp+rename), два писателя в одном процессе (MU-07),
  CAS-конфликт (MU-02), восстановление batch-истории (MU-07).
- Не проверено: SIGKILL между rename и index, два процесса на одном DATA_DIR, FTS rebuild после потери события,
  частичный JSON layered memory, EventLog при тысячах append.

## 6. Вывод

Data-path в файловом профиле **не имеет единой транзакционной границы**: файл, индекс и FTS обновляются
последовательно и могут разойтись. Для одного процесса это самовосстанавливается лениво; для нескольких
процессов и для памяти — нет. Аудит закрывает research-часть AUD-18; исправления вынесены в отдельные пункты.
