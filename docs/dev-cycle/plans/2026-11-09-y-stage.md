## 2. Порядок работ и зависимости

```
Y-02e1 → Y-02e2 → Y-02e3                (точка сборки и регистраторы, кроме search.ts)
        ↓
Y-03a → Y-02e4 → Y-03b → Y-03c          (Y-03a: SearchProvider; Y-02e4 закрывает Y-02
                                         переключением search.ts; затем отпечаток и индексация)
        ↓
Y-04a → Y-04b                           (внешние провайдеры по флагу; зависит от Y-03)
        ↓
Y-05a → Y-05b → Y-05c                   (SQLite: Store → Search/Vector/History/Lock → диагностика/бенчмарк)
        ↓
Y-07a → Y-07b                           (BlobProvider: контракт → S3/MinIO)
        ↓
Y-06a → Y-06b                           (Postgres: Store/Search → pgvector/версии)
        ↓
Y-08a → Y-08b                           (migrate-storage: file↔sqlite, затем с Postgres)
```

Почему такой порядок:

1. **Y-02e первым.** Пока регистраторы не получают хранилища из контекста, любой новый профиль
   (SQLite, Postgres) некуда подключить: точка сборки одна — `AppContainer`. Один файл —
   `register/search.ts` — зависит от индексного слоя, а не от коллекций, и переключается в Y-02e4
   сразу после того, как Y-03a введёт `SearchProvider`.
2. **Y-03/04 до VectorProvider.** `Y-05b` и `Y-06b` реализуют `VectorProvider` для профилей, но
   сам контракт и отпечаток модели рождаются в `Y-03`; делать их после — значит переделывать.
3. **Y-05 до Y-06.** SQLite встраивается в текущий процесс и в тестах дешевле; на нём проверяются
   контракты Store/Search/History/Lock, которые потом повторяются в Postgres без изменений
   (один набор контрактных тестов на профиль — ADR-009).
4. **Y-07 до Y-06.** BlobProvider не зависит от Postgres и добавляет в CI второй сервис (MinIO);
   разносить инфраструктурные изменения по времени дешевле, чем делать оба сервиса в одном PR.
5. **Y-08 последним.** Миграция требует двух готовых профилей; раньше неё писать движок не по
   чему проверять.
6. **Y-04 после Y-03**, потому что политика внешних вызовов стоит на `EmbeddingProvider` и
   отпечатке: без отпечатка нельзя исключать приватные проекты и учитывать стоимость по коллекциям.

## 4. Гейты и риски

| # | Риск/гейт | Что делаем | Куда записываем |
|---|---|---|---|
| 1 | `sqlite-vec` может отсутствовать/быть несовместим с Node 24 или Docker | Y-05a — явный гейт-прогон; при провале `VectorProvider` объявляет недоступность, поиск идёт без векторов с признаком в статусе (ADR-009 разрешает) | решение Y-05a, `doctor` |
| 2 | Postgres в CI | Y-06a добавляет сервис-контейнер; без него DoD не закрывается — контрактный набор обязан гоняться на реальном Postgres | CI-воркфлоу, решение Y-06a |
| 3 | MinIO/S3 в CI | Y-07b: сервис MinIO в CI; при недоступности — документированный пропуск и ручной прогон, DoD фиксирует это как ограничение среды | решение Y-07b |
| 4 | Внешние вызовы эмбеддингов | тесты только с fake/mock; сеть запрещена; ключи через SecretManager; по умолчанию внешних вызовов нет | решение Y-04 |
| 5 | Окно паузы записи при миграции 100k | измеряем в Y-08a; если неприемлемо — фиксируем ограничение в отчёте миграции, а не замалчиваем (ADR-009) | отчёт миграции |
| 6 | Локальная среда: Windows, 72 ядра, нет Docker; полный прогон только `--maxWorkers=4` | сервисы (Postgres/MinIO) проверяются в CI; локально — точечные наборы `--maxWorkers=2` | AGENTS |
| 7 | Регресс wire-формата | каждый инкремент с изменением доступа к хранилищу обязан сохранять ответы инструментов; паритетные тесты в Y-02e2/e3 и контрактные — в остальных | решения инкрементов |

## 5. Gate-условие закрытия этапа Y

Этап Y закрывается, когда:

1. все строки Y-02…Y-08 — `done`, подпункты закрыты;
2. один и тот же контрактный набор (`tests/storage-contract.test.ts`) зелёный на трёх профилях:
   file, sqlite, postgres;
3. `tests/embedding-contract.test.ts`, `tests/embedding-external-policy.test.ts`,
   `tests/blob-provider.test.ts`, `tests/storage-migrate.test.ts` зелёные (включая сервисные прогоны
   CI для Postgres/MinIO);
4. `migrate-storage` проверен в обе стороны с dry-run, идемпотентностью и откатом конфигурацией;
5. бенчмарки `docs/benchmarks/` содержат сравнение профилей (file vs sqlite vs postgres) по
   `hit@1`, `medianMs`, RSS на 100k;
6. `doctor` показывает активный профиль, манифест и возможности, а не «предполагаемые»;
7. документация (`docs/getting-started/configuration.md`, `docs/architecture.md`, индекс ADR) и
   `CHANGELOG.md` обновлены; AGENTS/BACKLOG без расхождений (`npm run backlog:check` зелёный).

## 6. Откат плана

План — документ; откат не требуется. Каждый инкремент обратим отдельно: Y-02e — вернуть прямые
импорты в регистраторах; Y-03/Y-04 — вернуть адаптер и отключить флаг; Y-05/Y-06 — вернуть
`STORAGE_PROFILE=file` (данные профиля не удаляются до подтверждения); Y-07 — файловый BlobProvider
остаётся реализацией по умолчанию; Y-08 — вернуть конфигурацию активного профиля, пока старый цел.
