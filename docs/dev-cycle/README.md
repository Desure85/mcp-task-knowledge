# Цикл разработки mcp-task-knowledge

Документ описывает управляемый цикл разработки: контролёр проверяет состояние репозитория,
выбирает один пункт бэклога, поручает его исполнителю, проверяет результат по первоисточникам
и доводит до merge. Процесс перенесён из личных файлов контролёра в репозиторий, чтобы его
можно было читать, обсуждать и менять как код.

Цикл не заменяет разработку вручную. Он формализует то, что иначе живёт в голове владельца:
кто принимает решения, что можно делать без спроса, и как отличить «работает» от «агент сказал,
что работает».

## Роли

| Роль | Кто | Задача |
|------|-----|--------|
| Контролёр | Claude Code, сессия с расписанием | Читает состояние, принимает решения, диспетчит, проверяет, делает push, PR и merge |
| Исполнитель | OpenCode через мост `opencode-bridge` (`OC_BRIDGE`) | Работает в отдельном worktree, коммитит локально, отчитывается по sha и проверкам |
| Состояние цели | LoopX | Хранит очередь цели и квоту; служит подсказкой, а не источником правды |
| Очередь | `BACKLOG.md` (`DEVCYCLE_BACKLOG`) | Источник пунктов, приоритетов и зависимостей |

Контролёр не пишет код по задаче. Исполнитель не делает push, PR и merge: это работа контролёра.
Мост доставляет поручение в живую сессию OpenCode, поэтому у исполнителя сохраняется весь
контекст его worktree и предыдущих коммитов.

## Схема цикла

```
тик
  -> квота LoopX и состояние (status)
  -> выбор одного пункта (next)
  -> диспетч исполнителю (мост opencode-bridge)
  -> проверка результата по первоисточникам (CI по sha, git, ветка)
  -> push, PR, merge при зелёном CI и mergeStateStatus CLEAN
  -> лог тика и запись решения в журнал
```

Один тик делает одно действие. Если подходящих случаев несколько, берётся первый по порядку
A, B, C, D, E, F из `tick.md`. Два пункта за тик не диспетчатся, две PR за тик не мержатся.

## Что где лежит

| Путь | Назначение |
|------|------------|
| `docs/dev-cycle/README.md` | Этот файл: роли, схема, запуск и остановка |
| `docs/dev-cycle/tick.md` | Инструкция одного тика и правила очереди |
| `docs/dev-cycle/rules.md` | Что разрешено и запрещено контролёру и исполнителю |
| `docs/dev-cycle/production-grade.md` | Критерии готовности (gates R1..R14) и протокол предложений улучшений |
| `docs/dev-cycle/decisions-log.md` | Журнал решений контролёра с основанием и откатом |
| `scripts/devcycle.mjs` | CLI цикла, единственная точка входа |
| `scripts/lib/devcycle-*.mjs` | Логика выбора пункта и вспомогательные модули |
| `.claude/commands/devcycle.md` | Слэш-команда контролёра `/devcycle` |
| `DEVCYCLE_STATE_DIR` (по умолчанию `.devcycle/`) | Локальное состояние `state.json` и лог `log.md`, в git не попадает |
| `DEVCYCLE_BACKLOG` (по умолчанию `BACKLOG.md`) | Очередь пунктов на свежем `origin/master` |

Каталог состояния локальный: у каждого контролёра своё расписание, свой `cronId` и свой лог.
Поэтому `.devcycle/` не коммитится и не должен попадать в артефакты сборки.

## Команды

CLI без внешних зависимостей, запускается через Node:

```
node scripts/devcycle.mjs status [--json] [--fetch]
node scripts/devcycle.mjs next [--json] [--backlog <path>] [--limit <n>]
node scripts/devcycle.mjs state get|enable|disable [--reason <text>] [--cron-id <id>] [--json]
node scripts/devcycle.mjs log "<text>"
node scripts/devcycle.mjs tick [--dry-run] [--json]
node scripts/devcycle.mjs report [--json]
```

| Код | Значение |
|-----|----------|
| 0 | Успех. Недоступный внешний источник отражается как `n/a: причина`, это не ошибка |
| 1 | Ошибка выполнения |
| 2 | Неверные аргументы |
| 3 | Пропуск: цикл выключен или lock занят другим тиком |

Код 3 нужен расписанию: пропуск не должен выглядеть как падение и не должен поднимать тревогу.
Контролёр в этом случае пишет в лог причину пропуска и завершает тик.

Слэш-команда контролёра:

| Команда | Что делает |
|---------|------------|
| `/devcycle status` | Выполняет `status` и кратко пересказывает по-русски, что требует внимания |
| `/devcycle start` | Включает цикл, создаёт расписание и записывает `cronId` |
| `/devcycle resume` | Восстанавливает расписание после перезапуска сессии |
| `/devcycle stop` | Удаляет расписание, выключает цикл, печатает отчёт |
| `/devcycle tick` | Выполняет один тик по инструкции `tick.md` |
| `/devcycle next` | Показывает следующий пункт очереди и пропущенные |
| `/devcycle report` | Печатает журнал решений и смерженные PR за последние сутки |

## Проба и действие

`status` это read-only проба. Она не делает `git fetch`, не двигает квоту LoopX (использует
`loopx turn plan`, а не `quota should-run`), не пишет в состояние и не отправляет поручений.
Флаг `--fetch` добавляет только обновление remote refs. Секции отчёта: Цикл, LoopX, GitHub,
OpenCode, Worktrees, Решения. Любой недоступный источник даёт `n/a: причина` и код 0.

`tick` это действие. Он берёт lock, делает `git fetch`, проверяет состояние, может отправить
поручение, сделать push, PR или merge и обязательно пишет строку в лог. Флаг `--dry-run`
показывает план без побочных эффектов.

Разделение важно для диагностики: `status` можно звать сколько угодно и в любой момент, `tick`
нельзя запускать параллельно, поэтому второй экземпляр получает код 3.

## Запуск, возобновление, остановка, проверка

### Запуск

`/devcycle start` выполняет `state enable`, создаёт расписание каждые 15 минут (минуты 7, 22, 37,
52) с промптом `/devcycle tick`, записывает `cronId` в состояние и пишет строку в лог. С этого
момента каждый тик читает `tick.md` и делает ровно одно действие.

### Возобновление

`/devcycle resume` читает состояние и список расписаний. Если `enabled=true`, а расписания нет,
оно создаётся заново. Если `enabled=false`, команда не запускает цикл молча, а спрашивает
владельца.

### Остановка

`/devcycle stop` удаляет расписание, вызывает `state disable --reason "<причина>"` и печатает
отчёт. После остановки состояние остаётся на диске: следующий `resume` увидит, что цикл был
выключен, и спросит владельца.

### Проверка

`/devcycle status`, `/devcycle report` и `node scripts/devcycle.mjs status --json` показывают
одно и то же состояние без побочных эффектов. Для ручной проверки достаточно `status`: если
секция GitHub показывает зелёный CI по `headRefOid` и `mergeStateStatus=CLEAN`, PR готова к
merge, а если секция OpenCode показывает `idle`, исполнитель закончил и ждёт проверки.

### Расписание живёт не вечно

Расписание Claude Code существует только пока открыта сессия и истекает через 7 дней. За сутки
до истечения контролёр предупреждает владельца. После перезапуска сессии расписание не
восстанавливается само: нужен `/devcycle resume`. Это ограничение инструмента, а не цикла, и
его нельзя обойти настройкой.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `DEVCYCLE_REPO` | текущий каталог | Корень git-репозитория |
| `DEVCYCLE_BACKLOG` | `BACKLOG.md` | Файл очереди, абсолютный или относительно репозитория |
| `DEVCYCLE_STATE_DIR` | `.devcycle/` | Каталог локального состояния и лога |
| `DEVCYCLE_REGISTRY` | `.loopx/registry.json` | Реестр LoopX для квоты и очереди цели |
| `DEVCYCLE_GOAL_ID` | `mcp-task-knowledge-goal` | Идентификатор цели LoopX |
| `DEVCYCLE_AGENT_ID` | `claude-controller` | Agent-id контролёра в LoopX |
| `DEVCYCLE_DB` | `$HOME/.local/share/opencode/opencode.db` | База OpenCode для пульса сессий, только чтение |
| `OC_BRIDGE` | `$HOME/.claude/skills/opencode-bridge/scripts/oc_bridge.py` | Скрипт моста доставки поручений |

Переменные задаются в окружении контролёра. В документации и конфигах не должно быть личных
абсолютных путей: всё, что зависит от машины, выводится из этих переменных.

## Связь с `.loopx-watchdog/loopx-watchdog.sh`

Watchdog и devcycle решают разные задачи и не заменяют друг друга.

Watchdog это фоновый демон: раз в интервал он синхронизирует `pending` из `BACKLOG.md` в todo
LoopX и пинает текущую сессию OpenCode через `tmux send-keys`. Он не смотрит CI, не читает PR,
не проверяет ветки и ничего не мержит.

Devcycle это команда контролёра: она проверяет GitHub и git, принимает решения по очереди,
диспетчит поручения через мост, проверяет результат по первоисточникам и доводит PR до merge.
Она не держит демон и не пишет в tmux.

Оба инструмента могут работать одновременно. Синхронизацию бэклога в LoopX devcycle берёт по
смыслу, но не копирует слепо: `blocked`, `deferred` и гейты владельца пропускаются, а не
добавляются в очередь.

## Режим без открытой сессии (не реализуется сейчас)

Сейчас цикл требует открытой сессии Claude Code: расписание и слэш-команда живут внутри неё.
Гипотетический следующий шаг это запуск `claude -p "/devcycle tick"` по таймеру systemd или
планировщику задач. Такой режим дал бы циклу независимость от открытого окна, но требует
отдельного разбора, поэтому сейчас не реализуется.

Что понадобится, если за это взяться:

- Права на `git fetch`, `git push`, `gh pr create`, `gh pr checks`, `gh pr merge`, `loopx` и
  отправку через `OC_BRIDGE`.
- Доступ на чтение к `DEVCYCLE_DB` и к реестру `DEVCYCLE_REGISTRY`.
- Файловый lock на время тика, бюджет на число тиков и отдельный kill switch.
- Хранение токенов в окружении юнита или в защищённом хранилище, а не в файлах репозитория.
- Ротация лога и уведомление владельца при красном master.

Риски: merge в master без человека, истёкшие или отозванные токены, двойной запуск при
неаккуратном таймере, накопление секретов в логе юнита, отсутствие гейта для решений, которые
принадлежат владельцу. Без lock, бюджета и kill switch такой режим включать нельзя.

## Ограничения

- Очередь считается по `BACKLOG.md` на `origin/master`. Очередь LoopX может отставать от git и
  служит подсказкой, а не источником.
- `next` не знает про смысл пункта. Если пункту нужна проработка, это решает контролёр по
  критериям из `tick.md`, а не эвристика скрипта.
- `status` не заменяет проверку результата. Перед merge контролёр смотрит CI по конкретному
  sha, `git status`, `MERGE_HEAD` и расхождение с `origin/master`.
- Журнал решений это история, а не план. Актуальная очередь всегда в `BACKLOG.md`.
