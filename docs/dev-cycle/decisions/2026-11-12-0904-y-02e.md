# 2026-11-12 09:04 — Y-02e: profile factory outside registrators

## Вопрос

Guard `tests/storage-wiring.test.ts` разрешал `setup.ts` импортировать профили и исключал его из
проверки, хотя DoD Y-02e требует: в `src/register/**` нет импортов `src/storage/*`. `setup.ts`
импортировал `createFileProfile`/`createSqliteProfile`/`createPostgresProfile`/`readStorageProfileKind`
и `StoreError`, то есть буквально нарушал контракт.

## Решение

- Новый композиционный корень `src/core/profile-factory.ts`: `createStorageProfile(options)`
  выбирает file/sqlite/postgres, обрабатывает `CONFIG_MISMATCH` и реэкспортирует `StorageProfile`.
- `src/register/setup.ts` больше не импортирует `src/storage/**`; вызывает фабрику и передаёт
  `dataDir`, `embeddingProvider`, `externalPolicy`, `POSTGRES_URL`, `STORAGE_BLOBS_DIR`.
- `src/core/storage-context.ts` реэкспортирует `DEFAULT_CLAIM_TTL_SEC`/`MAX_*`/`ClaimActor`;
  `src/register/tasks.ts` берёт их оттуда вместо `storage/contracts.js`.
- `src/register/context.ts` типизирует `storage` через `core/profile-factory.js`.

## Почему

- Композиция — ответственность `src/core`, а не регистратора инструментов; guard становится
  честным, без исключения `setup.ts`.
- Поведение выбора профиля и ошибок не меняется, wire-формат не затрагивается.
- Константы claim — часть контракта, но регистратор получает их через core-реэкспорт.

## Ограничения

- `setup.ts` по-прежнему сам создаёт auth.db и вызывает фабрику — это composition root, не
  регистратор.
- `src/core/profile-factory.ts` импортирует storage-модули; это разрешено (вне `src/register`).
- `storage-profile` тесты проверяют file profile; sqlite/postgres factory path не запускался.

## Откат

Вернуть импорты профилей/StoreError в `setup.ts`, удалить `core/profile-factory.ts`, вернуть
`tasks.ts` на `storage/contracts.js`; остальные регистраторы не менялись.
