## Вопрос

Как определить, что проект можно читать из индекса, если на живом ядре индекс создан, но пуст
(строки появляются только на мутациях, `rebuild` — после файловых миграций, `reindex` — SC-02d),
и как проект становится полным, не блокируя старт и не делая O(N) на каждом чтении.

## Решение

1. **Критерий полноты — инвариант счётчиков, а не сверка с каталогом.**
   `isProjectComplete(project)` истинно, когда одновременно: в `projects` есть строка проекта
   (`synced_at` заполнен завершённым наполнением), `meta.dirty = 0`, и
   `COUNT(tasks WHERE project) + COUNT(docs WHERE project)` равно `projects.file_count`,
   записанному в том же наполнении. Сверка «число строк == число файлов» отвергнута: число
   файлов требует `readdir`+`stat` по проекту на **каждом** чтении (100k — 1.1 с), то есть
   ровно та O(N), которую убирает SC-02. Счётчик строк читается по индексу (index-only scan
   префикса `project`) и кешируется в процессе до первой мутации.
   Следствие, зафиксированное честно: **файл, добавленный в обход сервера, этим гейтом не
   виден** (он не в индексе). Это зона `doctor`/`reindex --verify` (SC-02d). Правка и удаление
   существующего файла лечатся на странице (п. 5).

2. **`meta.dirty` входит в гейт** (прямое требование пункта). Цена: после неудачной записи в
   индекс проект читается файловым путём до `rebuild()`/`reindex`, который сбрасывает `dirty`.
   До SC-02d восстановление доступно только через существующий `rebuild()` (после файловых
   миграций / вручную). Это осознанная деградация «медленно, но верно» вместо чтения из
   заведомо неполного индекса.

3. **Наполнение — по проекту, при первом обращении, в фоне.** `ensureProjectIndexed(project,
   dirs)` при неполном проекте запускает `fillProject`: удаляет строки проекта, сканирует
   только каталоги этого проекта пачками по 2000, пишет строку `projects` с `file_count` и
   `synced_at`. Запрос **не ждёт** наполнения — текущее чтение идёт файловым путём. Один
   промис на проект на процесс (дедуп), форма взята у `src/search/warmup.ts`. Отвергнуто:
   глобальный `rebuild()` на первом чтении (O(все проекты)) и явный `rebuild` после старта
   (планировщик, стоимость на boot, всё ещё O(N) целиком). Каталоги резолвятся той же схемой
   «modern → legacy flat», что в storage; при legacy flat только запрошенный проект помечается
   полным, остальные строки получают строки без `projects`-записи и остаются на файловом пути.

4. **Схема v2.** Добавлены частичные индексы
   `idx_{tasks,docs}_active_page ... WHERE archived = 0 AND trashed = 0` для страницы и
   `countOnly` по умолчанию. `METADATA_INDEX_SCHEMA_VERSION` поднят до 2: существующий v1
   пересоздаётся пустым (производный кеш), чтения уходят на файловый путь, наполнение —
   фоновое. Частичный индекс SQLite индексирует подмножество **строк таблицы**, сами строки
   хранят архив и корзину, поэтому эквивалентность страниц не страдает.

5. **Самолечение — по строкам страницы.** Для каждой выбранной строки читается файл и
   сравнивается `mtime`; расхождение даёт upsert строки и, если файл больше не проходит
   фильтры, строка исключается из страницы (`total` уменьшается на число исключённых).
   Исчезнувший файл даёт удаление строки и `recountProject` — иначе счётчик разошёлся бы
   навсегда и проект навсегда ушёл бы на файловый путь. Внешняя правка **фильтруемого** поля
   (например `status`) не видна первому фильтрованному чтению: индекс её не выберет; она
   лечится на первом чтении, где строка попала на страницу. Это граница возможностей без
   O(N) и она же — аргумент за `reindex` в SC-02d.

6. **`total` точный** (как записано 14:37): файловый быстрый путь отдаёт число файлов проекта
   с `totalExact: false`, индексный — точный отфильтрованный `total` с `totalExact: true`.
   Намеренное изменение контракта, закреплено `tests/scale-index.test.ts`.

7. **`count`/`verify` остаются в SC-02d** — SC-02c их не вводит; гейт использует собственные
   два `COUNT(*)` по индексу, а не публичный метод.

8. **Наблюдаемость выбора пути для тестов.** `noteIndexPageRead`/`noteFilePageRead` и
   `getIndexReadStats()` — внутренние счётчики модуля, не поле MCP-ответа и не изменение
   контракта инструментов. Без них revert-check «выбран индексный путь» был бы вакуумным:
   результат страницы одинаков у обоих путей по определению эквивалентности.

## Почему

- Критерий на счётчиках — единственный, который одновременно доказывает «нет пропущенных строк»
  (иначе проект не полный) и не требует O(N) на чтении. Проверка «число строк == число файлов»
  ложно-отрицательна по стоимости, а не по смыслу.
- Наполнение по проекту не блокирует ни старт, ни запрос и ограничено по памяти (пачки 2000):
  на 100k в одном проекте наполнение — это те же 15–30 с фоновой работы, что у `rebuild`, но
  без затрагивания чужих проектов.
- `dirty` в гейте — требование пункта; цена описана выше и приемлема, потому что индекс
  производный: файловый путь остаётся корректным.
- Схема v2 с частичными индексами даёт `countOnly` по умолчанию без чтения строк; проверка
  `EXPLAIN QUERY PLAN` в тесте (`idx_tasks_active_page`/`idx_docs_active_page`, без `SCAN`)
  доказывает, что индекс не «декоративный».

## Дополнение: `file_count` поддерживается инкрементально (найдено владельцем)

**Пробел.** `projects.file_count` обновлялся только в `fillProject` и `recountProject`. Обычная
запись (create/update/delete) меняла число строк, но не счётчик, поэтому после первого же
`tasks_create` инвариант `rows == file_count` ломался: `isProjectComplete` возвращал `false`,
чтения уходили на файловый путь, а следующее чтение запускало **полное** фоновое наполнение
проекта заново (`synced_at` менялся, `file_count` подтягивался). На 100k при постоянных
изменениях индекс практически не использовался. Тесты и замер этого не ловили, потому что
шли без записей после наполнения.

**Исправление.** Счётчик двигается в той же транзакции, что и строки: `upsertTask`/`upsertDoc`
читают существующую строку проекта до записи и делают `+1` только при вставке новой строки
(при смене проекта — `−1` старому и `+1` новому), обновление существующей строки не меняет
счётчик; `deleteTask`/`deleteDoc` делают `−1` только если строка существовала. Операция —
`UPDATE projects SET file_count = MAX(0, file_count + ?) WHERE project = ?`; для нетрекнутого
проекта она не находит строку, и проект остаётся неполным (файловый путь), как и раньше.
`fillProject` и `recountProject` пишут счётчик явно и через `bump` не проходят, поэтому
двойного счёта нет. Защита от внешних изменений сохранена: файл, добавленный в обход сервера,
гейтом по-прежнему не виден — это зона SC-02d.

**Проверено.** Тест «keeps the project complete after create, update and delete of tasks and
documents» сначала RED на ветке без исправления (`expected 2 to be 4` для `file_count` после
create), после исправления GREEN: после create/update/delete задач и документов проект полный,
`file_count` = 2 → 4 → 4 → 2, следующее чтение идёт из индекса (`indexReads: 2`,
`filesReads: 0`), `synced_at` не меняется, состояние `complete`. Revert-check: убрать `+1` при
вставке → RED (`expected 3 to be 4`), убрать `−1` при удалении → RED (`expected 3 to be 2`),
после отката GREEN.

**Замер на 100k с записями.** 50 циклов create/update/delete для задач и 50 для документов
(300 операций, 225 мс): `file_count` 200 000 → 200 000, строк 200 000, проект полный,
различных значений `synced_at` за все циклы — 1 (наполнение не перезапускалось). Сразу после
записей `scripts/bench/run-scale.mjs --only tasks_list,knowledge_list --reps 3`:
`tasks_list` 15 мс, `knowledge_list` 17 мс (до записей 16/21 мс), ответы 32 365 / 22 156 байт.
