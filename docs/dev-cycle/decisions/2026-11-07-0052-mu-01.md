# 2026-11-07 00:52, MU-01: единственный процесс-владелец DATA_DIR

Вопрос: два сервера на одном `DATA_DIR` теряют чужие записи (`withFileLock` работает только внутри
процесса). Как запретить второго писателя так, чтобы отказ был понятным, `kill -9` не блокировал
каталог навсегда, а чужой хост в сетевой ФС не терял данные?

Решение: `src/storage-lock.ts` держит `DATA_DIR/.server.lock` (pid, hostname, identity процесса,
startedAt, transport, version, token). Захват атомарный: tmp-файл + `fs.link(tmp, lock)`, то есть
файл появляется уже с содержимым; на ФС без hardlink — fallback `wx`. Владение проверяется по
token, поэтому и асинхронный release, и синхронный релиз на выходе процесса удаляют файл только со
своим token. Захват — в `AppContainer.init()` до schema-gate, потому что миграция тоже пишет.
Второй процесс получает `SERVER_LOCK_HELD` (pid, hostname, startedAt, путь, что делать) и exit 1.
Протухший lock на Linux снимается автоматически с warn: pid мёртв или переиспользован
(starttime+btime из `/proc`); снятие сериализовано guard-файлом и внутри перепроверяет
классификацию. Чужой hostname не снимается (`SERVER_LOCK_FOREIGN_HOST`). Вне Linux identity
процесса недоступна, поэтому протухший lock автоматически не снимается
(`SERVER_LOCK_UNVERIFIABLE`) — решение владельца, чтобы не удалить lock живого процесса с
переиспользованным pid. Release: cleanup в `stop()`, `process.on('exit')`, а для stdio
(`handleSignals=false`) — собственные SIGINT/SIGTERM с переотправкой сигнала. Пропуск захвата:
proxy-режим (`--proxy-upstream` / `MCP_PROXY_UPSTREAM`, задел MU-08) и `doctor`, который выходит до
создания контейнера.

Почему: token вместо pid — файл мог быть пересоздан после снятия; `link` вместо exists+write —
иначе одновременные старты дают нескольких «победителей»; lock до schema-gate — иначе миграция идёт
без эксклюзивности; чужой hostname и отсутствие `/proc` — liveness доказать нельзя, автоудаление
рискует живыми данными; identity по starttime+btime, потому что pid переиспользуется; `writeSync(2, …)`
для сообщения об отказе — stderr в пайп асинхронный, и `process.exit` сразу после `write` обрезал
единственное объяснение (нашёл тест кейса a).

Проверено: проба до кода — два stdio-процесса на одном `DATA_DIR`, 60 раундов параллельного
`tasks_update` одной задачи: 56/60 потерянных обновлений (49/60 в первом прогоне). После — второй
процесс не стартует (exit 1, `SERVER_LOCK_HELD`), потерь 0. `tests/server-lock.test.ts`, 23 теста
(кейсы a-i плюс unit-блок): a) второй процесс, b) 20 одновременных захватов через барьер — ровно один
победитель, c) `kill -9` → следующий старт снимает протухший lock, d) переиспользование pid и отказ
вне Linux, e) SIGTERM снимает lock, f) чужой hostname, g) проба без потерь, h) uncaughtException
освобождает lock, i) синхронный релиз на выходе не удаляет lock, перехваченный преемником (другой
token). Revert-check точечными мутантами: без захвата в boot красные a, c, e, g; без проверки
identity — d; чужой hostname как stale — f; без reclaim — c, d; без release на сигнал — e;
exists+write вместо link — b (пять победителей вместо одного); снятие token-проверки в
`removeIfOwnedSync` — i. Гейты (build, test:types, lint, lint:md, backlog:check, полный тест) — в
отчёте сессии. Вне Linux и на сетевых ФС поведение не проверялось: `/proc` там нет, автоснятия нет
по решению выше.

Откат: revert коммита фикса (модуль, boot-правки, тесты, доки, строка BACKLOG, эта запись). Файл
`DATA_DIR/.server.lock` после отката кодом не читается и остаётся мусором — удалить вручную.
