## Вопрос

Контракт `SearchProvider` синхронный, а драйвер Postgres — асинхронный. Как дать настоящий поиск
(`tsvector` + `pg_trgm`) инструментам, не ломая существующие профили и не подменяя результат заглушкой?

## Решение

1. **Аддитивное расширение контракта:** `SearchProvider.candidatesAsync?(input)` — необязательный
   async-метод. Регистраторы (`register/search.ts`) через helper `candidateHits` вызывают его, когда
   он есть, иначе остаются на синхронном `candidates` (файловый и SQLite профили не меняются).
2. **Настоящий SQL-поиск:** `candidatesAsync` выполняет запрос по `search_index` с generated
   `tsvector` (GIN) и `plainto_tsquery('simple')`; при доступном `pg_trgm` добавляется fallback
   `similarity(title || ' ' || body, $1) > 0.15`, а score = `ts_rank + 0.5 * similarity`. `fullText`
   в манифесте теперь `true`.
3. **Синхронные части** (`available/isIndexComplete/fillState/dirty/ensureIndexed/countTasks`)
   обслуживаются in-process состоянием `searchStates`/`taskCounts`, которое заполняется
   `ensureIndexed` (async-перестройка с записью `search_state`) и мутациями
   (`writeTask`/`writeDoc`/`deletePermanent` — fire-and-forget, ошибка помечает проект dirty, а не
   валит мутацию). Синхронный `candidates()` для Postgres честно возвращает `[]`: реальный путь —
   `candidatesAsync`, и это записано в комментарии у метода.
4. **Индекс ведётся на мутациях:** create/update/lifecycle/delete обновляют/удаляют строку
   `search_index`; `ensureIndexed` пересобирает проект целиком (удаляет старые строки, вставляет
   только живые, сбрасывает счётчик задач); ошибка записи индекса делает проект dirty.

## Почему

- Менять весь контракт на async — большой рефакторинг файлового и SQLite профилей; необязательный
  метод даёт настоящий поиск там, где драйвер асинхронный, и ноль изменений для остальных.
- Синхронный `candidates()` не может ждать SQL; возвращать пустой список честнее, чем имитировать
  поиск или тащить кэш, который устаревает между запросами.

## Проверено

- `tests/storage-postgres.test.ts` — **16/16 против реального PostgreSQL 18.6** (запуск с
  `POSTGRES_URL`): перестройка индекса и `candidatesAsync` по задачам/документам, изоляция проектов,
  store/kind, положительные score, `taskStoreId/docStoreId`, идемпотентная переиндексация,
  `countTasks`, `fillState`; **pg_trgm fallback** на near-miss запросе (`postgre` → `postgres`);
  обслуживание индекса на create/update/delete; честное `idle` для неперестроенного проекта.
- Затронутые наборы: `storage-postgres` 16, `storage-sqlite` 33, `storage-wiring` 3,
  `storage-contract` 31, `search-fts`, `search-tasks-warmup` — **126/126**; `tsc` test-проекта
  чистый, build зелёный.
- Revert-check: **6 мутаций RED** — candidatesAsync без фильтра проекта, отключённый pg_trgm
  fallback, ensureIndexed ничего не делает, мутация не обновляет индекс, ложный `fullText=false`,
  delete не убирает строку индекса.

## Откат

Revert ветки: убирается необязательный `candidatesAsync` из контракта, helper в `register/search.ts`,
Postgres-реализация поиска (SQL, состояние, hooks) возвращается к честной заглушке
`fullText=false`, `search_index`-таблица остаётся неиспользуемой. Файловый и SQLite профили,
инструменты и wire-формат не затрагиваются.
