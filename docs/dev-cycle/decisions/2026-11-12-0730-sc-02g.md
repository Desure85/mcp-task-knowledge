## Вопрос

После SC-06 файлы задач/документов могут лежать в корне (`tasks/<project>/<id>.json`) или в
шардах (`tasks/<xx>/<id>.json`). Нужно проверить, что индекс читает оба layout'а и что rebuild
не теряет строки при переезде.

## Решение

- `tests/metadata-index.test.ts`: добавлен SC-02g сценарий:
  1) задача в `tasks/alpha/t-1.json` + flat `tasks/t-2.json` → rebuild видит обе;
  2) `t-1` переезжает в `tasks/al/t-1.json` → rebuild обновляет `rel_path`, не дублирует id.
- Продовый код не менялся: `scanTaskRows` уже читает и корневые файлы, и один уровень
  shard-каталогов; `upsert` по id заменяет `rel_path`. Тест фиксирует это поведение.

## Почему

- SC-06 добавил шардирование после SC-02; нужен явный контракт, что индекс не привязан к одному
  layout'у.
- Переезд с обновлением `rel_path` — это и есть «перестройка при смене layout» без отдельного
  флага: источник истины — файлы, rebuild идемпотентен.

- **Мутация RED:** `scanTaskRows` игнорирует каталоги → SC-02g падает; восстановление 16/16,
  build чистый.
- `npm run test:types` — чисто.
- backlog:check — SC-02g не входит в «Итого» (подпункт); см. заметку.

## Ограничения

- Проверены задачи; документы в шардах не переезжали (SC-06 использует тот же scan-подход).
- Один shard-каталог (первый уровень); более глубокая вложенность не поддерживается.
- Индекс не отслеживает layout-маркер: rebuild нужен явно (`reindex`/старт), автоматического
  триггера при переезде нет.
- Windows `rel_path` содержит `\`; тест нормализует для сравнения, продовый формат не менялся.
