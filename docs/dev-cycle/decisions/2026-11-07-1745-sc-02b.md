## Вопрос

Какие отклонения от записи 2026-11-07 14:37 допущены при реализации записи и почему.

## Решение

1. **Интерфейс `MetadataIndex` расширен двумя методами и одним свойством** сверх перечисленных в
   §«Профили хранилищ»: `markDirty(reason?)` (`meta.dirty` при ошибке индекса — требование DoD),
   `deleteProject(project)` (`project_delete` не должен читать строки, чтобы их удалить) и
   `readonly dataDir` (`rel_path` строится от DATA_DIR, не от `process.cwd()`). Ничего из
   перечисленного не меняет контракт файлового профиля.
2. **`rebuild` живёт в `metadata-index.ts` и сам сканирует файлы** (`tasksDir`/`knowledgeDir`
   передаются вызывающим, чтобы учитывать `MCP_TASK_DIR`/`MCP_KNOWLEDGE_DIR` и legacy-раскладку).
   Отдельный модуль не вводился: список разрешённых файлов SC-02b закрыт, а импорт `tasks.ts` из
   `metadata-index.ts` дал бы цикл (хуки уже импортируют индекс).
3. **`matter(raw, {})` в rebuild вместо `matter(raw)`.** `gray-matter@4.0.3` кеширует каждый
   разобранный документ в `matter.cache` по полному тексту и никогда не вытесняет его: на 100k
   документах (~650 MB текста) rebuild падал по OOM. Любой объект опций отключает этот кеш;
   поведение разбора не меняется.
4. **Удаление идемпотентно и при отсутствующем файле:** `deleteTaskPermanent`/`deleteDocPermanent`
   удаляют строку индекса и тогда, когда файла нет (лечит сироту), результат функции не меняется.
5. **`count`/`verify` не реализованы:** это SC-02d, где появляются `doctor` и `reindex --verify`.

## Почему

- Без `markDirty`/`deleteProject` DoD SC-02b невыполним: «ошибка индекса не валит мутацию и ставит
  `dirty`» и «`project_delete` убирает строки проекта» — прямые требования пункта.
- Кеш `gray-matter` — не ошибка реализации, а свойство зависимости, обнаруженное замером; лечится
  вызовом без опций, без форка и без новой зависимости.
- Порядок «файл → `stat` → upsert» и «ошибка индекса не валит мутацию» соблюдены ровно как в записи
  14:37: файл уже записан и является истиной.

## Проверено

- `npm test -- tests/metadata-index-write.test.ts` — 13 тестов: совпадение строки с файлом после
  каждой мутации, claim/renew/release меняют только `mtime`, дедуп удаления, `project_delete`,
  ошибка индекса (throw + закрытая БД) не валит мутацию и ставит `dirty`, rebuild из файлов
  воспроизводит набор строк пачками по 2, `STORAGE_INDEX=off` не трогает индекс.
- Revert-check: 11 мутаций (10 точек записи + «ошибка индекса пробрасывается») — каждая даёт RED
  по ассерту, после отката GREEN; журнал в отчёте исполнителя.
- Замер rebuild на 100k задач + 100k документов (`scripts/bench/seed-scale.mjs --n 100000 --seed 7`):
  33.6 с, БД 131 MB, live heap 25–41 MB, пик RSS 302 MB при настройках Node по умолчанию и 176 MB
  при `--max-old-space-size=160`. DoD SC-02b — «≤ 250 MB RSS (`node --expose-gc` проба)»: проба с
  ограниченной кучей укладывается, дефолтный прогон — нет (пик задаёт ленивый GC V8, а не
  удержанные строки).
