## Вопрос

`search_tasks`/`search_knowledge` токенизируют весь корпус на каждый запрос: на 100k документов
это 23.6 с и 4.1 GB RSS. Нужен инвертированный индекс (FTS5) в той же SQLite-базе, но так, чтобы
качество не просело: baseline hit@1 = 88.9% (MRR 0.926) на `scripts/kb-bench-queries.json`.

Один PR на всё — снова смешение: хранилище, запись в него при мутациях задач/документов, и
переключение read-пути с бенчмарком. Плюс главный риск (падение качества) проверяется только на
переключённом read-пути.

## Решение

1. **Разбить на три инкремента**, каждый со своим PR:
   - **SC-03a** — хранилище: таблица FTS5, upsert/remove/rebuild, ranked query с фильтрами,
     версия схемы (этот PR);
   - **SC-03b** — запись: хуки мутаций задач/документов держат индекс в актуальном состоянии,
     `doctor`/`reindex` знают про индекс, полнота по проекту;
   - **SC-03c** — чтение: `search_tasks`/`search_knowledge` читают индекс с откатом на in-memory
     BM25, проверка hit@1 ≥ 0.889 и `medianMs < 1000` на 100k, документация.
2. **Индексируются наши токены, а не сырой текст.** FTS5-токенизатор `unicode61` не разбивает
   `getUserProfile` и не знает наш список стоп-слов; индекс хранит результат `tokenize()` из
   `src/search/bm25.ts` (который для этого экспортирован). Иначе recall поедет молча.
3. **Запрос — те же токены + префиксное раскрытие.** Термы длиной ≥ 3 символов расширяются в
   `term*`: in-memory BM25 находил `authentication` по `auth` за счёт своей токенизации, и индекс
   обязан сохранить это поведение (иначе просядет recall на коротких запросах).
4. **`id`/`kind`/`project`/`updated_at` — `UNINDEXED`-колонки**: по ним фильтры (`kind`, `project`)
   и join к хранилищу, ранжирование — `bm25()`.
5. **Версия схемы в `search_meta`.** Несовпадение версии означает изменённую раскладку термов:
   таблица пересоздаётся, вызывающий обязан переиндексировать (`stats()` это покажет). Молча
   отдавать устаревшие термы нельзя.
6. **Хранилище не знает про `DATA_DIR`.** `FtsSearchIndex.open(file)` / `.inMemory()` — базу
   выбирает вызывающий (в SC-03b это будет `.index/metadata.db`, «в той же базе» из DoD).

## Почему

- Разбиение проверяемо: качество (hit@1) и скорость проверяются только после SC-03c, и до этого
  хранилище можно оттестировать изолированно (16 тестов, включая паритет токенизации).
- Индексирование наших термов превращает «FTS5 вместо BM25» из изменения поведения в изменение
  скорости — это и есть требование пункта.

## Проверено
