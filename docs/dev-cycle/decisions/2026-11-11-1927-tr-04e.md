## Вопрос

Аудит TR-04 подтвердил пять тестов, которые остаются зелёными при сломанном предмете:

| # | Файл | Мутация |
|---|---|---|
| K10b | `tests/app-container.test.ts` | ошибка `adapter.close()` в `stop()` стала фатальной |
| K12 | `tests/jwt-validator.test.ts` | `jwksCacheTtl` default 300000 → 0 |
| K13 | `tests/bm25.unit.test.ts` | `k1` default 1.5 → 0.1 |
| K14 | `tests/ab.bandits.test.ts` | ветка исследования `Math.random() < eps` отключена |
| K16 | `tests/embeddings.cache.test.ts` | вытесняется самый новый элемент вместо LRU |

## Решение (только тесты, production не менялся)

- **K10b:** новый тест подаёт адаптер с `close()` → reject, требует `stop()` resolved, `state === 'stopped'`,
  `close` вызван один раз и лог `transport close error (non-fatal)` с ошибкой.
- **K12:** проверяются фактические значения `jwksCacheTtl` (300000 по умолчанию, 1234 кастом),
  создание resolver, сброс после `invalidateCache()` (второй resolver не тот же объект) и безопасный
  `invalidateCache()` до создания resolver. Удалена `expect(true).toBe(true)`.
- **K13:** точные BM25-скоры для k1=0.1 и k1=5.0, проверка default-скора 0.314 и его отличия от k1=0.1;
  для b проверяется, что длинный документ при b=1 получает меньше, чем при b=0 (0.443 vs 0.449).
- **K14:** `Math.random` замокан: первый вызов 0.05 (< epsilon 0.1), второй 0.9 → выбирается `C`;
  проверено два вызова RNG, восстановление в `finally`.
- **K16:** persistence выключен, 4096-dim векторы (16 KiB) и 540 вставок при 8 MiB floor вызывают
  детерминированное вытеснение; `id0` трогается и обязана выжить, `id1` — LRU-жертва (undefined),
  `id539` — новая (defined). Старое «5000 вставок, проверить только newest» удалено.

## Почему

- Каждый тест теперь наблюдает именно ту ветку/параметр, который ломает мутация, а не конверт/длину массива.
- LRU проверяется на трёх разных позициях (touched, oldest, newest), поэтому подмена eviction на «новый»
  ловится.
- Нет production-изменений: пункт про качество тестов, wire-формат не затрагивается.
