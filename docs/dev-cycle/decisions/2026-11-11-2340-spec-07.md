# 2026-11-11 23:40 — SPEC-07: progressToken gating

- **Пункт:** SPEC-07 (low)

## Вопрос

`createProgressSender` слал `notifications/progress` без `progressToken` и без проверки, что клиент
вообще запросил прогресс. По MCP-спеке уведомление допустимо только при наличии `progressToken`
в `_meta` запроса; без него клиент не может сопоставить обновление с вызовом.

## Решение

- `progressTokenFromExtra(extra)`: достаёт `_meta.progressToken`, принимает только `string | number`.
- `createProgressSender(ctx, progressToken?)`:
  - без токена возвращает no-op — ни одного `sendNotification`;
  - с токеном включает `progressToken` в params уведомления.
- `withProgress` не менялся и работает с обоими режимами.
- Тесты обновлены: отсутствие токена → ноль уведомлений; токен → params с `progressToken`;
  transport error/missing sender по-прежнему non-fatal.

## Почему

- Gating на границе utility — единственное место, где можно гарантировать спеку независимо от
  транспорта (stdio/SSE).
- `progressToken` обязателен в params, иначе клиент не коррелирует уведомление.
- no-op sender намеренно не бросает: вызов `withProgress` не должен ломать инструмент, если
  клиент не запросил прогресс.

## Ограничения

- Production-вызовов `createProgressSender` сейчас нет: helper экспортирован, но ни один tool handler
  его не использует. Пункт закрыт на уровне контракта utility; фактических progress-уведомлений в
  инструментах пока нет.
- `progressTokenFromExtra` читает только `_meta.progressToken`; другие источники не поддерживаются.

## Откат

Убрать `progressToken` и gate, вернуть старые тесты; удалить `progressTokenFromExtra`.
