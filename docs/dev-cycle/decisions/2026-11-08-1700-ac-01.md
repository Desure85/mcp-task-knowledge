## Вопрос

AC-01 фиксирует два подтверждённых дефекта ядра: неизвестное имя параметра **молча
игнорируется** (`tasks_list({tags: [...]})` вернул все задачи вместо ошибки, потому что Zod
срезает лишние ключи до обработчика), и пустая строка пишется в данные (`tasks_bulk_create` с
`parentId: ""` создаёт задачу и сохраняет пустой `parentId`). Нужно было решить, где именно
перехватывать лишние параметры так, чтобы это работало для всех инструментов, не меняло
поведение валидных вызовов и не ломало опубликованный контракт.

## Решение

1. **Перехват — в единственном месте, центральный wrapper `registerTool` (`src/register/setup.ts`).**
   SDK валидирует аргументы через `safeParseAsync(z.object(shape))` и отдаёт обработчику уже
   очищенный объект, поэтому в обработчике лишних ключей уже нет. Wrapper передаёт SDK **рыхлую**
   схему (`z3.object(shape).passthrough()` или `z4.looseObject(shape)`) — лишние ключи доживают до
   обработчика, — а `guardUnknownParams` из `src/core/tool-arguments.ts` отвечает
   `{ ok:false, error:{ code:"UNKNOWN_PARAM", message, hint, details:{unknown, allowed, suggestion} } }`.
   Конверт — по конвенции `src/utils/respond.ts`; AC-01 записан как `{ok:false, code, hint}`, и
   `code`/`hint` лежат в `error`, как во всех остальных ошибках сервера.
2. **Гвард стоит внутри gate.** Порядок — `gateHandler(name, guard(handler))`: сначала auth/security
   (fail-closed), потом проверка аргументов; иначе неаутентифицированный вызов получал бы список
   имён аргументов раньше отказа в доступе.
3. **Подсказка — ближайшее имя (Левенштейн).** `tags` → `tag` — ровно случай из пункта. Порог:
   `max(1, len/2)`, чтобы для коротких имён подсказка была возможна, а для длинных не была шумом.
4. **Два вкуса Zod распознаются duck-typing.** 25 регистраторов объявляют схемы через `zod/v3`,
   2 — через `zod` (v4). Между ними не работает `instanceof`, и рыхлая схема обязана строиться тем
   же вкусом, что и оригинал (`_def` → v3 `passthrough`, `_zod` → v4 `looseObject`). Это не
   косметика: первая версия гварда не срабатывала вообще, потому что `instanceof z.ZodType` из
   `zod` (v4) для v3-схем ложно.
5. **Пустая строка = отсутствие поля, но `null` сохраняет смысл.** `src/utils/strings.ts::blankToUndefined`
   нормализует только `''`/`'   '`. Для документов `parentId: null` — документированный способ
   отцепить документ в корень (`tests/knowledge.detach_root.test.ts`), поэтому `null` не трогаем;
   первая версия нормализации ломала эти тесты и была откачена до сдачи.
6. **Контрактный тест — на все инструменты, не только на шесть `*_bulk_*`.** `tests/mcp-argument-contracts.test.ts`
   сверяет опубликованный `inputSchema.required` с Zod-опциональностью каждого зарегистрированного
   инструмента через живой сервер и in-memory транспорт, плюс прогоняет минимальные вызовы
   bulk-инструментов и оба дефекта из пункта.
7. **Побочный эффект опубликованной схемы принят и записан.** У инструментов на `zod/v3`
   `additionalProperties` в `tools/list` меняется с `false` на `true`: SDK публикует ту же схему,
   которой валидирует, а «рыхлость» — единственный способ увидеть лишний ключ в обработчике.
   `required`/`properties` не меняются, `docs/api-reference.md` после `npm run api:reference`
   не изменился. Альтернативы отвергнуты: строгая схема (`UNKNOWN_PARAM` невозможен — SDK бросает
   `InvalidParams` до обработчика, без кода и подсказки) и перехват на уровне транспорта
   (нужен свой пре-валидатор в каждом транспорте; оставлено как возможный следующий шаг, если
   `additionalProperties:true` окажется проблемой для клиентов).

## Почему

- Один wrapper вместо 138 мест регистрации: правка не размазывается по регистраторам и не
  забывается при добавлении нового инструмента.
- Валидный вызов не меняет поведение: известные ключи идут в инструмент как раньше, меняется только
  судьба неизвестных.
- `UNKNOWN_PARAM` с подсказкой — то, что реально нужно агенту: ошибка «неизвестный параметр `tags`»
  без «возможно, вы имели в виду `tag`» заставляет агента угадывать.

## Проверено

- `tests/mcp-argument-contracts.test.ts` — 7 тестов: сверка `required` со Zod-опциональностью по
  всем инструментам; минимальные вызовы `tasks_bulk_create/update`, `knowledge_bulk_create/update`,
  `tasks_bulk_archive/restore`; `tasks_list({tags})` → `UNKNOWN_PARAM` + подсказка `tag`;
  `tasks_list({tags, bogus})` → два неизвестных имени; `tasks_list({tag})` работает как раньше;
  `parentId: ""` не попадает в файл на create и снимает родителя на update.
- `npx tsc -p tsconfig.test.json --noEmit` — зелёный (тестовый проект; локальный `npm run build`
  его не проверяет).
- `tests/docs-tools-coverage.test.ts` (6), `tests/cli.tools_list.contract.test.ts` (6),
  `tests/pagination.unit.test.ts` (15) — зелёные.
- `tests/knowledge.detach_root.test.ts`, `tests/knowledge.bulk_update.detach.test.ts` — зелёные
  после того, как нормализация перестала трогать `null`.
- `npm run api:reference` — файл не изменился (130 инструментов, схемы в справочнике не печатаются).
- Полная сюита на Windows шумит (десятки падений и на master: stdio-spawn тесты таймаутят под
  параллельной нагрузкой, symlink/EPERM). Сравнение по именам тестов «ветка против master»
  показало, что единственная функциональная регрессия — тесты detach с `parentId: null` — устранена;
  остальные расхождения — таймауты одних и тех же spawn-тестов, меняющиеся от прогона к прогону.
  Гейт — Linux CI PR.
