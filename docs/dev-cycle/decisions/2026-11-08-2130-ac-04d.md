## Вопрос

1. Почему `tools_run{tasks_create, params:{project}}` без `title` создаёт задачу с
   `"title": null`, хотя прямой вызов того же инструмента отклоняется?
2. Почему `logs_tail` не маскирует Basic-авторизацию, `?token=`/`?password=`, `user:pass@host`,
   env-присваивания, `AKIA…`, PEM `PRIVATE KEY`, camelCase/дефисные ключи?

## Решение

1. **Вложенный вызов валидируется той же схемой, что и прямой.** SDK проверяет аргументы на
   транспорте, а `tools_run`/`tools_batch` вызывают `meta.handler(params)` напрямую — валидация
   не выполняется вовсе. `validateNestedParams` (`src/core/tool-arguments.ts`) читает raw shape
   из реестра (`readInputShape`) и разбирает `params` через `looseInputSchema` до вызова handler.
   **Почему loose, а не строгая схема:** строгая `z.object(shape)` вырезала бы неизвестные ключи
   до `guardUnknownParams`, и `UNKNOWN_PARAM` перестал бы приходить из вложенных вызовов —
   регресс AC-01. Loose сохраняет контракт: неизвестный ключ даёт `UNKNOWN_PARAM`, а missing
   required / тип / границы / enum — `VALIDATION_ERROR`.
2. **Отказ несёт машиночитаемые пути.** `errorEnvelope.details.issues` — массив
   `{ path, message, code }`, где `path` отрисован как `title` или `items[0].title`;
   `requestId` и запись в лог приходят от `innerFailure`, как у прочих ошибок AC-04a.
   `error` остаётся строкой — прежние клиенты не ломаются.
3. **Инструмент без raw shape не валидируется.** Для предсобранной схемы нечего проверять,
   а выдуманная схема отвергала бы валидные вызовы; такое поведение зафиксировано явно.
4. **Брошенная ошибка сохраняет конверт.** `catch` в `tools_run`/`tools_batch` передаёт объект
   ошибки в `innerFailure` целиком, поэтому `ToolError.code` больше не теряется (кандидат 5
   приёмочного списка; правка в том же `catch`, что и валидация).
5. **Маскирование: классы, а не отдельные литералы.** В `SECRET_PATTERNS` (`src/core/log-file.ts`)
   добавлены: Basic — **только** после поля `authorization`, чтобы не маскировать прозу
   «Basic authentication failed»; секретные query-параметры по точному списку имён;
   `user:pass@host` в строках подключения; env-присваивания по суффиксу
   (`…PASSWORD|…TOKEN|…SECRET|…API_KEY`); `AKIA…`; PEM-блок с обрезанным хвостом;
   заголовки `x-api-key:`; JSON-поля, **имя которых заканчивается** секретным словом —
   поэтому `clientSecret`, `authToken`, `x-api-key` закрыты, а `"tokenCount": 5` — нет.
6. **Негативные случаи закреплены тестом:** hex-хэш коммита, uuid, числовой `tokenCount`,
   проза про Basic, обычный URL с `limit/page`, блок CERTIFICATE, `user@host` без пароля.
7. **Границы `logs_tail` (фильтр по `requestId`, ротация, `project`) в этот PR не входят:**
   они не воспроизведены живой проверкой и записаны в AC-04e как кандидаты.

## Почему

- Валидация в одном месте (общий `validateNestedParams`) закрывает оба инструмента и не
  дублирует правила схем по регистрам.
- Отдельные маркеры (`[REDACTED_JWT]`, `[REDACTED_TOKEN]`, `[REDACTED_PRIVATE_KEY]`) сохраняются:
  generic-маска не съедает уже замаскированное значение.
- Якорение Basic на `authorization` и суффиксное правило для JSON-ключей выбраны из-за цены
  ложных срабатываний: маскирование обязано быть предсказуемым для оператора лога.
