## Вопрос

`register/search.ts` — последний регистратор с прямыми импортами хранилища, но его зависимости от
хранилища не коллекции, а индексный слой: `search/fts-indexer` (кандидаты, полнота, fill-состояние,
store id) и `storage/metadata-index` (счётчик задач для AC-05). Чтобы allowlist стал пустым без
временной прокладки, эти зависимости должны получить контракт.

## Решение

1. **`SearchProvider` в `src/storage/contracts.ts`** — ровно то, что нужно инструментам:
   `available()`, `dirty()`, `isIndexComplete(project)`, `fillState(project)`,
   `ensureIndexed(project)`, `candidates({store, kind, project, query, limit})`,
   `taskStoreId()`, `docStoreId()`, `countTasks(project)`. `StorageProfile.search` публикует его.
2. **Файловый профиль делегирует текущим модулям** (`FileSearchProvider`): FTS-кандидаты, полнота,
   fill-состояние и store id — из `fts-indexer`, счётчик задач — из metadata-индекса. Логика не
   переписана, поэтому ответы `search_tasks`/`search_knowledge` не меняются.
3. **`register/search.ts` переведён на профиль:** коллекции — `storageProfile(ctx).tasks/docs`,
   индекс — `storageProfile(ctx).search`; модульные helper'ы (`ftsTaskCandidates`,
   `ftsDocCandidates`, `scanDeferral`, `candidateMeta`, `projectTaskCount`) принимают `ctx`. Ни
   одного прямого импорта `storage/*`, `prompts/files`, `search/fts-index*` в `src/register/**`
   больше нет — **allowlist guard-теста пуст**.
4. **Y-02 закрыт:** a/b/c/d/e1/e2/e3/e4 выполнены; контрактные тесты (34 в файле) и guard-тест
   зелёные, файловый профиль остаётся поведением по умолчанию, регистраторы получают хранилище и
   индекс только из контекста.

## Почему

- `SearchProvider` — это именно тот интерфейс из ADR-009, который в Y-05/Y-06 реализуют SQLite и
  Postgres профили; вводить его здесь было обязательно, а не «для нуля в allowlist».
- Пустой allowlist теперь означает реальную инварианту: любой новый прямой импорт ломает guard-тест.
