## Вопрос

В SC-03a идентичность записи была `(kind, id)`, а фильтр — `project`. В проекте при этом
**несколько хранилищ**:

- корень `DATA_DIR`, но `TASKS_DIR`/`KNOWLEDGE_DIR` переопределяются через `MCP_TASK_DIR` /
  `MCP_KNOWLEDGE_DIR` (любой путь, в том числе на другом томе), плюс учитывается legacy-раскладка
  `DATA_DIR/mcp/{tasks,knowledge}` (`pickDir` в `src/config.ts`);
- legacy-задачи получают id из имени файла (`tasks.ts`: `f.slice(0, -'.json'.length)`), то есть
  `123`/`TASK-1`, которые могут совпасть в другом хранилище;
- имена проектов локальны для хранилища, поэтому `project` не может их различить.

Следствие: две записи из разных хранилищ с одинаковыми `kind`/`id` затирали друг друга, а
`query({project})` смешивал выдачу.

## Решение

1. **Ключ записи — `(store, kind, id)`.** `store` — канонический идентификатор корня хранилища:
   `resolveStoreId(root)` = `path.resolve`, без хвостового разделителя, в нижнем регистре на
   Windows (ФС регистронезависима, `C:\Tasks` и `c:/tasks` — одно хранилище). Абсолютный путь, а
   не хеш: его видно в `stores()`/`doctor`, и он остаётся осмысленным при отладке.
2. **`store` — обязательное поле записи и параметр запроса.** Без `store` запрос охватывает все
   хранилища файла индекса; это оставлено осознанно для инструментов аудита, но обычный путь
   (SC-03b/SC-03c) передаёт его всегда.
3. **`remove(store, kind, id)` и `clearStore(store)`**: удаление одной записи и очистка целого
   хранилища (переиндексация одного тома, удаление проекта).
4. **`stats(store?)` и `stores()`**: счётчики по хранилищу и список хранилищ в файле — `doctor`
   сможет показать, какие томы покрывает индекс, и поймать «один индекс на два хранилища».
5. **Схема → v2.** Добавлена колонка `store`; версия схемы уже заставляла пересоздавать таблицу
   при несовпадении, поэтому миграция — это пересборка (write-путь ещё не подключён, терять
   нечего).

## Почему

- Индекс — производное хранилище, и его идентичность обязана включать то, из чего он построен.
  Иначе при `MCP_TASK_DIR=/mnt/tasks`, `MCP_KNOWLEDGE_DIR=/mnt/kb` или двух `DATA_DIR` на одном
  индексе поиск начнёт отдавать чужие документы — молча, без ошибки.
- Абсолютный путь в ключе даёт бесплатную диагностику: расхождение `stores()` с ожидаемым набором
  сразу видно в `doctor` (SC-03b).

## Проверено

- `tests/search-fts.test.ts` — 20 тестов (16 прежних + 4 новых): одинаковые `project`/`id` в двух
  хранилищах не смешиваются (включая cross-store запрос без `store`), `stats(store)` и `stores()`
  считают по хранилищам, `remove`/`clearStore` не задевают соседнее хранилище,
  `resolveStoreId` нормализует хвостовой разделитель, `.`-сегменты и регистр на Windows.
- Revert-check: 3 мутации RED — убрать фильтр `store` в запросе, убрать `store` из ключа удаления,
  убрать нормализацию регистра.
- `npm run build`, `tsc -p tsconfig.test.json --noEmit` — зелёные; `api:reference` не менялся.
