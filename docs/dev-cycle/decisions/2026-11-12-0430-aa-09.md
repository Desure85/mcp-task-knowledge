## Вопрос

`BACKLOG.md` и трекер расходятся: `T-002` в BACKLOG — `done` (PR #49), а в трекере может быть
`pending`. Нужен явный read-only чекер с картой «ID бэклога ↔ задача трекера», чтобы расхождение
показывалось, а не затиралось.

## Решение

- `scripts/backlog-sync-check.mjs`: парсит таблицы BACKLOG, читает `DATA_DIR/tasks/<project>/**/*.json`
  (включая будущие shard-каталоги), сверяет только явно отображённые ID.
- `docs/backlog-tracker-map.json`: object `ID → {taskId?|taskTitle?}`; `T-002` сопоставлен
  точному трекерному заголовку `1.2 TCP/Unix сервер (multi-client)`.
- Нормализация статусов: `done/completed/closed` → `done`, `in progress/in_progress/in-progress/wip`
  → `in_progress`, `todo` → `pending`; `blocked/review/deferred` сохраняются; markdown/✅ игнорируются.
- `--json` для машинного чтения; exit 0 — 0 расхождений, 1 — есть, 2 — ошибка входа.
- BACKLOG — нормативный источник; скрипт не пишет ни BACKLOG, ни task-файлы.
- Docs `docs/features/backlog-sync.md`.

## Почему

- Точное сопоставление по title/UUID исключает ложные совпадения по подстроке.
- Read-only + хеш-проверка в тесте гарантируют, что сверка не «исправляет» данные.
- Явная карта позволяет обновлять соответствия при переименовании без fuzzy-эвристик.

## Ограничения

- Сверяются только ID из карты; полная инвентаризация не делается.
- Tracker-файлы могут быть SQLite-профилем — скрипт читает только file layout.
- Одноимённые задачи в разных проектах не различимы без `--project`; project обязателен по смыслу.
- Реальный `/data` проверяется в среде, где он смонтирован.
