# 2026-11-11 14:55 — T-02: проектные роли viewer/editor/admin и ACL

- **Пункт:** T-02 (high), зависимость T-01
- **Ветка / sha:** `feat/t-02-project-acl`, от `origin/master` `1bbc169`

## Вопрос

ACL-движок существовал, но знал только **глобальные** роли: участник проекта не мог быть viewer в одном
проекте и admin в другом; `project_list` показывал все проекты, а любой аутентифицированный пользователь
мог писать в чужой проект.

## Решение

- `ProjectMetadata.members?: Record<userId, 'viewer'|'editor'|'admin'>` в
  `DATA_DIR/projects/<id>.json`; `readProjectMetadataSync` — для синхронного security-gate.
- `src/core/project-access.ts`:
  - `resolveAccess` — open-режим/global admin → admin; проект **без** `members` считается legacy/public;
    проект с участниками — только явный член;
  - `isWriteTool` (create/update/delete/archive/close/claim/bulk/…), `isProjectAdminTool`
    (`project_update`, `project_delete`, `project_members_*`, statuses/types/transitions/agents set);
  - `checkProjectToolCall` — read требует членства, viewer не пишет, admin-инструменты требуют admin;
  - `filterVisibleProjects` — legacy + свои проекты.
- `SecurityStack` — новая стадия `project-acl` (по умолчанию включена; `projectAccess:false` только для
  тестов/аварий). `AuthManager.getSessionCurrentProject` даёт project при вызове без `project`.
- `project_list` фильтрует `projects/current/count` по caller; `project_members_list/set/remove` —
  новые MCP-инструменты; `project_update` не менялся.
- UI `/projects/settings`: карточка **Members** — список, Add/update (user id + viewer/editor/admin),
  Remove; legacy-подсказка.
- `/ws`: `canAccessProject` в `RealtimeAttachOptions`; handshake и `subscribe` отклоняют чужой project.

## Почему

- Membership в `.project.json` — существующий источник project-настроек, без новой БД и без изменения
  формата задач.
- Legacy-проекты без `members` остаются доступны, чтобы обновление не заперло существующих пользователей;
  как только admin добавляет первого участника, проект становится закрытым.
- Гейт в `SecurityStack` покрывает все tools, включая `tools_run`/`tools_batch`, а не только прямые
  handlers; project_list/search/ws дополнительно фильтруют данные.
- `project-acl` аддитивен к `ACL` и не меняет wire-формат ответов, кроме нового кода отказа в тексте.

## Проверено

- `tests/project-acl.test.ts` — **4/4**:

  - `filterVisibleProjects` скрывает чужой members-проект;

- `docs-tools-coverage` 6/6 (151 tools, 3 новых строки); web tsc; design guards 12/12; build/tsc.

## Ограничения

- Legacy-проект без `members` **публичен** для всех аутентифицированных; это осознанная миграционная
  совместимость, а не «ACL по умолчанию для всех».
- `project_members_set` не проверяет существование user id (можно добавить опечатку); UI подсказывает,
  но это не FK.
- `/ws` `canAccessProject` проверяет только project scope; события без `project` остаются глобальными.
- UI members не имеет отдельного e2e; проверены tsc/guards и серверные тесты.
- Роль `viewer` не ограничивает `prompts_*`/`knowledge_*`, если они не project-scoped? Они scoped по
  префиксу и идут через тот же gate; глобальные `memory_*`/`system_*` вне T-02.

## Откат

Revert ветки: удалить `project-access.ts`, `members`/`readProjectMetadataSync`, стадию `project-acl`,
фильтр `project_list`, member tools, UI-карточку и `canAccessProject`; тест удаляется. `project_update`
и `.project.json` останутся совместимыми.
