# 2026-11-07 06:45, P-20261107-9: документация поверхности инструментов сведена с кодом (ветка docs/mcp-docs-sync)

Вопрос: как привести доки к фактической поверхности MCP-инструментов на `origin/master` (e104188) и
поставить исполняемый страж, чтобы расхождение больше не жило незамеченным — не добавляя функций, не
меняя `src/` (кроме временных мутаций с откатом) и не выходя за файлы поручения.

## Решение

1. **Счёт инструментов — не одно число, а контракт из четырёх режимов.** Живая регистрация на e104188
   (stdio, `tools_list` с пагинацией по 100 плюс протокольный `client.listTools()`):

   | Режим | env | реестр `tools_list` | протокол `tools/list` |
   |---|---|---|---|
   | по умолчанию | — | 128 | 128 |
   | каталог, чтение | `CATALOG_ENABLED=true` | 130 | 130 |
   | каталог, запись | плюс `CATALOG_WRITE_ENABLED=true` | 132 | 132 |
   | компактный | `MCP_TOOLS_ENABLED=false` | 128 | 4 |

   Канон для документации: **128 по умолчанию, 130 с каталогом**; 132 — только при записи каталога,
   4 — то, что реально видит протокол в компактном режиме. Источник истины — регистрация, а не grep:
   вызовы `server.registerTool` многострочные, статический подсчёт даёт 133 против живых 128.

2. **`scripts/api-reference.mjs`: шапка выводится из live-списка.** `total` = размер списка,
   `core` = total минус инструменты с префиксом `service_catalog_`, число динамических — их разность.
   Хардкода нет; текст шапки объясняет, какие два инструмента динамические и при каком env они
   появляются.

3. **`tests/docs-tools-coverage.test.ts` — страж на реальной регистрации, два режима в одном файле.**
   Спай ставится на `McpServer.prototype.registerTool` **до** `createServerContext()`:
   `src/register/setup.ts:299` берёт `orig` с инстанса (то есть прототип) и вызывает его только для
   реально регистрируемых инструментов, поэтому спай видит именно протокольную поверхность — в
   компактном режиме ровно 4 имени. Это осознанно отличается от `tests/cli.tools_list.contract.test.ts`
   (TR-04c), где спай ставится на инстанс: там цель — поймать попытки регистрации, включая дубли,
   которые обёртка молча проглатывает; здесь цель — провод.
   Проверки: каждый зарегистрированный инструмент имеет строку таблицы в `docs/features/tools.md`
   (wildcard-строки вида `github_*` покрывают семейство), шапка `docs/api-reference.md` совпадает с
   live total/core/dynamic, в компактном режиме протокол равен
   `tool_help, tool_schema, tools_list, tools_run` и `tools_batch` отсутствует, в `tools.md` есть
   раздел про `MCP_TOOLS_ENABLED=false`. Вакуум-стражи: захвачено больше 120 регистраций и больше 100
   строк таблицы, иначе тест падает — «зелёный на пустоте» невозможен.
   Режимы изолированы `vi.resetModules()` и динамическим импортом (`config.ts` читает флаги при
   загрузке модуля) плюс отдельный `DATA_DIR` в `os.tmpdir()` на режим.

4. **Документированным считается только строка таблицы.** В `tools.md` строкой не были описаны
   **19** инструментов, а не 17 из поручения: `briefing` и `dashboard_stats` упомянуты в прозе, но
   строки с описанием не имели. Проза не засчитывается — иначе страж пропускает инструмент без
   описания. Добавлены все 19; счётчики разделов пересчитаны по фактическим строкам (Memory 24 → 30,
   Knowledge 14 → 15, Prompts 15 → 16, Admin 2 → 3, Graph 1 → 2, Introspection 7 → 8, новые
   Dashboard & Briefing 5, Cluster 3, Auth 1). Описания взяты из `description` живого инструмента
   (через сгенерированный `api-reference.md`), не придуманы.

5. **`AGENTS.md`: 662 → 527 строк.** §8 переписан под факт на master (ветка, база e104188, контракт
   счёта, правило «новый инструмент = строка в `tools.md` + `npm run api:reference`»). Хроника сессий
   2026-08-28 … 2026-10-31, список PR #100-#173 и прежние планы «Что дальше» перенесены **дословно**
   (164 строки) в `docs/history/agents-session-log.md` (169 строк с заголовком-провенансом) со ссылкой
   из §8 — перенос, не удаление. §11 сверен с `package.json`: `@xenova/transformers` → `@huggingface/transformers`,
   `onnxruntime-node` 1.20.0 → 1.30.0, `zod` 3 → 4, `uuid` и `service-catalog` больше не зависимости,
   добавлены `jose`, `pino`, `prom-client`, `ws`, `better-sqlite3`. §5: 116 → 128 инструментов,
   тесты — по факту прогона (3189). Структура и обязательные разделы §0-§4, §6-§7, §9-§10, §12 не менялись.

6. **`docs/deployment/systemd.md` — новое ядро под systemd** (юнит, `EnvironmentFile` с правами 640,
   нестандартный порт через `MCP_PORT`, обновление с `dist.previous`, клиенты через `bridge`).
   Проверяемые факты взяты из кода: `MCP_PORT`/`MCP_HOST` (`src/transport/http-transport.ts:227-228`),
   `/healthz`, `/readyz`, `/drainz`, `/metrics` (`:327-337`), `bridge --url/--token` и env
   `MCP_PROXY_UPSTREAM`/`MCP_PROXY_TOKEN`, коды выхода 2/3/4 (`src/cli/bridge.ts:22-110`),
   `MCP_LOGIN_USER`/`MCP_LOGIN_PASSWORD`/`JWT_SECRET` (`src/transport/login-route.ts:121-131`),
   один процесс на `DATA_DIR` и `SERVER_LOCK_HELD`/`SERVER_LOCK_FOREIGN_HOST`. В документе только
   плейсхолдеры — ни путей владельца, ни портов стенда, ни секретов. Ссылка добавлена в
   `docs/getting-started.md`.

7. **`BACKLOG.md` не менялся.** Пункта про синхронизацию документации с кодом там нет (раздел
   «Документация» закрыт на D-001…D-005), а новый пункт поручение создавать запрещает. «Итого»
   (405 / 93 / 7 / 282 / 22 / 1) не пересчитывалось — статусы не менялись.

## Почему

- **Четыре режима вместо одного числа.** Пин одного числа — либо ложь (каталог включён), либо хрупкость
  (следующий агент «починит» цифру). Контракт объясняет, откуда берётся каждое число, и страж сверяет
  его с данными, а не с литералом.
- **Прототипный спай, а не инстансный.** Компактный режим реализован тем, что `orig.call()` не
  вызывается (`src/register/setup.ts:322`), но инструмент всё равно попадает в `toolRegistry`. Поэтому
  инстансный спай в компактном режиме увидел бы 128 и не смог бы проверить провод; прототипный видит
  ровно то, что уходит в SDK.
- **Строка таблицы как критерий.** Поручение обещало 17 недостающих; фактических — 19. Причина
  расхождения не в счёте, а в критерии: `briefing` и `dashboard_stats` присутствовали в прозе.
  Принять критерий «упомянут где угодно» значило бы оставить два инструмента без описания и без
  стража.
- **Отвергнутая альтернатива для AGENTS.md:** удалить хронику (короче, но теряется история PR и
  решений) — вместо этого перенос дословно в отдельный файл со ссылкой.
- **Отвергнутая альтернатива для счётчиков:** перегенерировать `tools.md` целиком из `api-reference`
  (риск потерять пояснения и разбивку по разделам ради формальной полноты) — правки точечные.

## Находки вне скоупа (не чинились)

1. **Дублирование литерала whitelist'а компактного режима:** `src/register/tools-introspection.ts:10`
   (`TOOLS_DISABLED_WHITELIST`) и `src/register/setup.ts:322` (инлайн-массив тех же четырёх имён).
   Расхождение даст тихий дефект: `tools_list` будет обещать инструмент, которого нет на проводе.
   Предложение — экспортировать один набор и использовать его в обоих местах (правка `src/`, вне скоупа).
2. **`@types/uuid` остался в devDependencies** при том, что пакет `uuid` удалён (TD-007, `crypto.randomUUID`).
   Удаление — изменение зависимостей, поручением запрещено.
3. **`docs/getting-started.md` содержит два раздела «From source»** (строки 5-13 и 26-34); второй
   отличается только `npm start` вместо прямого `node dist/index.js`. Не ломает ничего, но дублирует
   инструкцию. Приоритет низкий.
4. **`README.md` до правки противоречил сам себе:** строка 111 «127 tools by default, 129 with catalog»,
   строка 127 и таблица Stats — «128 / 130». Исправлена строка 111; таблица Stats была верна.
5. **`docs/features/tools.md` содержал два разных итога** («129 with catalog; 127 by default» в заголовке
   и «Total: 127 tools by default (129 with catalog)» в конце) — оба отставали на один. Сведены к 128/130.
