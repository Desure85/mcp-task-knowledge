# 2026-11-11 20:00 — UI-31: блокировки и влияние

- **Пункт:** UI-31 (high); зависит от UI-30 (закрыт #385)
- **Ветка / sha:** `feat/ui-31-influence`, от `origin/master` `c521544`
- **Сырьё:** `tasks_dag`, `tasks_get_deps`, `tasks_get` (`includeGraphMetrics`),
  `knowledge_list.parentId`, страница задачи и reader документа

## Вопрос

Как на той же карточке показать, что блокирует задачу, что она заденет при изменении и где она на
критическом пути, а для документа — какие документы от него зависят, не добавляя серверный формат?

## Решение

- **Задача, блок `Influence`** (в карточке Dependencies):
  - `Blockers (transitive)` — обход `tasks_dag` вперёд по `from → to` (edge направлен от зависимой
    к зависимости); если страница DAG не содержит рёбер, fallback на прямые `tasks_get_deps.dependsOn`;
  - `Changing this task affects` — обратный обход рёбер (кто зависит от этой задачи), fallback на
    `dependedBy`;
  - `Critical path` — из `tasks_get?includeGraphMetrics=true` (`onCriticalPath`) и
    `dependentsCount`; отдельного расчёта не дублируем.
- **Документ, блок `Dependent documents`** в reader: `knowledge_list` с `parentId=<docId>` (ленивый
  уровень из #386), ссылки открывают дочерний документ в том же reader.
- Новых MCP-инструментов/полей нет.

## Почему

- `tasks_dag` уже отдаёт направленные рёбра и критический путь; карточка использует их, а не
  строит второй граф.
- DAG-страница ограничена `limit`/полями, поэтому прямой fallback на `tasks_get_deps` не даёт
  карточке остаться пустой при усечённой странице.
- `parentId`-дети — уже существующая связь документа; отдельный endpoint не нужен.

## Проверено

- `e2e/task-dependencies.spec.ts` — **UI-31 1/1**: A → B → C; карточка B показывает A в
  `Blockers (transitive)` и C в `Changing this task affects`; `Influence` виден.
- `e2e/knowledge-tree.spec.ts` — добавлена проверка: `/knowledge?doc=<parent>` показывает
  `Dependent documents`, клик по ребёнку открывает его.
- web tsc чистый; существующий UI-38 сценарий (blockers/cycle/DAG filters) не менялся по коду.
- **RED-наблюдение:** до fallback на direct deps карточка B не показывала C, потому что DAG-страница
  на переполненном проекте не содержала ребра B→C; тест падал на отсутствии C.

## Ограничения

- Транзитивный обход использует только рёбра, попавшие в текущую DAG-страницу (`limit`/бюджет);
  усечённая цепочка компенсируется прямыми зависимостями, но глубже одного уровня fallback не идёт.
- `tasks_dag` на SQLite-демо не отдаёт рёбра (известный gap профиля); fallback показывает прямые
  блокировки. CI/файловый профиль — решающий.
- Для документов показываются только прямые дети (один уровень), не всё поддерево.
- Влияние не учитывает закрытые/архивные задачи отдельно — как их отдаёт DAG/депсы.

## Откат

Revert ветки: удаляется `Influence` из карточки задачи, `Dependent documents` из reader и новые
проверки; используются только прежние Dependencies/Subtasks. Серверный wire-формат не меняется.
