# 2026-11-11 23:55 — TR-32: logger redaction + JIRA https + scopes

- **Пункт:** TR-32 (low)
- **Ветка / sha:** `fix/tr-32-redaction-jira-https`, от `origin/master` `29aa8a4`

## Вопрос

- `logger.ts` не имел pino `redact`: токены/`apiKey`/`authorization` могли попасть в stderr/файл при
  следующем wiring `LoggingMiddleware`.
- `jira.ts` принимал любой `JIRA_HOST`; с Basic-auth plaintext host отправил бы пароль/токен по HTTP.
- `connectors.md` не фиксировал минимальные scopes.

## Решение

- `LOG_REDACT_PATHS`: `token`, `apiKey`, `authorization`, `password`, `secret` + вложенные `*.*`,
  `req.headers.authorization`, `headers.authorization`; censor `[REDACTED]`.
- Redaction включён в оба варианта pino: стандартный root logger и `createLogger(destination)`
  (последний параметр добавлен для теста/embedding, кэш `_root` не используется).
- JIRA `init`: абсолютный URL и `https:` обязательны; ошибки `JIRA_HOST must be an absolute https URL`
  и `JIRA_HOST must use https (Basic auth would leak over plaintext)`.
- `docs/features/connectors.md`: таблица минимальных credentials/scopes.

## Почему

- Redaction на уровне pino — defense-in-depth до появления LoggingMiddleware; поля перечислены
  явно и покрывают вложенные объекты.
- Basic auth Jira по plaintext `http` — утечка; отказ на старте лучше, чем «работает локально».
- Scopes в документации снижают риск выдать токен с лишними правами.

  non-absolute reject, https accept.

## Ограничения

- Redaction действует только на поля pino-записи; произвольные строки в `message` не маскируются.
- Проверка JIRA host — на `init`, а не на каждом fetch; смена host в конфиге после init не поддерживается.
- `http://localhost` также отклоняется (без исключения для dev).
- Scopes — рекомендация, не проверяются API.

## Откат

Убрать `LOG_REDACT_PATHS`/`redact` и параметр destination; убрать https-проверку; удалить таблицу
scopes и тест.
