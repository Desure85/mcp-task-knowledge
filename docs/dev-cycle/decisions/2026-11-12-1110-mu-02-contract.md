# 2026-11-12 11:10 — MU-02: optimistic version contract (design gate)

- **Пункт:** MU-02 (high; design gate перед реализацией)
- **Ветка / sha:** `docs/mu-02-version-contract`, от `origin/master` `020f77f`

## Вопрос

Нужен контракт версии и `CONFLICT` для задач/документов/промптов: `version`, `expectedVersion`,
поведение при устаревшей основе, слияние правок разных полей и форма ответа конфликта.

## Решение

1. **Версия сущности** — целое `version` с 1, монотонно растёт на каждую успешную запись.
   Legacy-сущности без поля считаются `version = 1`.
2. **Карта полей** — `fieldVersions: Record<string, number>`; при записи каждому изменённому полю
   присваивается новая версия. Это позволяет отличить «кто-то изменил другое поле» от реального
   конфликта.
3. **Update-контракт** — необязательный `expectedVersion`:
   - отсутствует → текущее поведение last-write-wins (обратная совместимость);
   - `expectedVersion === current.version` → запись;
   - `expectedVersion < current.version` → для каждого поля патча:
     `fieldVersions[field] > expectedVersion` → поле конфликтует; иначе поле сливается;
     если конфликтующих полей нет — запись проходит (merge разных полей);
     если есть — `CONFLICT`, ничего не записано.
4. **Ошибка `CONFLICT`** — `ok:false`, `error.code = "CONFLICT"`, `error.data`:
   `{ expectedVersion, currentVersion, fields: string[], current: subset, diff: {field, expected?, current}[] }`.
   `current` — только значения полей, не весь объект; пароли/секреты не попадают.
5. **Задачи/документы** — integer `version`/`fieldVersions`; документы сохраняют существующий
   `history`/`.versions` как отдельную механику, но `version` становится авторитетной для CAS.
6. **Промпты** — версия semver (`id@version`); `expectedVersion` — строка, сравнение точное;
   field-level merge не применяется, конфликт возвращает текущую версию и список полей.
7. **Не трогать** claim/heartbeat: они не bump `version` и не должны создавать ложный конфликт
   (это уже зафиксировано в `TaskClaim`).

## Почему

- Version-only CAS без fieldVersions не даёт требуемого «разные поля сливаются».
- Хранить историю изменённых полей на каждой сущности дешевле, чем отдельный журнал, и достаточно
  для контракта.
- `expectedVersion` опционален: существующие клиенты и wire-формат не ломаются.
- `CONFLICT` возвращает данные, а не только текст, чтобы UI мог показать «взять чужое/оставить моё».

## Проверено

- Codebase: у `KnowledgeDocMeta` уже есть `version`/`history` (TD-005); у `Task` версии нет;
  промпты версионируются semver-файлами. Контракт учитывает все три случая.
- `TaskClaim` уже требует не менять `updatedAt`/version на heartbeat — конфликт с контрактом
  отсутствует.
- Реализация не входила в этот PR; тесты появятся вместе с ней.

## Ограничения

- Это design-only: код `expectedVersion`/`CONFLICT` ещё не реализован; MU-02 остаётся open.
- Field-level merge работает только если клиент прислал `expectedVersion`; без него — LWW.
- Для промптов semver-сравнение точное, без range/diff.
- Поля, добавленные после `expectedVersion`, считаются изменёнными (`fieldVersions` отсутствует = 0),
  поэтому могут дать конфликт; это консервативно.
