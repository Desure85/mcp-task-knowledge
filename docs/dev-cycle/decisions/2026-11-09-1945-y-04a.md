# 2026-11-09 19:45 — Y-04a: политика внешних провайдеров эмбеддингов

- **Пункт:** Y-04a (подпункт Y-04; Y-04 закрывается после Y-04b)
- **Ветка / sha:** `feat/y04a-external-policy`, от `origin/master` `f4ef6ea` (PR #331 влит)
- **Основание:** ADR-009 §«Внешние провайдеры эмбеддингов» (правила 1–3), план Y-04a, решения Y-03a–c

## Вопрос

Нужно разрешить внешние провайдеры эмбеддингов — но ровно так, как требует ADR: по умолчанию ничего
не уходит, включение только явным флагом, при включении — предупреждение при старте, запись в
декларацию приватности, ключи через `SecretManager`, исключение приватных проектов и документов
`trustLevel: external`, лимиты и учёт стоимости. Ошибка внешнего провайдера не должна выглядеть как
«ничего не найдено».

## Решение

1. **`src/search/external-policy.ts`** — конфигурация из env (`EMBEDDINGS_EXTERNAL_ENABLED` и
   спутники, читается лениво, без циклов с `config.ts`), `externalEmbeddingStartupWarning()`
   (текст предупреждения при старте), `externalEmbeddingPrivacyEntry()` (строка для
   `docs/privacy.md` генерируется из кода, чтобы документ не расходился с поведением),
   `createExternalEmbeddingGate()` — решение «можно ли отправить» по проекту и `trustLevel`, и
   `ExternalEmbeddingError` с кодами `DISABLED | MISSING_KEY | POLICY_DENIED | RATE_LIMITED |
   PROVIDER_ERROR`.
2. **`src/search/external-provider.ts`** — обёртка `EmbeddingProvider`: при выключенном флаге
   бросает `DISABLED` и не трогает ни внутренний провайдер, ни секреты; при включённом лениво
   достаёт ключ из `SecretManager` (в логи/события попадает только имя ключа), ограничивает тексты
   в минуту, считает запросы/тексты/оценку токенов и стоимость, а ошибку внутреннего провайдера
   превращает в `PROVIDER_ERROR` с событием деградации. `fingerprint()` подменяет `modelId` на
   `external:<provider>:<model>`, чтобы коллекция не смешалась с локальной.
3. **Исключения работают до выхода из машины:** `IndexingServiceOptions.externalPolicy` и
   `FileProfileOptions.externalPolicy` — заблокированные элементы не попадают в очередь вовсе
   (счётчик `blocked` в статусе), а не фильтруются после. `Setup` строит гейт из конфигурации и
   передаёт его в профиль; предупреждение пишется в лог один раз при старте.
4. **`embeddings_status`** получил секцию `external` (включён/провайдер/модель/baseUrl/
   предупреждение) — статус честно показывает egress, а не только локальную конфигурацию.
5. **Декларация приватности обновлена** (`docs/privacy.md`): строка про external embeddings с
   триггером, адресатом, отправляемыми данными и исключениями.

## Почему

- Гейт на этапе **постановки в очередь**, а не в провайдере: у `EmbeddingProvider` нет проекта и
  `trustLevel` в сигнатуре, а «отфильтровать после отправки» — уже утечка.
- Ленивый ключ: секрет не должен читаться на старте, если внешний провайдер не используется, и не
  должен попадать в логи при ошибке (тест это фиксирует).

## Проверено

- `tests/embedding-external-policy.test.ts` — 12/12: без флага `DISABLED`,inner не вызывается и
  секреты не читаются; с флагом ключ читается один раз, в события не попадает, стоимость считается;
  отсутствующий секрет → `MISSING_KEY`; лимит текстов/минуту срабатывает и восстанавливается после
  окна; гейт блокирует исключённый проект и `trustLevel=external`; индексатор не ставит в очередь
  заблокированные элементы (`blocked` в статусе), внутренний провайдер видит только разрешённые
  тексты; ошибка провайдера → `PROVIDER_ERROR` + событие без секрета; `embeddings_status.external`
  выключен по умолчанию; запись приватности не содержит секрета.
- Затронутые наборы: `indexing-service` 11, `embedding-contract` 12, `embedding-collections` 11,
