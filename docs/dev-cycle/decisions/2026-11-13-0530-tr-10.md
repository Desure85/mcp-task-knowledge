# 2026-11-13 05:30 — TR-10: API governance

- **Пункт:** TR-10 (low, был `blocked` на design review)
- **Ветка:** `docs/tr-10-api-governance`, от `origin/master` `2259bc4`

## Вопрос

Для ~200 инструментов нет политики: что считается breaking change, какие error-коды
стабильны, как именовать новые tools и как выводить из эксплуатации старые.

## Решение

`docs/api-governance.md` фиксирует:

1. **Версионирование**: minor — только additive; major — rename/remove/required/new envelope.
2. **Совместимость**: enum растёт, клиент игнорирует неизвестные поля/значения; `ok/error`
   конверт стабилен; `code/hint/details/meta` — additive.
3. **Error taxonomy**: `VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT`, `FORBIDDEN`,
   `UNAVAILABLE`, `RATE_LIMITED`, `CONFIRM_REQUIRED`, `INTERNAL`; код — стабильный
   `UPPER_SNAKE_CASE`, один код = одно условие, новый код документируется в том же PR.
4. **Naming**: `<domain>_<verb>`, `_bulk_`, `_list`, `_get`; существующие исключения
   (`tools_run`, `briefing`, `changes_since`, `graph_neighbors`) заморожены.
5. **Deprecation**: `[DEPRECATED since X.Y: use …]`, минимум два minor-релиза (или 90 дней),
   старая форма продолжает работать, удаление — только в major.
6. **PR checklist** и известные ограничения.

Это **design-only**: runtime-флага `deprecated` в ToolRegistry нет, политика действует как
ревью-контракт, а не как enforcement.

## Почему

- Без политики каждый PR решает совместимость заново; ломать клиентов легко, заметить — поздно.
- Единая таксономия ошибок нужна и MCP-клиентам, и UI: `code` уже используется в контрактах.
- Заморозка существующих имён важнее косметического переименования.

## Ограничения

- Нет runtime `deprecated` и автоматической проверки breaking changes.
- Политика не покрывает prompt/skill-файлы и storage-схемы — у них отдельные ADR.
- Tool profiles (AA-08) скрывают tools, но не являются deprecation-механизмом.
