## Вопрос

Хранилище FTS5 (`src/search/fts-index.ts`) готово, но не подключено: индекс наполняется только
вручную, поэтому SC-03c (чтение из индекса) не может быть выпущен — поиск отдавал бы устаревшее.
Нужно: где писать, каким текстом, что делать с archived/trashed, как пережить сбой записи и как
доказать, что индекс полон.

## Решение

1. **Точка записи — storage-слой**, рядом с существующими хуками metadata-индекса:
   `createTask`/`updateTask`/`deleteTaskPermanent` в `src/storage/tasks.ts`,
   `createDoc`/`updateDoc`/`deleteDocPermanent` в `src/storage/knowledge.ts`,
   `deleteProject` в `src/projects.ts`. Хендлеры инструментов не трогаются.
2. **Текст — `buildTextForTask`/`buildTextForDoc`** из `src/search/index.ts`, те же, что у
   in-memory BM25. Своя композиция запрещена: иначе SC-03c изменил бы recall по причине, не
   связанной с ранжированием.
3. **`store` — `resolveStoreId(TASKS_DIR)` и `resolveStoreId(KNOWLEDGE_DIR)`**, у видов разные
   корни. `doctor`/`verify` показывают счётчики по каждому `(store, kind)` — это и есть требуемое
   ADR-009 «расхождение скоупов» с metadata-индексом, который знает один `DATA_DIR`.
4. **Файл индекса — `DATA_DIR/.index/metadata.db`**, тот же гейт `STORAGE_INDEX=auto|off`, что у
   metadata-индекса; FTS открывается вторым соединением better-sqlite3 (WAL + `busy_timeout`
   уже настроены в `FtsSearchIndex`).
5. **Индекс — только поисковый корпус:** archived/trashed удаляют строку, restore возвращает.
   В схеме `search_fts` нет колонки archived; добавлять её — значит либо фильтровать после
   ранжирования, либо протаскивать флаг в SC-03c.
6. **Сбой записи индекса не валит мутацию.** Файл уже записан и остаётся источником правды;
   ошибка логируется и ставит `search_meta.dirty` (+ `dirty_reason`), `reindex` снимает флаг.
   Прецеденты: `emitKnowledgeChanged` глотает ошибки слушателя, metadata-индекс ставит `dirty`.

Дополнительно: `reindex --data` пересобирает FTS (полностью или по `--project`), `--verify`
считает расхождение проблемой (exit 1), `doctor` предупреждает `fts-unavailable`/`fts-dirty`/
`fts-drift`/`fts-stale-terms`. Пропуск «everything complete» больше не срабатывает, если FTS
отсутствует, грязный или расходится по счётчикам.

## Почему

- **Storage-слой, а не инструменты.** `src/register/bulk.ts` вызывает те же `updateTask`/
  `updateDoc` (строки 96 и 141), поэтому `tasks_bulk_*`/`knowledge_bulk_*` покрываются бесплатно;
  хендлерная точка их бы пропустила. `project_purge` идёт через `deleteTaskPermanent`/
  `deleteDocPermanent` — тоже покрыт. Отдельно обработан только `project_delete`, который удаляет
  каталоги целиком и per-row хуков не вызывает.
- **Тот же текст.** Пара «индексируем `buildTextFor*` → читаем `tokenize`» держит паритет
  recall между старым и новым путём; SC-03a уже зафиксировал паритет токенизации тестами.
- **Удаление archived/trashed.** Альтернатива — хранить всё и фильтровать на чтении — требует
  либо колонки в FTS (схема v3), либо join к storage на каждый хит, что и есть стоимость, которую
  SC-03 убирает. Restore проходит через `updateDoc`/`updateTask`, поэтому строка возвращается
  автоматически.
- **Отказ не валит мутацию.** Индекс производный; падение поиска не должно ломать запись задачи.
  Цена — возможная неполнота, которую ловит `verify`/`doctor` и лечит `reindex`.
- **Отвергнуто:** писать из хендлеров (пропускает bulk и purge), новая шина событий для задач
  (у знаний шина есть, но она нужна фоновому прогреву эмбеддингов; для FTS достаточно прямого
  вызова в той же транзакции), отдельный файл индекса (DoD требует `.index/metadata.db`),
  новые интерфейсы провайдеров (это Y-02, ADR-009 прямо разрешает SC-03b писать напрямую).

## Откат

`STORAGE_INDEX=off` выключает и metadata-индекс, и FTS-запись (индекс не создаётся). Точечно —
убрать вызовы `note*` из storage-слоя: read-путь SC-03b не меняет, поэтому поиск продолжит
работать на in-memory BM25. Файл `.index/metadata.db` производный: удаление безопасно,
`reindex` создаёт заново.
