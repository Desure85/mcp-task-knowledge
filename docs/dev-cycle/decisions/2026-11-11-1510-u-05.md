## Вопрос

`npm run memory:verify` умел проверять живость анкоров, но только как CLI: агент, опирающийся на факт,
не мог спросить сервер «этот якорь ещё жив?» без выхода в shell и без разбора JSON-файла.

## Решение

- `src/memory/verify.ts` — чистая часть CLI: `anchorsOf`, `buildSuffixIndex`, `resolveRepoPath`,
  `lineInRange`, `ticketOf`, `branchesFor`, `verifyAnchors`, `loadRepoIndex`.
- `memory_verify({ project?, repo?, limit?, status? })`:
  - читает `memory_fact`-документы через `storageProfile(ctx).docs` (file/sqlite/postgres);
  - `repo` по умолчанию `process.cwd()`, `git rev-parse --show-toplevel` должен совпасть с `repo`
    (иначе `REPO_INVALID`, без случайного наследования родительского git);
  - путь/строки — `git ls-files` + suffix-map; символы `Class::method` — `git grep` по `.php`
    с кешем на запрос;
  - статусы `verified / stale / no-anchor`, `counts` и `items`; `status` фильтрует выдачу;
  - **read-only**: теги `state:*` не пишутся (в отличие от CLI `--write`).
- `pending-merge` в MCP-версии не вычисляется (нужен ticket-branch проход CLI), поэтому в `counts`
  всегда 0; это записано, а не замаскировано.

## Почему

- Та же модель анкоров, что в CLI, вынесена в модуль — нет второй правды.
- `repo` явный и проверяется на корень: иначе `git ls-files` из вложенной папки вернул бы чужой индекс.
- Read-only по умолчанию: инструмент вызывается агентом до решения, а не как фоновый рефакторинг тегов.
- Слабые анкоры (bare-имя без строки) могут подтвердить факт, но не делают его stale — как в KE-04.

## Ограничения

- `pending-merge` не вычисляется; CLI остаётся полным проходом по тикет-веткам.
- Семантическая проверка («факт всё ещё значит то же») не автоматизируется — только анкоры.
- Символы ищутся по `.php`-файлам; TS/JS-символы не поддержаны.
- `repo` должен быть корнем git; подкаталог отклоняется.
- Read-only: обновление `state:*` тегов только CLI.
