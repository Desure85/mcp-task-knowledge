# 2026-11-11 15:00 — SC-04: серверная пагинация и агрегированные счётчики

- **Пункт:** SC-04 (high); зависит от SC-01
- **Ветка / sha:** `feat/sc-04-server-pagination`, от `origin/master` `1ebe8ca`
- **Сырьё:** `web-ui/app/tasks/page.tsx`, `web-ui/app/knowledge/page.tsx`,
  `web-ui/lib/api-client.ts` (`callToolAll`), `src/register/tasks.ts`, `knowledge_list`, 10k fixture
  `scripts/bench/seed-scale.mjs`, реальный прогон `scripts/bench/ui-bench.mjs`

## Вопрос

Почему дашборд на 10k задач/документов всё равно привозит весь корпус в браузер, и какие серверные
страницы/счётчики нужны, чтобы DOM и время до отрисовки уложились в SC-04 без потери drag&drop,
bulk-select, quick view и фильтров?

## Решение

- **Доска:** `tasks_list` получил `groupByStatus` + `offsets` — один ответ с ограниченными колонками
  (`limit` 25 на статус), точными `total` по каждой колонке, `typeCounts` и `nextOffset`. UI делает
  один вызов вместо `callToolAll`, показывает «Showing X of total» и кнопку **Load more**
  (следующий `offsets` для колонок). Фильтры `priority`/`tag`/`type` уходят в серверный вызов.
- **Знания:** `knowledge_list` уже отдавал cursor-страницы; UI переведён на `api.knowledge.page`
  (60 документов), `Load more` и серверные `tag`/`type`; поиск остаётся серверным
  (`search_knowledge`).
- **Счётчики:** статусы — из `total` каждой колонки; типы — `typeCounts` из того же агрегата, а не
  из загруженной страницы.
- **Bench:** `ui-bench.mjs` теперь считает `domSettledMs` по последней записи `MutationObserver`, а
  не по грубому опросу `querySelectorAll('*').length` (тот видел только изменения количества
  элементов и требовал 3 с тишины). `pollSettledMs` сохранён для сравнения; детектор MCP-запросов
  понимает и прямой `/mcp`, и прокси `/api/mcp`.

## Почему

- Один агрегат по всем задачам нужен только для точных счетчиков; отдавать 10k карточек в браузер
  для этого не нужно. `groupByStatus` удерживает ответ O(limit × статусы), а `total` остаётся точным.
- Отдельный новый MCP-инструмент увеличил бы контракт и счётчик инструментов; флаг на существующем
  `tasks_list` аддитивен и не ломает текущих клиентов.
- `MutationObserver` измеряет то, что заявлено («последнее изменение DOM»), а не косвенную эвристику.

## Ограничения, записанные честно

- Это **bounded pagination + Load more**, а не windowing-библиотека: DOM ограничен страницей, но
  off-screen карточки остаются в дереве. Для SC-04 метрики этого достаточно; настоящая
  виртуализация — отдельный шаг, если понадобится.
- «Load more» грузит следующую страницу всех колонок сразу; точечная подгрузка одной колонки не
  делалась.
- Опции tag/type в знаниях строятся по первой странице; полный facet-список потребует отдельного
  агрегата. Поиск ограничен 100 результатами.
- `search_tasks` для текстового поиска отдаёт до 100 совпадений; счётчики при активном поиске —
  по результатам поиска, не по колонкам.
- Бенчмарк-метрика `domSettledMs` переопределена на MutationObserver; `pollSettledMs` сохранён,
  чтобы старые и новые числа можно было сопоставить.

## Откат

`tasks_list`, `page()` из api-client и `Load more`; `ui-bench.mjs` возвращается к count-опросу.
Данные и wire-формат без флага не меняются.
