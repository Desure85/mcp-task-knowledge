## Вопрос

Как показать расхождение производного индекса с файлами и как его починить, не нарушая двух
инвариантов: файлы остаются источником истины, а `doctor --fix` не трогает индекс. Дополнительно:
`rebuild()` заполняет таблицы строк, но не пишет строки `projects`, поэтому после перестройки
индекс формально «неполный» и страницы уходят на файловый путь, пока фоновое наполнение не
повторит тот же скан.

## Решение

1. **Сверка — отдельный read-only модуль `src/cli/index-inspect.ts`, сравнение по `rel_path` +
   `mtime_ms`.** Файловая сторона — `readdir` + `stat` (без разбора JSON/frontmatter), сторона
   индекса — прямые SQL-запросы. Четыре находки и два состояния: `orphans` (строка без файла),
   `missing` (файл без строки), `drift` (`mtime` разошёлся), `countDrift` (`projects.file_count`
   не равен числу строк), плюс `dirty`, версия схемы, `data_dir` и полнота проектов. Сэмплы
   ограничены (20 по умолчанию), итоговые числа считаются всегда — отчёт не растёт с корпусом.
2. **`size` не сравнивается.** Схема хранит `mtime_ms`, но не `size`; добавление колонки —
   версия схемы 3 и перестройка у всех ради сигнала, который `mtime` уже несёт. Отклонение от
   формулировки проработки («расхождения mtime/size») записано здесь явно.
3. **В `doctor` находки индекса — `warn`, никогда `error`.** Индекс производный: расхождение
   стоит скорости, а не данных. Отсутствующий `.index/` — нормальное состояние (свежий `DATA_DIR`
   или `STORAGE_INDEX=off`), предупреждение только для существующего и нечитаемого файла.
   `--fix` индекс не трогает: у него своя команда.
4. **Ремонт — команда, а не флаг.** Проработка упоминала `doctor --reindex`; пункт бэклога
   фиксирует команду `reindex [--project] [--verify] [--force]`. Выбрана команда: у неё своя
   семантика (`--verify` без записи и с exit 1, `--project`, `--force`), а `doctor` остаётся
   диагностикой без побочных эффектов.
5. **Полный `rebuild` завершается `markProjectsComplete()`.** Иначе `reindex` чинил бы индекс,
   который тут же игнорируется гейтом полноты SC-02c. Метод пишет `projects` (row count,
   `synced_at`, `dir_mtime_ms = 0`) и снимает `dirty` — ровно то, что проверяет
   `isProjectComplete`. `dir_mtime_ms` остаётся 0 осознанно: `writeJson` пишет временный файл и
   делает rename, поэтому mtime каталога меняется на каждой записи и триггером быть не может; это
   диагностика, как и записано в проработке.
6. **`reindex` берёт lock `DATA_DIR` (MU-01), `--verify` — нет.** Перестройка пишет в тот же
   каталог, что сервер; вместо гонки команда отказывается работать (`SERVER_LOCK_*`, exit 2) с
   подсказкой, как освободить каталог. `--verify` ничего не пишет и lock не нужен.
7. **`--force` снимает единственную оптимизацию «ничего не делать».** Проверка дешёвая:
   `isProjectComplete` по проектам из `readdir`, без обхода файлов. Глубокая проверка — это
   `--verify`.
8. **`.index` добавлен в `BASE_EXCLUDED` архива бэкапа.** В `src/services/data-backup.ts`
   исключение было с SC-02a, а `src/services/backup-archive.ts` (путь `admin_backup`) его не
   знал: 140 MB производных данных попадали в каждый архив. Это дефект, а не украшение.

## Почему

- Сравнение по `rel_path` — единственный ключ, который есть и в индексе, и в файловой системе без
  разбора содержимого; `id` у документов может прийти из frontmatter, и сверка по именам файлов
  давала бы ложные «пропуски».
- `warn` вместо `error` держит контракт: `doctor` отвечает на вопрос «целы ли данные», а индекс
  чинится командой.
- `markProjectsComplete` закрывает разрыв между «перестроил» и «используется»: без него `reindex`
  выполнял бы работу, которую гейт игнорировал бы до следующего чтения (и оно же повторяло бы
  скан в фоне).
- Lock в `reindex` — тот же инвариант, что у сервера: один писатель на `DATA_DIR`.

## Проверено

- `npx vitest run tests/metadata-index-doctor.test.ts` — 14 тестов: чистое состояние (строки,
  файлы, полнота), удалённый файл → сирота, добавленный → пропуск, правка `utimes` → дрейф,
  отсутствующий индекс → `available: false` без исключения, `doctor` печатает `Index:` и даёт
  `warn`, `doctor` и `doctor --fix` не меняют `built_at`/`dirty`, `reindex --project` лечит,
  полный `reindex` помечает проект полным, «nothing to do» без `--force` и перестройка с ним,
  `--verify` → exit 1 при расхождении и exit 0 на чистом, `STORAGE_INDEX=off` → no-op, разбор
  флагов (exit 2), `.index` не в архиве и данные в архиве есть.
- Revert-check — 4 мутации RED→GREEN: убрать `.index` из `BASE_EXCLUDED`; не собирать сэмплы
  сирот; не вызывать `markProjectsComplete`; вернуть `--verify` exit 0. Каждая красит ровно один
  тест.
- Соседние наборы: `tests/metadata-index.test.ts`, `tests/metadata-index-write.test.ts`,
  `tests/scale-index.test.ts`, `tests/doctor-data.test.ts` — 83 теста зелёные (перестройка,
  запись, чтение и `doctor` не задеты).
  `tests/dx16-backup-archive.test.ts` на этой машине не запускается по причине окружения
  (`EPERM: operation not permitted, symlink` при сиде), к изменению отношения не имеет — Linux CI
  его прогоняет.
- Живой замер на 100k-корпусе (200 000 файлов, Windows 11/NTFS): `reindex --data --verify` —
  10.4 с, 0 сирот/пропусков/дрейфа, exit 0; `reindex --data` — «nothing to do» (проект полный);
  `reindex --data --force` — 128.3 с на 200 000 строк (100 пачек), после него проект полный и
  сверка снова чистая.
- `npm run build`, `npm run backlog:check`, `markdownlint` на изменённых файлах — зелёные.

## Найдено

- Устаревший `DATA_DIR/.server.lock` после убитого сервера блокирует `reindex` на Windows
  (`SERVER_LOCK_UNVERIFIABLE`: нет времени старта процесса, pid мог быть переиспользован). Это
  корректная защита, но она же — продолжение находки SC-02e про lock; автоматики нет, только
  сообщение.
