## Вопрос

`search_tasks` и `search_knowledge` собирали весь корпус в память и заново строили BM25 на
каждый запрос (23.6 с и 4.1 GB RSS на 100k). Индекс FTS5 уже написан при мутациях (SC-03b), но
чтение его не использует. Как переключить чтение, не отдав неполный индекс за полный и не потеряв
качество ранжирования?

## Решение

1. **FTS — префильтр кандидатов, не замена ранжирования.** `search_tasks`/`search_knowledge`
   берут до 500 id из `search_fts`, затем прогоняют их через существующие `hybridSearch`/
   `promoteExactMatches`/`fuseRankings`. Токенизация 500 кандидатов дешёвая, а правила
   (lexical floor, RRF, promotion точных анкоров, пустой ответ на anchor-only запрос) остаются
   ровно те же.
2. **Полнота доказывается тремя сторонами:** `metadataIndex.isProjectComplete(project)`,
   `!fts.isDirty()`, и `fts.projectCounts(store, project)` равны счётчикам metadata-индекса с
   `archived = 0 AND trashed = 0` с обеих сторон (FTS не хранит архивные строки, metadata — да).
   Любая сторона не сходится → запрос идёт файловым сканом.
3. **Дозаполнение — фоном, по образцу `ensureProjectIndexed`:** один inflight на проект;
   сначала metadata-fill (он же обновляет `projects.file_count`), затем FTS-rebuild проекта.
   Запрос, запустивший fill, отвечает файловым сканом и помечает ответ `indexing: true`.
   Грязный индекс (`dirty`) не дозаполняется: только полный `reindex --data` доказывает, что не
   потеряна чужая строка.
4. **Честность ответа:** поле `source: 'fts' | 'scan'` в meta; при FTS `totalExact: false` и
   `candidates`, когда пул кандидатов упёрся в лимит. Фолбэк больше нельзя принять за полный
   индекс ни по meta, ни по числу.
5. **`type` в `search_tasks` остаётся на файловом пути:** фильтр типа применяется к корпусу до
   ранжирования; постфильтрация FTS-кандидатов изменила бы, какие задачи вообще ранжируются.
6. **Миграции DATA_DIR — за офлайн-путём `reindex --data`.** Сервер при первом boot на большом
   DATA_DIR делал полную перестройку metadata-индекса (и теперь FTS), не успевая к `/healthz` за
   120 с. `reindex --data` применяет миграции и пишет `.schema-version`; следующий boot не
   мигрирует и не перестраивает. Полная перестройка при миграциях дополнительно вызывает
   `markProjectsComplete()`, иначе проекты остаются untracked до фонового fill.

## Почему

- **Префильтр, а не «FTS вместо BM25».** FTS5 `bm25()` и наш BM25 расходятся в IDF-гейте
  (`BM25_MIN_IDF_RATIO`), confidence floor и exact-anchor promotion. Прямой переход на
  `bm25(search_fts)` изменил бы качество по причине, не связанной с индексом. Кандидаты + старый
  ранжировщик сохраняют поведение, а индекс убирает O(corpus) работу.
- **Три стороны полноты, а не флаг.** `fillProject` пишет строки прямо в SQLite и обходит
  storage-хуки, поэтому «metadata complete» не означает «FTS полон»; обратное тоже неверно.
  Счётчики ловят пропавшие строки, `dirty` — потерянную запись.
- **Фоновый fill.** Синхронная постройка на 100k — это те же 100+ с внутри запроса; фолбэк на
  файлы даёт корректный, хоть и медленный первый ответ, а второй уже идёт из индекса.
- **Отвергнуто:** отдавать FTS-скор напрямую (ломает паритет и `exactMatches`), фильтровать
  `type` после FTS (меняет корпус ранжирования), дозаполнять при `dirty` (нельзя доказать
  отсутствие потерь), вектор только по кандидатам без фолбэка при пустом FTS (теряются
  семантические запросы без лексического пересечения — при пустом пуле остаётся скан).

## Попутно исправлено (дефект SC-03a)

`upsert()` делал `DELETE FROM search_fts WHERE store = ? AND id = ? AND kind = ?` на каждую
строку, а эти колонки в FTS5 `UNINDEXED` — полный скан таблицы на каждую запись. На 100k
`reindex --data` шёл 26 минут на 100% CPU (rchar 411 ГБ), не записав ни строки. Добавлена
таблица `search_fts_keys(store, kind, id, project, rowid)` с PRIMARY KEY и индексом
`(store, kind, project)`: удаление/обновление по rowid, `rebuild` очищает таблицу один раз и
вставляет без предварительных DELETE. Схема FTS — v4 (при несовпадении пересоздаётся).
Тот же индекс колонки `project` сделал проверку полноты O(log n): она стоила ~670 мс на 200k и
вызывалась дважды за `search_tasks` (1.8 с).

## Откат

`STORAGE_INDEX=off` оставляет только файловый путь (индекс не создаётся, FTS не читается).
Точечно — убрать `ensureProjectFtsIndexed`/`fts*Candidates` из `src/register/search.ts`: старый
скан и `hybridSearch` остаются на месте. Файл `.index/metadata.db` производный: удаление
безопасно, `reindex --data` создаёт заново (схема v4).
