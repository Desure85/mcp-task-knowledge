# 2026-11-06 21:50, DX-16: архив DATA_DIR только для файлового профиля, restore это замена, а не наложение

Вопрос: что именно делают `admin_backup`/`admin_restore`, в каком формате и с какими гарантиями
(этап ADR перед реализацией DX-16a/DX-16b).

Решение (полностью в `docs/adr/0008-admin-backup-restore.md`, статус Proposed):

1. Формат — стандартный tar.gz с `manifest.json` в корне: `formatVersion`, `profile`,
   `schemaVersion`, `entries[].sha256`, `excluded`. Только относительные пути, детерминированная
   сортировка. Свой writer/reader на `node:zlib`: в зависимостях нет tar/zip, новые запрещены, а
   защита от `../`, симлинков и бомб всё равно делается нами.
2. В архив не входят `.jwt-revoked.json`, `auth.db`, `audit.log`, `.embeddings`, `.emb_cache`,
   `.backups`. Секреты добавляются только флагом `include-secrets`, и это помечается в манифесте.
3. Restore — замена в пределах scope (`prune`), а не наложение: иначе состояние не равно архиву и
   R12 не выполняется. `dryRun` по умолчанию, `confirm` с одноразовым токеном, автоснапшот
   `pre-restore` перед применением, `.restore.lock` между процессами.
4. Архив поддерживается только для файлового профиля; SQLite/Postgres получают
   `BACKUP_PROFILE_UNSUPPORTED` и отсылку к средствам СУБД и `migrate-storage` (Y-08).
5. Найденные дефекты существующего `restoreBackup` (доверие `entry.from`, сохранение симлинков,
   копирование секретов, наложение вместо отката, отсутствие версии/контрольных сумм) в этом PR не
   чинятся: они вынесены в DX-16b с file:line в ADR. `dev-cli export` не переиспользуется: он не
   копирует файлы и смотрит в пустой временный DATA_DIR.

Почему: decisions-log `:128-133` фиксирует «один активный профиль, источник правды это он» и что
бэкап работает по активному профилю, поэтому tar по DATA_DIR верен только для files; `:96-101`
прямо запрещает хеши в backup без флага. Наложение вместо откатa подтверждено пробой: документ,
созданный после бэкапа, остался, а отзыв токена, сделанный после бэкапа, исчез.

Проверено (2026-11-06, `/tmp/dx16-probe`, `dist/` ветки):

- `createDataBackup({scope:'full'})` на реалистичном DATA_DIR: 14 файлов, в манифесте
  `.jwt-revoked.json` и `auth.db`; симлинки сохранены (`outside-link -> /etc/hostname`).
- `restoreBackup` после изменения данных вернул файлы, но затёр `.jwt-revoked.json` версией из
  снапшота; документ, созданный после бэкапа, остался (наложение).
- Подменённый манифест с `from` вне DATA_DIR привёл к записи в `/tmp/dx16-probe/outside`
  (path traversal, `src/services/data-backup.ts:376-392`).
- `dev-cli export --out …`: 0 записанных файлов, `mcp: 0 tasks, 0 docs` (`scripts/dev-cli.mjs:46-59`,
  `:130-148`).
- `npm run docs:test` исполняет пример из ADR (`tar.gz` + детект `../`), `npm run lint:md`,
  `npm run backlog:check`, `npm run build`, `npm run test:types`, `npm test` — результаты в отчёте
  поручения.

Откат: revert коммитов ветки `docs/dx16-backup-adr`; строка DX-16 в BACKLOG возвращается к прежней
формулировке, подпункты DX-16a/DX-16b удаляются, ADR-008 удаляется. Реализация не затрагивалась.
