## Вопрос

Как перенести DATA_DIR между файловым и SQLite-профилями идемпотентно, с проверяемой целостностью и
безопасным откатом, не меняя wire-формат и не оставляя источник в изменённом состоянии?

## Решение

1. **Движок `src/storage/migrate.ts`** (`migrateStorage`) реализует фазы ADR:
   - **план**: читает снимок обеих сторон (file: задачи JSON, markdown с frontmatter, метаданные
     проектов, `.versions`, блобы; SQLite: таблицы напрямую), считает `created/updated/skipped` по
     sha256 канонического JSON и расхождения; `dryRun` возвращает отчёт, ничего не записывая и не
     создавая backup;
   - **снимок цели**: копия SQLite-файла и блобов (или файловых каталогов при обратном направлении)
     в `DATA_DIR/.backups/migrate-<timestamp>`;
   - **дельта**: запись в цель под `withFileLock('migrate-storage:<dataDir>')` — эксклюзивная секция
     в процессе; SQLite пишется транзакцией, файлы — поэлементно; источник не меняется;
   - **проверка**: повторное чтение цели, контрольные суммы по коллекциям + блобам, обновление
     `discrepancies` уже по пост-состоянию (а не по плану), `checksums.equal`;
   - **переключение**: `switchHint` — `STORAGE_PROFILE=sqlite|file` и рестарт; откат — вернуть
     профиль, потому что данные в старой локации не тронуты, повторное копирование не нужно.
2. **Идемпотентность**: сравнение по каноническому JSON (сортированные ключи, без `undefined`);
   совпавшие записи — `skipped`, изменённые — `updated`, новые — `created`. Нормализация тела
   документа (CRLF→LF, снятие хвостовых переводов строки) делает round-trip file→SQLite→file
   стабильным; frontmatter сохраняет `history`, потому что файловый профиль хранит версии в нём.
3. **Область**: задачи, документы, проекты, версии документов, блобы. Промпты/память в обоих
   профилях файловые — переносятся вместе с DATA_DIR и не копируются отдельно; журнал событий и
   замки — операционные данные профиля (снапшоты/lease пересоздаются) и осознанно не мигрируются.
4. **CLI**: `scripts/migrate-storage.mjs` (обёртка над `dist/`) поддерживает
   `--data/--db/--direction/--dry-run/--verify/--json`; runbook —
   [`docs/features/migrate-storage.md`](../../features/migrate-storage.md).

## Почему

Прямая работа с раскладкой file-профиля и таблицами SQLite — самый короткий путь, который не требует
нового публичного контракта импорта и не переписывает инструменты. Проверка целостности считается по
содержимому (json/блобы), а не по mtime/размерам; поэтому перезапуск безопасен.

## Проверено

- `tests/storage-migrate.test.ts` — **4/4**: dry-run не создаёт БД/backup и корректно считает план;
  file→SQLite переносит задачи (включая архивные), документы, проект, версии и блоб, `checksums.equal`
  true, повторный прогон — `skipped` без дублей, чтение через SQLite-профиль совпадает; изменение
  файла даёт `updated=1` и равные суммы; **verify-only** после порчи цели не пишет, отдаёт
  `equal=false` и discrepancy; обратный перенос SQLite→file восстанавливает читаемую раскладку
  (задачи, доки, версии, блоб).
- Затронутые наборы: `storage-migrate`, `storage-sqlite`, `storage-contract`, `storage-wiring` —
  **71/71**; `tsc` test-проекта чистый, build зелёный.
- Revert-check: **5 мутаций RED** — dry-run пишет; существующие не считаются skipped; verify-only
  применяет дельту; verify-only всегда рапортует равенство; архивные задачи не переносятся.
- CLI-обёртка собрана и проверена чтением аргументов (полный прогон — в runbook).

## Ограничения, записанные честно

- **Замер окна паузы на 100k не выполнен в этом инкременте** (сессионный бюджет; перенос 100k
  файлов — минуты). Переносится в Y-08b (там по плану и так проверка на 100k и runbook), а не
  заявляется здесь сделанным.
- Эксклюзивность — внутрипроцессный file-lock; для живого сервера нужен останов (runbook). Межпроцессная
  блокировка DATA_DIR сервером — существующий `storage-lock`, его подключение к CLI — Y-08b.
- Журнал событий/замки не переносятся (операционные данные, записано выше).
