# 2026-11-10 19:00 — T-01a: UserStore, scrypt-пароли и личные токены

- **Пункт:** T-01a (часть T-01, high)
- **Ветка / sha:** `feat/t01a-user-store`, от `origin/master` `a8c762d` (PR #362 влит)
- **Основание:** BACKLOG T-01; `DATA_DIR/auth.db`, `better-sqlite3`, MU-01, DX-16

## Вопрос

Как заменить единственного env-админа на хранилище пользователей с хешами и личными токенами так,
чтобы неверный пароль и неизвестный пользователь были неразличимы, отозванный/истёкший токен не
проходил, а env-админ остался bootstrap'ом?

## Решение

- `src/auth/user-store.ts`:
  - интерфейс `UserStore` + `SqliteUserStore` (`DATA_DIR/auth.db`, WAL);
  - пароли — scrypt (N=16 384, r=8, p=1, 64 байта, 16-байтовая соль), формат `scrypt$…`; plaintext
    не хранится и не возвращается;
  - `authenticate()` **всегда** считает scrypt — для неизвестного пользователя проверяется dummy-хеш,
    поэтому форма и текст ответа не различают «нет пользователя» и «неверный пароль»;
  - роли, disabled, смена пароля (инвалидирует все личные токены пользователя);
  - личные токены: случайный `mtk_…`, в БД только sha256 + prefix; name, expiresAt, revokedAt,
    lastUsedAt; `verifyToken()` отклоняет revoked/expired/disabled, `listTokens` не отдаёт plaintext;
  - `ensureBootstrapAdmin()` создаёт env-админа только если его ещё нет; существующий пароль не
    перезаписывается.
- `/auth/login` (`src/transport/login-route.ts`) принимает `userStore`: сначала проверяет store,
  затем env-пару как bootstrap; при отсутствии store поведение прежнее (env-only, fail-closed 503).
  JWT содержит роли пользователя; ответ — стабильный `user.id`.
- `setup.ts` открывает `auth.db` только если задан `JWT_SECRET`/`MCP_LOGIN_*`; HTTP-транспорт передаёт
  store в login handler. `.gitignore` уже покрывает `*.db`.

## Почему

- `auth.db` — локальный single-writer ресурс; better-sqlite3 уже в зависимостях, отдельная СУБД не нужна.
- Dummy-scrypt — единственный способ не выдавать существование пользователя по времени без сложной
  инфраструктуры; текст ответа одинаковый.
- Env-пара остаётся для первого входа/восстановления, но не является основным источником пользователей.
- Разделение на T-01a (хранилище + login) и T-01b (MCP-инструменты/админка, валидатор личных токенов
  в AuthManager) честно фиксирует, что UI-управление ещё не сделано.

## Ограничения, записанные честно

- MCP-инструменты управления пользователями/токенами и админ-UI — **не сделаны** (T-01b); в T-01a нет
  API-поверхности, кроме самого `UserStore` и `/auth/login`.
- Личные токены пока не подключены как `TokenValidator` к `AuthManager` — это T-01b; сейчас они
  проверяются `UserStore.verifyToken` и покрыты тестами.
- Формальная проверка равенства времени — через dummy-scrypt и одинаковый ответ; отдельного
  статистического timing-теста нет (он был бы флейки).
- `auth.db` уже исключён из backup/restore DX-16 без `includeSecrets`; отдельно менять не потребовалось.
