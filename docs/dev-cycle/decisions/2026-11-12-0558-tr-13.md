# 2026-11-12 05:58 — TR-13: upgrade-path e2e (schema 0 → 1)

- **Пункт:** TR-13 (low)
- **Ветка / sha:** `test/tr-13-upgrade-path`, от `origin/master` `a207e8c`

## Вопрос

Нужно доказать, что данные версии N читаются после «апгрейда пакета», и что это ловит то,
чего не покрывает schema-version. В этой среде нет старого бинарника пакета, поэтому границей
служит **schema 0 на диске + текущий dist**.

## Решение

- `tests/upgrade-path.test.ts`: создаёт DATA_DIR **без** `.schema-version` с задачей без `type`
  и документом в старом frontmatter-формате, запускает реальный `dist/index.js` по stdio.
- Проверяет `tasks_get`/`knowledge_get`, дефолт `type='task'`, тело документа и появление
  `.schema-version` со `schema: 1`.
- Schema-version no-op миграция 0→1 стампит манифест; чтение старых полей обеспечивают
  storage fallback + `withDefaultType`, а не миграция.

## Почему

- Реальный stdio-клиент проверяет boot-последовательность (checkSchemaVersion → storage read),
  а не только функции.
- Отсутствие манифеста — самый старый поддерживаемый layout; field-reshape для 0→1 нет, поэтому
  тест фиксирует именно совместимость чтения.

## Проверено

- `tests/upgrade-path.test.ts` — **1/1**, 3.2 s, реальный dist.
- `npm run build` — чисто.
- `npm run test:types` — чисто.
- backlog:check **371/27**.
- Мутация не заявлена: тест проверяет миграцию/чтение, но не отдельную ветку кода, которую можно
  точечно отключить без изменения schema-version. Это ограничение ниже.

## Ограничения

- Нет **старого артефакта пакета**: проверена schema 0 + текущий dist, а не N→N+1 с двумя
  бинарниками. Полевой reshape (если появится в будущей schema) этим тестом не покрыт.
- Один проект/одна задача/один документ; массовые layout'ы и shard-layout не входят.
- Schema-version 0→1 — no-op; тест не доказывает корректность будущих миграций.
- Нет теста отказа при `schema > CURRENT_SCHEMA` (это DX-18).

## Откат

Удалить `tests/upgrade-path.test.ts`; продовый код не менялся.
