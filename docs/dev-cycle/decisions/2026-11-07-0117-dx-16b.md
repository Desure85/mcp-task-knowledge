# DX-16b: admin_restore и ужесточение restoreBackup

**Дата:** 2026-11-07 01:17
**Задача:** DX-16b (`admin_restore` + hardening существующего `restoreBackup`), ADR-008
**Ветка:** `feat/dx16b-admin-restore` (worktree `/home/dm/work/mcp-tk-dx16b`)

## Вопрос

Как восстановить `DATA_DIR` из архива DX-16a так, чтобы восстановление не писало вне `DATA_DIR`,
не воскрешало отозванные токены, не оставляло «наложенные» файлы, переживало сбой посередине и не
конфликтовало со вторым процессом — и при этом не сломать старые каталог-снапшоты DX-19?

## Решение

- `admin_restore` (и `restoreArchive`) читает архив **только** `readBackupArchive` из DX-16a:
  до первой записи проверяются формат, версия, профиль, схема, все заголовки, типы, размеры,
  `sha256` и пути. Цель записи всегда вычисляется как `resolveUnderPath(DATA_DIR, entry.path)` —
  абсолютный `from` из манифеста не используется.
- По умолчанию `dryRun: true`: ответ `{dryRun, applyToken, creates, overwrites, deletes,
  warnings}`; ни файлов, ни lock-файлов не создаётся. Apply — только `dryRun: false` +
  `confirm: <applyToken>`; токен привязан к плану (пути/действия) и к архиву (путь, размер,
  `createdAt`), поэтому изменение `DATA_DIR` между dry-run и apply даёт
  `RESTORE_CONFIRM_REQUIRED`.
- Apply: `.restore.lock` (`fs.link`, pid/startedAt/host, стейл по мёртвому pid или 30 мин) +
  `withFileLock`, затем pre-restore снапшот `.backups/<ts>-pre-restore/` формата DX-19 **с
  секретами**, затем распаковка во временный `.restore-tmp/` и замена в пределах
  archived roots с prune. Сбой посередине → восстановление снапшота + удаление созданных путей
  вне снапшота; ошибка несёт `rolledBack`.
- Секреты (`.jwt-revoked.json`, `auth.db`) не входят в обычный архив и не восстанавливаются без
  `includeSecrets`. `.server.lock` и `.restore.lock` исключены и у writer'а, и у restore.
- Легаси `restoreBackup` переведён на тот же движок: `to` под `DATA_DIR`, симлинки пропускаются,
  секреты по флагу, prune по умолчанию, `dryRun` только строит план.
- CLI `dev-cli restore`: dry-run по умолчанию, `--confirm <token>`/`--yes`, `--no-prune`,
  `--include-secrets`; `export` удалён (Д6).

## Почему

- `entry.from` — недоверенный вход: манифест можно отредактировать, и запись пойдёт по
  произвольному абсолютному пути (Д1). Единственный безопасный источник цели — относительный `to`.
- Снапшот-наложение (Д4) откатывает отзыв токена и оставляет удалённые документы; DoD требует
  «документ после бэкапа удаляется при prune» и «отзыв токена не исчезает». Поэтому prune только
  под archived roots и секреты вне обычного restore.
- Токен подтверждения связан с планом, а не с «нажатием»: иначе между просмотром и apply данные
  меняются, и оператор подтверждает не то, что видел.
- Откат через собственный снапшот выбран вместо «отменить частичные записи вручную»: snapshot —
  единственный механизм, который уже умеет восстанавливать и файлы, и удаления.
- `.restore.lock` через `fs.link` — атомарная публикация: конкурент никогда не читает пустой файл
  (тот же приём, что в `scripts/lib/devcycle-state.mjs`).

## Проверено

Проба дефектов ДО кода (dist на `902d1e3`, временный `DATA_DIR` под `/tmp`): Д1-Д6 все
воспроизведены (Д1 запись вне `DATA_DIR`; Д2 симлинк сохранён/разыменован; Д3 секреты в снапшоте;
Д4 файл остался, отзыв откатился; Д5 нет `formatVersion`/`entries`; Д6 `export` пишет 0 файлов).

Тесты: `tests/dx16b-admin-restore.test.ts` (18) и `tests/dx16b-cli-restore.test.ts` (2);
`tests/data-backup.test.ts` (14) и `tests/dx16-backup-archive.test.ts` (21) остались зелёными.
Revert-check 20/20: точечная поломка кода → тест RED, восстановление → GREEN (таблица в отчёте
сессии).

## Откат

`git revert` коммита DX-16b. Совместимость: `admin_restore` — новый tool; `restoreBackup`
принимает прежний вызов `(backupDir, {dryRun})`, но теперь по умолчанию prune и не трогает
секреты. Архивы DX-16a читаются без изменений. Каталог-снапшоты DX-19 остаются восстановимыми.
