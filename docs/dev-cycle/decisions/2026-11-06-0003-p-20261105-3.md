# 2026-11-06 — P-20261105-3: хрупкие тесты (devcycle lock, BM25 perf) и pre-push на устаревшем dist

Основание: реестр пробелов P-3. (1) `tests/devcycle-state.test.ts:115` на selfcheck PR #262/#263
получил коды `[0,0]` вместо `[0,3]`, повторный прогон зелёный. (2) `tests/search-perf.test.ts` падал
при `npm run test:coverage` параллельно с другими процессами, в одиночку проходил. (3) `.husky/pre-push`
запускает полный vitest по собранному `dist`; 2026-11-05 устаревший dist (от 20 октября) дал 34 ложно
красных теста.

Решение:

1. Overlap-тест devcycle: `Promise.all` гарантирует одновременный spawn, но не перекрытие окон —
   при медленном старте второй тик приходил после `release` и получал 0. Заменено на барьер: ждём
   появления читаемого `lock.json` (pid + startedAt) и только затем запускаем второй тик; окно
   удержания поднято до 8 с; дополнительно проверяется, что второй тик увидел pid первого.
2. BM25 perf: один замер `Date.now()` заменён на прогрев + медиану трёх замеров; добавлена
   относительная проверка «стоимость на документ не растёт при росте корпуса в 5 раз» (не зависит
   от загрузки машины: обе стороны сравнения меряются под одним давлением). Абсолютные потолки
   4 с / 12 с сохранены как сеть для 10–20-кратной деградации. Между замерами — yield в event loop,
   иначе долгий синхронный поиск даёт `onTaskUpdate` timeout воркера vitest.
3. dist: `tests/support/dist-guard.ts` сравнивает mtime `dist/index.js` с самым свежим `src/**/*.ts`
   (tsc не инкрементальный — каждый build перезаписывает `index.js`) и бросает «dist устарел: выполни
   `npm run build`»; при отсутствии dist собирает сам под каталогом-локом (параллельные воркеры не
   запускают tsc одновременно). Гард подключён к `tests/e2e-full/harness.ts` и к каждому тесту,
   который спавнит `dist/index.js` напрямую. `.husky/pre-push` теперь вызывает `npm run build` перед
   vitest.

Почему: тест не должен проверять скорость старта процессов, загрузку CI или возраст build-артефакта —
только своё свойство. Барьер и медиана убирают зависимость от времени, относительная метрика — от
загрузки; потолки оставлены, потому что равномерную деградацию относительная метрика не видит.

Проверено (числа):

- devcycle, до: задержка старта 3 с при окне 1.5 с даёт `[0,0]` (2/2); под 2 ядрами с 4 busy-loop —
  `[0,0]` в 1 из 6 прогонов теста; 30 прогонов файла в той же нагрузке — 0 падений (редкость гонки).
  Корень найден и измерен: парный цикл acquire/hold — 36 двойных удержаний на 836 захватов, 38
  срабатываний «EEXIST + нечитаемый lock»; сценарий теста (одна попытка, окно 1500 мс) — 1 двойной
  запуск на 40 попыток (2.5%).
- devcycle, после: тест 30/30 зелёный под той же нагрузкой (2 ядра + 4 busy-loop); мутация продукта
  (acquireLock всегда возвращает ok) краснит тест.
- perf, до: под 2 ядрами + 12 busy-loop старый тест 10/10 красный (50k 7730–7955 мс при пороге 5000;
  при 20 busy-loop 10933–11605 мс против 5000 и 2406–2663 против 2000 для 10k).
- perf, после: 30 прогонов под той же нагрузкой (12 busy-loop, 2 ядра) — 0 падений, все 7 тестов зелёные в каждом прогоне;
  мутации: O(N) работы на документ краснит относительную проверку (0.295 против 0.212 мс/док,
  рост 4.2x > 3), 21-кратное равномерное замедление краснит потолки (4283 > 4000; 21396 > 12000).
- dist/pre-push, до: старый порядок хука при устаревшем dist — 47 файлов failed, exit 1, 25.9 с;
  на свежем dist — 271 файл / 3110 тестов passed, 49.8 с.
- dist/pre-push, после: на устаревшем dist хук собирает его сам и проходит — 271 файл / 3110 тестов
  passed, 56.8 с (+7 с на build). Гард падает за 0.9 с с понятным сообщением вместо 47 красных файлов;
  при отсутствующем dist собирает сам.
- Проверки: `npm run build`, `npm run test:types`, `npm run lint` (0 errors), `npm run lint:md`,
  `npm run backlog:check`, полный `npx vitest run` 3/3 (271 файл, 3110 тестов), `npm run e2e:full`
  (30 файлов, 122 теста).

Не сделано (вне разрешённого набора файлов): продуктовая гонка `acquireLock` в
`scripts/lib/devcycle-state.mjs` — неатомарное создание lock и трактовка нечитаемого lock как
устаревшего. Нужен отдельный пункт: создавать lock через временный файл + `fs.link` (атомарный
exclusive create) и считать нечитаемый свежий lock занятым (короткий grace), а не свободным.
