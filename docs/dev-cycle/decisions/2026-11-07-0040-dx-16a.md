# 2026-11-07 00:40, DX-16a: archiveBytes вне манифеста, манифест последней записью архива

Вопрос: в манифесте ADR-008 есть `stats.archiveBytes`, но манифест лежит внутри того же архива —
финальный размер gzip до закрытия потока неизвестен. Варианты: второй проход по данным, поле
фиксированной ширины или размер только в ответе инструмента.

Решение (владелец, 2026-11-07): `archiveBytes` из манифеста внутри архива убрать; размер готового
файла возвращают `admin_backup` и `dev-cli backup` по `stat` после `rename`. `stats.files`,
`stats.bytes` и добавленный `stats.dirs` остаются. Манифест пишется последней записью tar-потока —
иначе хеши и размеры перечисленных файлов ещё не вычислены. «В корне архива» означает путь, а не
позицию в потоке; reader находит манифест по имени.

Почему: второй проход удваивает I/O на `models/` (до 200 МБ), поле фиксированной ширины ломает
человекочитаемый JSON, а размер архива нужен вызывающему, не восстанавливающей стороне.

Проверено (ветка `feat/dx16a-admin-backup`): `tests/dx16-backup-archive.test.ts` — 21 тест, включая
`deterministic` (два прогона с одним `now` дают побайтно равные архивы) и `roundtrip`; на реальном
архиве — `gzip -t`, `tar -tzf`, распаковка системным `tar` и сверка `sha256` по манифесту; revert-check
каждого теста (21/21 RED при точечной поломке). `npm run build`, `npm run test:types`, `npm run lint`,
`npm run lint:md`, `npm run backlog:check`, `npm run docs:test` — exit 0; полный `npm test` — в отчёте.

Откат: revert коммитов ветки DX-16a. Вернуть `archiveBytes` в манифест можно только вместе с решением
о втором проходе (тогда меняется и порядок записей), поэтому откат поля — это откат всего DX-16a.
