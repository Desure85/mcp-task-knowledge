# 2026-11-13 17:40 — TK-05: команды, workflow-переходы, work items

- **Пункт:** TK-05 (low, был `blocked` на design)
- **Ветка:** `feat/tk-05-commands-workitems`, от `origin/master` `d6a1d1d`

## Вопрос

Как дать youtrack-подобные команды (`for me State Done`), проверять переходы через проектный
workflow и учитывать затраченное время, не ломая wire-формат и не открывая массовые
необратимые изменения?

## Решение

Реализован v1 по контракту `docs/design/tk-05-commands-workflow.md`:

- `tasks_command`: только `State <status>` и `for me State <status>`; фильтр минимум с одним
  предикатом; `dryRun=true` по умолчанию, `confirm:true` для записи; максимум 50 задач;
  переходы через `assertTransition`; последовательное применение с `applied/failed`;
  `expectedVersion` — per-task CAS; ошибки `COMMAND_SYNTAX`,
  `COMMAND_IDENTITY_REQUIRED`, `COMMAND_TOO_MANY`, `COMMAND_CONFIRM_REQUIRED`;
- `Task.workItems` (аддитивное поле) + `tasks_worklog_add` / `tasks_worklog_list`;
  `durationMin` 1..1440, `startedAt` ISO, сумма минут в списке;
- `for me` берёт `userId` из метаданных сессии; без auth — явная ошибка;
- `tasks_get`/storage отдают `workItems` как часть задачи, старые клиенты поле игнорируют.

## Почему

- Команда без фильтра могла бы перевести весь проект — поэтому обязательный предикат и лимит 50.
- `dryRun` по умолчанию + `confirm` дают предсказуемый двухшаговый сценарий.
- Work items не дублируют сумму в отдельном поле: `totalMinutes` вычисляется из массива.

## Ограничения

- Нет редактирования/удаления work item, таймера, ставок и кросс-задачных отчётов.
- Применение не транзакционное: частичный успех возвращается, не откатывается.
- `for me` зависит от `userId` в метаданных сессии; локальный stdio без auth его не даёт.
- UI-экрана нет; реальные проектные workflow с ограниченными переходами в тесте не поднимались
  (проверен сам вызов `assertTransition`, без отдельного e2e).
