## Вопрос

Спека MCP растёт (elicitation, sampling, roots, subscriptions, completion). Что сервер берёт,
что осознанно нет и как решать это в следующий раз?

## Решение

`docs/mcp-spec-frontier.md`:

- **Уже взято**: tools, resources (list/read/templates/subscribe), prompts (snapshot),
  logging/setLevel, tools list_changed.
- **Оценить**: `completion/complete` — объявлен в dispatch, handler отсутствует (SPEC-05).
- **Отклонено**: `elicitation` (server-initiated prompt блокирует агента), `sampling`
  (сервер не тратит модель клиента), `roots` (пути принадлежат `DATA_DIR`, не клиенту).
- **Правила adoption**: capability только с handler; ADR для изменения trust boundary;
  additive fallback; live-тест; ревью changelog при bump SDK; никаких пустых stub-handler'ов.

## Почему

- `roots`/`elicitation` меняют границу доверия; молчаливое включение опаснее отказа.
- `completion` без handler — уже дефект: capability не должна опережать реализацию.
- Матрица делает будущие споры дешевле: решение и причина записаны.

## Проверено

- Сверено с `src/register/setup.ts`: advertised `resources.subscribe`, `tools.listChanged`,
  `logging`; `completion` в dispatch, handler не найден.
- `markdownlint` зелёный; `backlog:check` — **412 done / 0 wip / 0 pending / 15 blocked / 1 deferred**.
- Код не менялся; сборка/тесты не требуются.

## Ограничения

- Design-only: feature-флаги не добавлены, `completion` остаётся нереализованным (SPEC-05).
- SDK может сам выставлять capability по зарегистрированным handler'ам; фактический wire
  проверяется отдельно, политика фиксирует намерение.
- Нет автоматического сравнения с upstream changelog — только процесс на bump.
