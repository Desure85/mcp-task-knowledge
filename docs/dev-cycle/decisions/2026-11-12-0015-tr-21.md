# 2026-11-12 00:15 — TR-21: единый IP-ключ AuthProtection

- **Пункт:** TR-21 (low)
- **Ветка / sha:** `fix/tr-21-auth-key-dedupe`, от `origin/master` `5562220`

## Вопрос

`AuthManager.authenticate()` ключует `AuthProtection` по IP (`clientKey` из `SessionManager.remote`),
а `SecurityStack` проверял/писал тот же `AuthProtection` по `sessionId`. Два инстанса/подхода давали
разные ключи: lockout после неудачных логинов не видел `mcp.authenticate`-вызовы, а проверка стека
создавала шумовые записи по сессиям.

## Решение

- `AuthManager.getClientKey(sessionId)` — публичный доступ к уже существующему IP-ключу
  (`ip:port` → `ip`, fallback `sessionId`).
- `SecurityStackCall.clientKey?`; `check()` и `recordAuthOutcome()` используют
  `clientKey ?? sessionId ?? 'anonymous'`.
- `auth-gate` при построении `secCall` передаёт `auth.getClientKey(sessionId)`, если AuthManager есть.
- Поведение без `clientKey` сохранено (fallback на sessionId) — обратная совместимость тестов/вызовов.

## Почему

- Один ключ = один lockout-счётчик: неудачные `mcp.authenticate` и последующие tool-calls с того же
  IP делят бюджет, свежий `initialize` его не сбрасывает.
- IP-ключ уже был каноном в `AuthManager` (AUD-13); унификация не меняет политику, только убирает
  дублирование.
- `getClientKey` не раскрывает токены/сессии — только сетевой идентификатор.

## Ограничения

- `auth-gate` использует публичный метод AuthManager; сторонние AuthManager-совместимые объекты без
  `getClientKey` сохраняют старое поведение (fallback).
- IP берётся из `SessionManager.remote`; за прокси это адрес прокси, а не клиента (как и раньше).
- `unix:`/`unknown` remote остаются как есть.

## Откат

Убрать `getClientKey`, поле `clientKey` и его использование в auth-gate/security-stack; удалить тест.
