# 2026-11-07 02:15 — MU-08: мост stdio → один http-сервер

## Вопрос

Как дать stdio-клиентам (IDE-расширения, агенты) доступ к единственному http-ядру, не поднимая
второй сервер на том же `DATA_DIR`, и что для этого реально умеет готовый `src/proxy/*` (P-001..P-004)?

## Решение

Команда `mcp-task-knowledge bridge --url <core> [--token <t>]` (env `MCP_PROXY_UPSTREAM`,
`MCP_PROXY_TOKEN`; `--proxy-upstream` — алиас `--url`) запускает `StdioBridge` (`src/proxy/shim.ts`):
stdio `McpServer` с зеркалом поверхности ядра (`ProxyMirror`) и HTTP-клиентом `ProxyBootstrap`.
Шим не поднимает хранилище и эмбеддинги, не берёт `.server.lock`, не требует `DATA_DIR`.
Токен передаётся и заголовком `Authorization` (`requestInit` у `StreamableHTTPClientTransport`),
и фактическим путём ядра — вызовом `mcp.authenticate` после каждого connect/reconnect.

`src/index.ts` грузит `AppContainer` динамически, поэтому `bridge` работает без `DATA_DIR`;
`doctor` не расширялся.

## Почему

- **Проба до кода** на живом ядре (`DATA_DIR=/tmp/mu08-probe/store`, `EMBEDDINGS_MODE=none`,
  `MCP_TRANSPORT=http`, порт от ОС) показала: `ProxyBootstrap.start()` проходит (`initialize`
  pre-auth), но `listTools()` сразу после connect возвращает
  `StreamableHTTPError 401: authentication required for 'tools/list' — call mcp.authenticate first`
  (`src/core/auth-gate.ts:152`, `PRE_AUTH_PROTOCOL_METHODS` — только `initialize`/`ping`).
  Значит зеркало получило бы 0 инструментов и мост был бы пустым.
- `ProxyBootstrap` вообще не использовал `config.auth.token` (не передавал `requestInit`), не имел
  downstream-listener (комментарий в `bootstrap.ts`: «Downstream listener is set up by the caller»)
  и не восстанавливал аутентификацию после `reconnect()`. Проба подтвердила: после `kill -9` ядра
  и `reconnect()` `tools/list` снова 401, пока не вызван `mcp.authenticate`.
- `ProxyForwarder` не связан с зеркалом, а его таймаут только логирует и не реджектит промис
  (`src/proxy/forwarder.ts:158-176`), поэтому flow control в мост не тянулся: транспортный уровень
  и так сериализован SDK, а починка таймаута — отдельный предмет, не MU-08.
- Запуск `node dist/index.js bridge --url …` без `DATA_DIR` падал на module load
  (`dist/config.js:80`: `DATA_DIR must be set`), потому что `src/index.ts` статически импортировал
  `AppContainer` → `src/config.ts:143`. Отсюда динамический импорт: доковый конфиг клиента
  `command: mcp-task-knowledge, args: [bridge, …]` не задаёт `DATA_DIR`.
- Отвергнутая альтернатива: `unix`-сокет / named pipe и второй слушатель в ядре — это AA-01,
  по поручению не трогается. Отвергнуто также добавление health-секции в `doctor`: DX-17 `doctor`
  — сканер целостности `DATA_DIR` без секций, расширение было бы новым деливераблом и ложным
  закрытием DX-11.

## Доработка (2026-11-07, после независимой проверки)

**Смерть родителя.** Было: `process.ppid === 1`. На машине владельца осиротевший шим переходит к
subreaper (`systemd --user`, ppid 3485), а не к pid 1, поэтому условие никогда не срабатывало.
Стало: `initialPpid` фиксируется при старте, интервал 1 с завершает шим (код 0), когда
`process.ppid !== initialPpid` — переподчинение и есть смерть родителя. Работает и там, где ppid
становится 1 (контейнер/CI), и там, где работает subreaper.

**Усиленные тесты.**

- (g): `expect(child.exitCode).toBe(BRIDGE_EXIT.AUTH)` плюс отдельно `expect(BRIDGE_EXIT.AUTH).toBe(4)`
  (публичный контракт) и проверка, что stdin клиента был открыт и клиент ничего не писал — отказ
  происходит на старте.
- (h) новый: bash-обёртка держит stdin шима открытым, `kill -9` обёртки → шим завершается ≤ 3 с
  (состояние читается из `/proc/<pid>/stat`, зомби считается завершённым; перед убийством ждём
  точный сигнал `stdio bridge ready`, иначе шим не успевает запомнить ppid).
- (i) новый: `--url .../mcp?probe=<токен>` при недоступном ядре → exit 3, токена нет ни в stdout,
  ни в stderr. Найден и закрыт реальный дефект: pino-лог `ProxyBootstrap` печатал URL с query
  целиком; добавлен `redactUrl()` (userinfo и query вырезаются) для всех логов и `health()`.

**Итог по M4 (`if (failed)` → `if (false)`).** После усиления (g) мутация остаётся эквивалентной
по наблюдаемому контракту: отказ ловит следующий слой (401 → зеркало получает 0 инструментов →
`bridge.ts` классифицирует «no tools» как auth-отказ и выходит с кодом 4). Это осознанно
избыточный слой: он даёт точное сообщение «invalid token» вместо «no tools». Тест (g) теперь
ловит мутацию контракта: `BRIDGE_EXIT.AUTH = 1` → RED (ожидается 4).

**Revert-check доработки:** `ppid === 1` → RED (h); `write()` без `redact` → RED (i);
`BRIDGE_EXIT.AUTH = 1` → RED (g); M4 → GREEN (эквивалентная мутация, см. выше).

## Доработка 2 (2026-11-07, по замечанию контролёра: тест (i) был вакуумным)

Контролёр показал: в (i) секрет в URL совпадал с настроенным токеном, а CLI вырезал именно
настроенный токен, поэтому тест не проверял редактирование URL. Пробы со сторонним секретом
подтвердили две утечки:

- `bridge: upstream unreachable: http://…/mcp?probe=SECRET-…` и `connected to <url>` печатали URL
  как есть — query-секрет попадал в stderr;
- при credentials в URL pino `err.message` трижды содержал `http://user:PASSWD@…`
  (`Request cannot be constructed from a URL that includes credentials: <url>`): поле `url`
  редактировалось, а `err` — нет.

Исправлено:

- все CLI-сообщения (`connected to`, `upstream unavailable (attempt …)`, `upstream unreachable`)
  проходят через `redactUrl` + `scrubSensitiveText`; сырой URL в текст больше не попадает;
- `--url`/`MCP_PROXY_UPSTREAM` с userinfo отвергается при разборе: exit 2, сообщение
  «credentials in the URL are not supported; pass the token via MCP_PROXY_TOKEN», без эха URL;
- `sanitizeError()` вырезает из `err.message`/`err.stack` любые URL (userinfo/query) и настроенный
  токен; применяется во всех `log.error`/`log.warn` с `err` в `ProxyBootstrap` и `StdioBridge`.
  Санитизация выполняется на месте, поэтому pino-формат (`type` и остальные поля) не меняется.

Тесты: (i) сторонний query-секрет → exit 3, секрета нет; (j) userinfo → exit 2, пароля нет;
(k) «connected to» при успешном коннекте с `?probe=SECRET` не содержит секрета; (l) pino-ошибка
на URL с credentials не содержит пароля. Revert-check: откат CLI-редактирования → RED (i,k);
снятие отказа userinfo → RED (j); снятие санитайзера err → RED (l).

Пробы контролёра до/после (тот же сценарий, сторонний секрет):
до — `query`: exit 3, `SECRET-Q-55555` в stderr; `userinfo`: exit 3, `PASSWD-LEAK-4242` в stderr
и в pino `err.message`; после — `query`: exit 3, секрета нет; `userinfo`: exit 2, пароля нет.
