# 2026-11-11 18:07 — SPEC-06: resources/subscribe + resources/updated

- **Пункт:** SPEC-06 (medium), зависит от SPEC-02
- **Ветка / sha:** `feat/spec-06-resources-subscribe`, от `origin/master` `a8024b6`

## Вопрос

Сервер объявлял `resources.subscribe: false` и не обрабатывал `resources/subscribe`/`unsubscribe`.
Клиент не мог узнать, что `tasks://current`, `knowledge://project/<id>` или `project://...` изменились,
кроме повторного `resources/read` по опросу. EventBus уже был, но моста к MCP-нотификациям не было.

## Решение

- `src/register/setup.ts`:
  - `resources: { subscribe: true, listChanged: ... }` в `SERVER_CAPS` и в
    `registerCapabilities({resources:{list,read,subscribe}})`.
  - Низкоуровневые `SubscribeRequestSchema`/`UnsubscribeRequestSchema` добавляют/удаляют URI в
    `resourceSubscriptions` (Set на экземпляр `McpServer` → per-session на HTTP/stdio).
  - `rawServer.registerTool` оборачивает gated-обработчик: после успешного вызова
    `notifyToolMutation(name)` шлёт `sendResourceUpdated({uri})` для подписок с префиксом:
    `tasks_` → `tasks://`, `knowledge_` → `knowledge://`, `project_` → `project://`.
  - Уведомляются только write-глаголы (`create/update/close/delete/archive/trash/restore/move/claim/
    renew/release/transition/set/add/remove/promote/write/import/start/complete/bulk`), поэтому list/get/search
    не создают ложных updated-событий.
- `docs/features/tools.md`: документация subscribe/unsubscribe и актуальный счётчик 154.

## Почему

- `resources/subscribe` — серверная возможность, а не инструмент; SDK уже умеет `sendResourceUpdated`.
- Set на сервер, а не глобальный: у HTTP каждый клиент имеет свою сессию и свой `McpServer`; глобальный Set
  слал бы уведомления чужим сессиям.
- Фильтр по write-глаголам вместо «любой tasks_*»: `tasks_list` не меняет ресурс, иначе клиент получал бы
  updated на каждый чтение.
- `resources/listChanged` не привязан к subscribe: список ресурсов меняется только при регистрации tool-
  resources, и этот флаг остаётся прежним.

## Проверено

- `tests/resource-subscribe.test.ts` — **2/2** на реальном `dist/index.js` через stdio:
  - `initialize` объявляет `resources.subscribe: true`;
  - subscribe `tasks://current` → `tasks_create` → `notifications/resources/updated` с этим URI;
  - unsubscribe → следующий create не даёт уведомлений за 300 мс.
- `protocol-version-e2e` 3/3 и `docs-tools-coverage` 6/6 — 11/11 вместе; build/tsc.
- `tests/e2e-full/listchanged.test.ts` обновлён: SPEC-04 проверял `subscribe` как false; теперь ожидает
  true (SPEC-06 реализовал возможность) — 3/3.
- **Мутация RED:** `notifyToolMutation` немедленно `return` — оба subscribe-теста падают; восстановление 2/2.

## Ограничения

- Уведомление отправляется после успешного возврата инструмента, но при `ok:false` (валидационная ошибка)
  обёртка всё равно может отправить updated; отдельной проверки конверта нет.
- `tools_run`/`tools_batch` не создают уведомлений: внешний вызов идёт как `tools_run`, а не как
  `tasks_create`; прямой client.callTool покрыт.
- Подписки живут в памяти сервера/сессии; перезапуск и TTL сессии их теряют.
- Порог «успешного write» — эвристика по имени; новый write-глагол вне списка не уведомит.
- Нет проверки, что URI существует: подписка на произвольную строку принимается, но никогда не сработает.
- HTTP/SSE и WebSocket-notifications не проверены отдельным e2e; stdio — реальный транспорт.

## Откат

Убрать handlers/capability/обёртку в `setup.ts`, тест и абзац docs; вернуть `subscribe: false`.
