## Вопрос

Какое поведение `tools_run`/`tools_batch` является контрактом **сегодня**, чтобы будущие изменения
(grouped/batch API) не сломали его незаметно?

## Решение

Добавлен `tests/tools-run-batch-contract.test.ts`, который вызывает зарегистрированные хэндлеры
напрямую через фейковый `ServerContext` (без сборки сервера и без dist), фиксируя:

- `tools_run`: порядок результатов = порядок `items`; последовательность исполнения (счётчик
  активных обработчиков и порядок вызовов); ошибка в середине пачки по умолчанию **не**
  останавливает остальные; `stopOnError: true` останавливает цикл после первого сбоя;
- `tools_batch`: параллельность через `Promise.all` доказана **барьером** — два обработчика
  одновременно активны, пока тест не отпустит барьер (без `sleep`); порядок результатов сохранён;
  `parallel: true` в ответе; в схеме **нет** `stopOnError`; `items` ограничен 1..50 (Zod), 51 — ошибка;
  смешанный успех/ошибка возвращает все результаты.

Нового кода и изменения wire-формата нет — только тест-спека.

## Почему

- Фейковый контекст делает тест быстрым и детерминированным; реальный серверный тест здесь не нужен.
- Барьер и счётчик активных обработчиков — единственный способ отличить `Promise.all` от
  последовательного цикла без временных задержек (DoD запрещает sleep).

- Тест фиксирует текущее поведение, а не желаемое: если контракт решат менять (группировка/батч),
  спека должна обновляться вместе с решением — это её цель.
- Транспортный уровень (Zod-валидация MCP SDK для верхнего уровня) не дублируется: тест проверяет
  схему напрямую и не поднимает сервер.
