# 2026-11-11 11:35 — TR-38: drain enforcement на session admission

- **Пункт:** TR-38 (medium), зависимость TR-08
- **Ветка / sha:** `feat/tr-38-drain-admission`, от `origin/master` `c75bf24`

## Вопрос

`HealthChecker.startDraining()` только выставлял флаг для `/readyz`; новые HTTP/TCP-сессии
продолжали создаваться. Как сделать drain настоящим admission-гейтом, не обрывая уже
установленные сессии?

## Решение

- **HTTP** (`src/transport/http-transport.ts`): после проверки существующей сессии и того, что
  POST содержит `initialize`, но **до** создания нового transport:
  - при `healthChecker.isDraining` → `503`, `Retry-After: 5`, JSON-RPC error `-32000`
    `Server is draining: no new sessions`;
  - запросы с известным `mcp-session-id` идут в `existing` ветку раньше этой проверки и продолжают
    обслуживаться.
- **TCP/Unix** (`src/transport/stream-transport.ts`):
  - `StreamTransportAdapter` принимает `HealthChecker` (базовый constructor);
  - `handleConnection` при draining пишет JSON-RPC error строкой и закрывает сокет **до** создания
    `McpServer`/SocketTransport;
  - фабрики `TcpTransportFactory`/`UnixTransportFactory` прокидывают `options.healthChecker`.
- `--health`/`/readyz` не менялись; сетевой слой не отдаёт новые сессии, существующие не трогаются.

## Почему

- Проверка в HTTP стоит после `existing` и после `isInitialize`, поэтому не блокирует GET/DELETE
  существующей сессии и не влияет на login/health/api маршруты.
- TCP-проверка в `handleConnection` — единственная точка, где создаётся сессия; отказ дешевле
  создавать McpServer и сразу рвать.
- `Retry-After` даёт клиенту/прокси явную подсказку, а не голый 503.

## Проверено

- `tests/transport-drain.test.ts` — **2/2**:
  - HTTP: `startDraining()` → initialize `503` + `Retry-After` + сообщение `draining`;
    `stopDraining()` → initialize больше не 503 (новые сессии снова принимаются);
  - TCP: `handleConnection` при draining пишет JSON-RPC error и вызывает `end` до создания сессии.
- build/tsc.
- **Мутация RED:** замена `if (this.healthChecker?.isDraining)` на `if (false)` в HTTP → тест
  краснеет; восстановление → 2/2.
- Существующие сессии: HTTP-ветка `existing` выполняется раньше drain-проверки (по коду); отдельный
  e2e с живой сессией не писался.

## Ограничения

- HTTP-тест не поднимает полноценную MCP-сессию; проверяется отказ на initialize и возобновление
  после `stopDraining`, а не long-lived SSE-сессия.
- TCP-тест проверяет admission-метод с fake-сокетом, не реальное TCP-соединение (сетевой тест был
  флейки на Windows: `address()`/close).
- Drain не прерывает in-flight долгие tool-вызовы; это ответственность graceful shutdown, не
  admission-гейта.
- `MCP_REALTIME` WebSocket upgrade не проверяет draining (realtime — отдельный канал).

## Откат

Revert ветки: удалить drain-блоки из HTTP/`handleConnection`, вернуть TCP/Unix-конструкторы без
`HealthChecker` и прокидывание в фабриках; `tests/transport-drain.test.ts` удаляется. `/readyz`
продолжит репортить 503, но новые сессии снова будут приниматься.
