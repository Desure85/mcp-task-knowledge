## Вопрос

Проверить конкурентные и аварийные сценарии: конфликт одного поля, слияние разных, массовая
операция всё-или-ничего, обрыв между записью и коммитом, второй писатель, авторство коммита.

## Решение

- `tasks_bulk_create`: при ошибке создания k-го элемента удаляются уже созданные элементы
  (`deletePermanent`) — частичного батча не остаётся.
- `tests/git-history-batch.test.ts`: восстановление enqueue после «обрыва» (close без flush → новый
  инстанс) и два писателя на одном `DATA_DIR`; автор коммита из `setAuthor`.
- `tests/bulk-per-item.test.ts`: падение второго элемента откатывает первый.
- Конфликт/слияние полей уже покрыты MU-02-тестами (`version`/`fieldVersions`).

## Почему

- File-профиль не имеет транзакций; компенсационное удаление даёт all-or-nothing для bulk create без
  изменения wire-формата. TR-37 per-item остаётся для bulk update/archive/trash (осознанный контракт).
- Durable queue — точка восстановления после kill: enqueue на диске, flush при старте.

## Проверено

- `tests/git-history-batch.test.ts` — **7/7** (recovery/два писателя/автор).
- `tests/bulk-per-item.test.ts` — **4/4** (rollback частичного batch).
- build чистый; `backlog:check` **388 done / 0 pending / 32 blocked / 1 deferred**.

## Ограничения

- «Kill -9» эмулирован `close()` без flush, а не реальным SIGKILL; durable queue проверена.
- Компенсация bulk create не защищает от падения процесса между create и rollback.
- Конфликт/слияние полей проверены на file-профиле; SQLite/PG — существующие ограничения MU-02.

## Откат

Убрать rollback в `tasks_bulk_create` и новые тесты; поведение вернётся к частичному batch.
