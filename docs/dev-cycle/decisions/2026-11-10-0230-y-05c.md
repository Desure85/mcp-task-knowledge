## Вопрос

Как эксплуатировать SQLite-профиль, а не только запускать: что должен показывать `doctor`, что делает
`reindex`, насколько профиль быстрее файлового на 100k и что делать с гейтом `sqlite-vec` в Docker?

## Решение

1. **`src/storage/profiles/sqlite/diagnostics.ts`** — два CLI-независимых инструмента (путь передаёт
   вызывающий, ADR-009 rule 1):
   - `inspectSqliteStorage(path)` — read-only снимок: версия схемы, `node/sqlite/fts5`, доступность
     `sqlite-vec` и его версия, счётчики коллекций (`tasks/docs/projects/vector rows/collections/fts`),
     состояние FTS-индекса (`projects/complete/dirty` + список dirty-проектов), размер файла и
     предупреждения: `sqlite-fts5-unavailable`, `sqlite-fts-dirty`, `sqlite-fts-drift` (строки FTS
     против канонических коллекций), `sqlite-vec-unavailable` (векторы работают через brute-force).
   - `rebuildSqliteStorageIndexes(path)` — `reindex`: пересобирает FTS по всем проектам, снимает
     dirty-флаги, делает `wal_checkpoint(TRUNCATE)`, возвращает метрики (`projects/indexed/ftsRows/
     dirtyBefore/sizeBefore→sizeAfter/durationMs`).
2. **`doctor`** при `STORAGE_PROFILE=sqlite` добавляет секцию SQLite (счётчики, runtime, vec, schema) и
   превращает предупреждения инспекции в обычные `issues`; `--json` отдаёт `sqlite` объект.
   **`reindex`** при SQLite-профиле обслуживает БД вместо `metadata.db`: `--verify` печатает
   предупреждения и возвращает exit 1 при их наличии, обычный запуск пересобирает FTS и печатает
   метрики (или `--json`).
3. **Бенчмарк `scripts/storage-bench.mjs`** (и `npm run bench:storage`): одинаковый сценарий на file
   и sqlite — create/list/первая страница/get/update, `--count`, `--profile`, `--ops`, `--json`.
   Замеры ниже.
4. **Найден и исправлен O(n²) при записи FTS:** `search_fts` удалял строку по `(store,kind,project,id)`,
   а это UNINDEXED-колонки — SQLite сканировал весь FTS-индекс на каждую мутацию. На 10k sqlite-create
   это давало **35.9 с**, на 100k прогон не укладывался в бюджет сессии. Добавлена карта rowid
   `search_fts_keys(store,kind,project,id,rowid)` (схема v6): удаление теперь идёт по rowid, ключ
   обновляется при upsert, чистится при delete/архивации/удалении проекта. После исправления:
   10k create — **5.5 с** (было 35.9), 100k create — **99.7 с** (полный прогон завершается).
5. **Гейт `sqlite-vec` в Docker:** выполнить не удалось — Docker CLI установлен, но демон в среде
   недоступен (`failed to connect to the docker API at npipe://…dockerDesktopLinuxEngine`). Это
   записано как ограничение среды, а не как «проверено»: Node-гейт (`tests/sqlite-vec-gate.test.ts`)
   зелёный, `sqlite-vec` — npm-пакет с prebuilt-бинарниками, поэтому в контейнерном образе он
   проверяется тем же тестом при наличии Docker; отдельный Docker-шаг остаётся за инфраструктурой.
6. **Документация:** [`docs/features/storage-profile-sqlite.md`](../../features/storage-profile-sqlite.md)
   (включение, что где хранится, диагностика/обслуживание, бенчмарк, ограничения) + строка
   `STORAGE_PROFILE` в `docs/getting-started/configuration.md`.

## Почему

- Диагностика — часть профиля (ADR-009), а не серверного кода: `doctor`/`reindex` получают данные
  через функции, которые можно тестировать без CLI и которые не тянут config.
- Бенчмарк был обязан найти O(n²): это именно то, зачем Y-05c существует; после исправления цифры
  изменились на порядок, и без замера фикс было бы нечем подтвердить.

## Бенчмарк

Машина: Windows, Node 24.22.2, локальный SSD; одинаковый сценарий, однопоточный цикл, без прогрева
(абсолютные числа — не throughput-гарантия, сравнение — смысл замера).

10 000 задач (`node scripts/storage-bench.mjs --count 10000`, после FTS-фикса):

| операция | file (ms) | sqlite (ms) | sqlite быстрее |
|---|---:|---:|---:|
| create (по одной) | 22 720 | 5 455 | 4.2× |
| list (100k?) — весь проект (10k) | 687 | 30 | 23× |
| первая страница 100 | 230 | 22 | 10.7× |
| get ×200 | 64 | 3 | 23× |
| update ×100 | 223 | 92 | 2.4× |

100 000 задач:

| операция | file | sqlite |
|---|---:|---:|
| create (по одной) | 231 267 ms (≈3.9 мин) | 99 747 ms |
| list всего проекта | не замерено (см. ограничения) | 302 ms |
| первая страница 100 | не замерено | 325 ms |
| get ×200 | не замерено | 8 ms |
| update ×100 | не замерено | 259 ms |

До FTS-фикса sqlite create на 10k занимал 35 902 ms (в 6.6 раза медленнее сегодняшнего), а полный
100k-прогон выходил за 40-минутный бюджет сессии — то есть O(n²) был воспроизводимым фактом, а не
теоретическим опасением.

## Ограничения, записанные честно

- **Docker-гейт `sqlite-vec` не выполнен:** демона Docker в среде нет; Node-гейт зелёный, пакет
  поставляется с prebuilt-бинарниками. Проверка в образе остаётся инфраструктурным шагом.
- **100k file-read операции не замерены:** полный file-прогон на 100k (list/page/get/update поверх
  100k JSON-файлов) не уложился в бюджет сессии; отдельно измерен только create (231 с). Это само по
  себе показательно (файловый list на 100k — минуты против 0.3 с у SQLite), но в таблице отмечено как
  неизмеренное, а не оценено «на глаз».
- **create измеряется по одной записи**, без bulk-API: сценарий отражает текущий `create` инструмент,
  а не потенциальный batch.
- Промпты и память в SQLite-профиле остаются файловыми (решение Y-05a3); `ProjectInfo.paths` пуст
  (ADR-009 цель — убрать поле отдельным изменением wire-контракта).
