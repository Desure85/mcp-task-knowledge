## Вопрос

`tasks_list` и `knowledge_list` на 100k занимают 1118 и 1247 мс (медиана, HTTP MCP, master
`969a5f5` с уже влитым SC-01) и обе делают `readdir` + `stat` по всем файлам проекта. Любой
содержательный фильтр (`status`, `tag`) или `countOnly` дополнительно читает и парсит **все**
файлы: 2.2–2.6 с и 2.0 GB RSS на 100k. Холодный page cache делает это неинтерактивным
(`scale-2026-10.md` §3.5: 1000 файлов из 100k холодными — 25.8 с).

Нужно: убрать O(N)-скан листингов, сохранив файлы источником истины и не сломав SC-01-контракт
(`fields`, `maxBytes`, курсор `(updatedAt desc, id)`, `countOnly`, стабильные коды ошибок).

## Решение

Файловый профиль получает **производный** SQLite-индекс метаданных:

- один файл на `DATA_DIR`: `DATA_DIR/.index/metadata.db` (better-sqlite3, WAL);
- строки `tasks` и `docs` + нормализованные таблицы тегов + служебная `projects` + `meta`;
- обновление — **в той же критической секции**, что запись файла: сначала файл (истина), затем
  upsert строки; падение между ними делает индекс отставшим, но не портит данные;
- чтение листингов идёт по индексу (id + путь + ключ страницы), содержимое читается только для
  страницы;
- индекс **никогда не источник истины**: ошибка/повреждение/несовпадение версии схемы → индекс
  отключается (fallback на файловый скан) или перестраивается, мутация из-за индекса не падает;
- перестройка — явная команда и `doctor`; «сверка при старте» — ленивая, O(проектов), полная
  проверка — по явному запросу.

Цель DoD достигается с запасом: 100k страница — 0.69 мс (задачи) и 1.42 мс (документы) против
1138 и 1381 мс файлового пути, включая чтение 50 файлов страницы (замеры §3).

## Схема и совместимость с SC-01

```sql
PRAGMA journal_mode = WAL;          -- читатели не блокируют писателя, перестройка не «стопит» листинги
PRAGMA synchronous = NORMAL;        -- индекс производный: потеря последних транзакций лечится сверкой
PRAGMA busy_timeout = 5000;
PRAGMA temp_store = MEMORY;
PRAGMA wal_autocheckpoint = 1000;

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL) WITHOUT ROWID;
-- ключи: schema_version, data_dir (абсолютный путь — защита от переноса файла БД), built_at, dirty

CREATE TABLE tasks (
  id          TEXT PRIMARY KEY,
  project     TEXT NOT NULL,
  status      TEXT NOT NULL,
  priority    TEXT,
  type        TEXT NOT NULL DEFAULT 'task',
  parent_id   TEXT,
  updated_at  TEXT,                 -- поле файла (для updatedSince и сортировки старых consumers)
  mtime_ms    REAL NOT NULL,        -- ключ страницы SC-01: ровно fs.stat().mtimeMs, без округления
  archived    INTEGER NOT NULL DEFAULT 0,
  trashed     INTEGER NOT NULL DEFAULT 0,
  rel_path    TEXT NOT NULL         -- путь относительно DATA_DIR: оба layout'а + будущее шардирование SC-06
) WITHOUT ROWID;
CREATE INDEX idx_tasks_page        ON tasks(project, mtime_ms DESC, id ASC);
CREATE INDEX idx_tasks_status_page ON tasks(project, status, mtime_ms DESC, id ASC);
CREATE INDEX idx_tasks_type_page   ON tasks(project, type, mtime_ms DESC, id ASC);
CREATE INDEX idx_tasks_parent_page ON tasks(project, parent_id, mtime_ms DESC, id ASC);
CREATE INDEX idx_tasks_priority    ON tasks(project, priority, mtime_ms DESC, id ASC);

CREATE TABLE task_tags (task_id TEXT NOT NULL, tag TEXT NOT NULL, PRIMARY KEY (task_id, tag)) WITHOUT ROWID;
CREATE INDEX idx_task_tags_tag ON task_tags(tag, task_id);

CREATE TABLE docs (
  id          TEXT PRIMARY KEY,
  project     TEXT NOT NULL,
  title       TEXT,
  type        TEXT,
  parent_id   TEXT,
  trust_level TEXT,
  updated_at  TEXT,
  mtime_ms    REAL NOT NULL,
  archived    INTEGER NOT NULL DEFAULT 0,
  trashed     INTEGER NOT NULL DEFAULT 0,
  rel_path    TEXT NOT NULL
) WITHOUT ROWID;
CREATE INDEX idx_docs_page        ON docs(project, mtime_ms DESC, id ASC);
CREATE INDEX idx_docs_type_page   ON docs(project, type, mtime_ms DESC, id ASC);
CREATE INDEX idx_docs_parent_page ON docs(project, parent_id, mtime_ms DESC, id ASC);
CREATE TABLE doc_tags (doc_id TEXT NOT NULL, tag TEXT NOT NULL, PRIMARY KEY (doc_id, tag)) WITHOUT ROWID;
CREATE INDEX idx_doc_tags_tag ON doc_tags(tag, doc_id);

CREATE TABLE projects (
  project      TEXT PRIMARY KEY,
  dir_mtime_ms REAL NOT NULL,
  file_count   INTEGER NOT NULL,
  synced_at    TEXT NOT NULL
) WITHOUT ROWID;
```

Почему именно так:

- **`mtime_ms REAL`, а не `updated_at`** — контракт SC-01 уже выстроен вокруг mtime: `listTaskEntries`
  сортирует по `mtimeMs desc, id asc` (`src/storage/tasks.ts:145-156`), курсор несёт
  `String(mtimeMs)` как `k` (`src/utils/pagination.ts:116-136`). `updated_at` из файла — другое
  значение (может быть равен mtime только при записи через `writeJson`, но не после правки файла
  руками и не после claim, см. ниже). Сортировать по `updated_at` значит поменять порядок и
  инвалидировать выданные курсоры. Хранится `REAL` без округления, чтобы `String(value)` из
  better-sqlite3 совпадал с `String(fs.stat().mtimeMs)` байт-в-байт: курсор, выданный файловым
  путём, обязан приниматься индексным и наоборот (переключение `STORAGE_INDEX=off/on` не должно
  ехать по страницам).
- **`rel_path`**, а не вывод пути из `project`+`id` — иначе legacy-раскладка
  (`resolveTasksDir`, `tasks.ts:130-135`) и шардирование SC-06 ломают чтение страницы.
- **Теги отдельной таблицей** — фильтр `tag=` становится индексным (`tag, task_id`), а не `LIKE`
  по JSON; тегов в наборе 100k — 193 481 строка, ~2 мс на фильтр с чтением страницы.
- **`archived`/`trashed` в строке** — это фильтры по умолчанию в обоих листингах
  (`taskPasses`, `tasks.ts:190-200`; `docPasses`, `knowledge.ts:158-165`), их нельзя вынести за
  индекс без чтения файла.
- **`WITHOUT ROWID`** на маленьких/узких таблицах — запись 0.18 мс и компактность; на `tasks`/`docs`
  тоже допустимо (PK — текстовый id, вторичные индексы несут PK), замерено 134 MB на 200k.

**Эквивалентность результата.** Индекс — «искатель»: он возвращает `id`, `rel_path`, `mtime_ms`, а
содержимое страницы читается из файлов и проходит те же пост-обработчики, что сегодня
(`withoutExpiredClaim`, `withDefaultType`). Поэтому expired-claim по-прежнему скрывается на
чтении, `type` без поля по-прежнему `task`, а содержимое всегда свежее файла.

**Одно намеренное изменение поведения:** `total`/`totalExact`. Сегодня быстрый путь отдаёт
`total = число файлов проекта` (архив и корзина включены) с `totalExact: false`
(`tasks.ts:265-271`). Индексный путь считает **точный** отфильтрованный `total` и ставит
`totalExact: true`; `hasMore` — по `LIMIT n+1` вместо «читаем ещё один». Это улучшение, а не
регресс, но оно фиксируется тестом: `total` в индексном и файловом путях совпадает только на
фильтрах без архив/корзины, и это записано в DoD SC-02c как ожидаемое расхождение.

## Критическая секция записи

Порядок и владение:

1. **Файл** — `writeJson`/`writeText` (атомарно: tmp + rename, `src/fs.ts:30-41`, `:85-95`).
2. **`fs.stat(file)`** — взять фактический `mtimeMs` (mtime tmp-файла сохраняется при rename;
   вычислять его из `Date.now()` нельзя — округление ФС и задержка дадут расхождение с
   `listTaskEntries`).
3. **Upsert строки** + пересборка тегов этой строки (`DELETE`+`INSERT` внутри одной транзакции).

Всё это — внутри уже существующего лока записи: `withFileLock('workflow:<project>')` для
create/update задач (`tasks.ts:72`, `:554`) и `withFileLock('doc:<project>/<id>')` для документов
(`knowledge.ts:257`). Новый лок не вводится — иначе появится второй порядок и дедлок.

**Падение между (1) и (3).** Файл записан, индекс отстал: строка отсутствует или старая.
Последствия и лечение:

- содержимое страницы читается из файла → пользователь не видит старых данных;
- порядок/фильтр могут быть неверны ровно для этой записи до первой сверки;
- страница при чтении сама сверяет `mtime` файла со строкой индекса и чинит совпавшие строки
  (self-heal, §6), `doctor` показывает остаток, `reindex` лечит целиком.

**Ошибка индекса не валит мутацию.** Если upsert упал (SQLITE_BUSY после `busy_timeout`, ENOSPC,
повреждение), файл уже записан — это истина. Решение: писать `meta.dirty = 1`, логировать
`warn`, вернуть успех мутации. Альтернатива (откатывать файл или возвращать ошибку) отвергнута:
получился бы отказ в записи задачи из-за кеша. `dirty` заставляет `doctor`/`reindex` и следующую
сверку проекта отработать явно.

**Claim/renew/release.** `persistClaim` (`tasks.ts:420-425`) перезаписывает файл целиком и меняет
mtime, **не меняя** `updatedAt`. Это важно: в текущем файловом пути листинг сортируется по mtime,
поэтому claim уже поднимает задачу в начало списка. Индекс обязан вести себя так же — upsert в
`persistClaim` обязателен, иначе индексный путь и файловый разойдутся в порядке.

## Сверка при старте, внешние правки, `doctor`, `reindex`

Полный `readdir`+`stat` на старте — это ровно та O(N), которую убирает SC-02 (100k: 83 мс только
`readdir`+count, 1.1 с со `stat`, 6.9/11.9 с с разбором). Поэтому:

1. **Старт (boot):** открыть БД, проверить `meta.schema_version` и `meta.data_dir`.
   Стоимость 0.3 мс, не зависит от N. Если версия схемы другая или `data_dir` не тот — индекс
   удаляется и строится заново (производный, терять нечего). Если открыть нельзя — `STORAGE_INDEX`
   выключается на процесс, все листинги идут файловым путём, в лог `warn`.
2. **Ленивая сверка:** страница уже читает свои 50 файлов; для каждой строки сравнивается
   `mtime` файла со строкой индекса, расхождение → upsert этой строки. Так «правка файла руками»
   исправляется там, где она видна (внутри страницы), без O(N).
3. **Сигнал «каталог проекта менялся»:** `projects.dir_mtime_ms` обновляется после каждой
   серверной записи. `stat` каталога — 0.02 мс. Использовать его как автоматический триггер
   пересканирования нельзя: `writeJson` пишет tmp в тот же каталог и делает rename → mtime
   каталога меняется на каждой записи, любая запись вызывала бы полный rescan проекта при
   следующем чтении. Поэтому `dir_mtime_ms` служит только диагностикой в `doctor`.
4. **`doctor`** (`node dist/index.js doctor --data <dir>`, `src/cli/doctor.ts`) получает секцию
   `index`: строк в индексе, файлов, расхождения по `mtime`/`size` в выборке, сироты (строка без
   файла), пропуски (файл без строки), `dirty`, версия схемы. Расхождения — `warn`, не `error`:
   индекс лечится, данные целы. `doctor --fix` **не** трогает индекс (он не данные); отдельный
   флаг `--reindex`.
5. **`reindex`** — CLI-подкоманда по образцу `doctor` (`src/index.ts:21-45`):
   `node dist/index.js reindex [--project <p>] [--verify] [--force]`. Полная перестройка O(N),
   построение пачками по 2000 строк в транзакции, RSS ≤ ~250 MB на 100k (прототип держал всё в
   памяти — это его артефакт, не требование). `--verify` — сверка без записи, печатает сводку.
6. **После миграции файловой схемы** (`checkSchemaVersion` вернул `applied.length > 0`,
   `src/core/app-container.ts:380`) — индекс перестраивается: миграции вправе переписать файлы.

## Перестройка, версия схемы, откат

- **Версия:** `meta.schema_version`. Несовпадение → drop + rebuild (данные не читаются).
  SC-03 добавит FTS5-таблицы шагом версии 2 в том же файле.
- **Перестройка:** `reindex`; автоматически — при несовпадении версии, при `data_dir` mismatch,
  после файловых миграций. Инкрементально — upsert на каждой мутации.
- **Откат:** удалить `DATA_DIR/.index/` (включая `-wal`, `-shm`); либо `STORAGE_INDEX=off`.
  Данные не трогаются, файлы остаются истиной. Это же — процедура при повреждении БД
  (`SQLITE_CORRUPT` → `STORAGE_INDEX=off` на процесс + rebuild при следующем старте).
- **Бэкап:** `.index/` — производное, в бэкап не включается (рядом с `.embeddings`/`.emb_cache`,
  `src/services/data-backup.ts:210`); после восстановления — `reindex`. `admin_backup`/`admin_restore`
  (ADR-008) в этой ветке отсутствуют; при их появлении — то же правило.

## Профили хранилищ (Y-01, Y-02, Y-05, Y-06)

По решению Y-09 источник правды — активный провайдер. Значит:

- **files** — файлы источник, индекс производный (этот документ).
- **sqlite / postgres** — источник сама база, отдельный индекс метаданных не нужен вовсе.

Так как Y-02 (вынос `Store` за интерфейсы) ещё `pending`, SC-02 вводит **внутренний** интерфейс
`MetadataIndex` (`open/close/upsertTask/deleteTask/upsertDoc/deleteDoc/listTasks/listDocs/count/
rebuild/verify`) и единственную реализацию `SqliteMetadataIndex` (файловый профиль). Создание
индекса — в одном месте (`AppContainer.init` после `checkSchemaVersion`), флаг
`STORAGE_INDEX` (`auto`/`off`) (`auto` = включён только для файлового профиля). Когда придёт Y-02,
`listTasksPage`/`listDocsPage` станут методами файлового профиля, а `MetadataIndex` — его
внутренней деталью; профили sqlite/postgres просто не создают его. Переделки «выбросить и
написать заново» не будет, если интерфейс ограничить этими девятью методами.

**Риск порядка работ:** SC-02 идёт раньше Y-02 (в бэклоге SC зависит от SC-01, Y-02 не в
зависимостях). Это осознанно: gate R7 красный, надёжность и масштаб важнее, а индекс нужен и
самому Y-02 (файловому профилю он всё равно нужен). Альтернатива «сначала Y-02, потом SC-02»
отвергнута: Y-02 — рефакторинг без поведенческого выигрыша, и он растянет красный гейт.

## Блокировка DATA_DIR (`SERVER_LOCK`)

`SERVER_LOCK` в репозитории **отсутствует**: `rg SERVER_LOCK src scripts` — пусто; межпроцессная
блокировка `DATA_DIR` — это MU-01 (`pending`). Сегодня `withFileLock` — in-process `Map`
(`src/fs.ts:43-64`), два сервера на одном каталоге не координируются.

Следствие для SC-02: **новый lock не вводится** (это был бы MU-01 под другим именем).
Многопроцессная безопасность обеспечивается самой SQLite:

- WAL + `busy_timeout=5000` — параллельные записи из двух процессов сериализуются в БД;
- порядок «файл → индекс» в каждом процессе свой, поэтому два процесса могут дать отставшую
  строку — её лечит self-heal/`doctor`/`reindex`;
- когда MU-01 появится, взятие `SERVER_LOCK` ставится перед инициализацией индекса и перед
  `reindex` (одна строка в `AppContainer.init` и в CLI), больше ничего не меняется.

## Почему

- **Почему индекс, а не «ещё оптимизировать файловый скан».** Скан — это O(N) `open`+`parse` на
  каждый листинг: `stat` 100k стоит 1.1 с, любое содержательное поле требует чтения файла
  (2.2–2.6 с). Ни кэш, ни конкурентность это не убирают; убирает только отдельная структура,
  которую можно читать по B-tree.
- **Почему файлы остаются истиной.** Решение владельца Y-09: в файловом профиле источник — файлы.
  Отсюда порядок «файл → индекс», отсутствие обратной записи, откат удалением индекса и
  self-heal/`reindex` вместо доверия индексу.
- **Почему `mtime`, а не `updated_at`.** Контракт SC-01 уже на mtime: порядок
  `(mtimeMs desc, id asc)` и курсор `{k: String(mtimeMs), id}`. Сортировка по `updated_at` изменила
  бы порядок (claim и правка файла руками меняют mtime, но не `updatedAt`) и сломала бы выданные
  курсоры.
- **Почему лучше-`better-sqlite3`.** Уже в зависимостях и уже используется (`fts-search.ts`,
  `migration-framework.ts`), синхронный API без моста в event loop; `node:sqlite` в Node 22 требует
  `--experimental-sqlite`, а `engines` допускает Node 22.
- **Почему один файл индекса.** Кросс-проектные листинги, счётчики и поиск идут одним запросом;
  одна версия схемы, одна команда `reindex`, один WAL. Per-project дал бы N соединений и N версий
  при том же объёме данных.
- **Почему WAL.** Перестройка проекта не блокирует чтения, запись 0.18 мс, а потеря последних
  транзакций при отключении питания лечится сверкой — индекс производный, `synchronous=NORMAL`
  достаточен.
- **Почему ошибка индекса не валит мутацию.** Иначе кеш становится точкой отказа записи задачи;
  файл уже записан и является истиной, поэтому фиксируется `meta.dirty` и `warn`, а не отказ.
- **Почему `total` становится точным.** Быстрый файловый путь отдаёт число файлов проекта
  (архив/корзина включены) с `totalExact: false`; индексный может посчитать точный отфильтрованный
  `total` за 0.4 мс (1k), 6 мс (10k) и 117 мс (100k без частичного индекса; с ним ожидается единицы мс). Это улучшение контракта,
  а не регресс, и оно закреплено тестом.
