# 2026-11-11 08:00 — UI-37: полная страница задачи `/tasks/<id>`

- **Пункт:** UI-37 (high); закрывает основу для UI-36 (быстрый просмотр)
- **Ветка / sha:** `feat/ui-37-task-page`, от `origin/master` `d12c577` (PR #375 влит)
- **Основание:** BACKLOG UI-37; UI-10/UI-12/UI-34/V-02/U-01

## Вопрос

Как дать задаче прямой URL, переживающий reload, с правкой полей, графом переходов V-02,
claim-арендой U-01 и destructive-архивом/корзиной — не дублируя проверки статусов на клиенте?

## Решение

- `web-ui/app/tasks/[id]/page.tsx` (client, `useParams`): грузит текущий проект, `tasks_get`,
  статусы/переходы/типы, `tasks_dag` (рёбра для «зависит/блокирует») и `tasks_get_children`
  (подзадачи).
- Правка: title, description, priority, type, tags, links, status, dependsOn через
  `tasks_update`; сервер остаётся владельцем V-02. При `TRANSITION_NOT_ALLOWED` страница показывает
  **код**, сообщение и серверный `hint` с `allowed from …`.
- U-01: активная аренда (session/client/expiresAt), Claim / Renew / Release; после renew срок виден.
- Архив и корзина — destructive `Dialog` с подтверждением, затем переход на `/tasks`.
- Прямой URL, reload, loading, error и 404-подобное состояние (`Task not found`, ссылка назад);
  ровно один `h1` через `PageHeader`; ссылки на зависимости/подзадачи ведут на их `/tasks/<id>`.
- `api-client`: типы `claim/dependsOn/archived/trashed`, `tasks.claim/renew/release`,
  `bulkArchive/bulkTrash/bulkRestore`; `tasks.getChildren` исправлен на реальный контракт
  `{parent, children}` (до этого тип обещал массив — UI-37 поймал это падением рендера).
- `TaskCallError` теперь несёт серверное поле `allowed` (top-level), не только `details`.

## Почему

- Единственный источник истины для переходов — серверный workflow; клиент показывает ошибку, но не
  изобретает «разрешённые» переходы.
- `tasks_dag` уже отдаёт корректное направление `from=задача → to=зависимость`, поэтому «блокирует» —
  это рёбра с `to === id`; не нужно перебирать все задачи.
- Архив/корзина используют существующие `tasks_bulk_*` на один id, а не новые wire-инструменты.

## Ограничения, записанные честно

- «История изменений» показывает createdAt/updatedAt и честно пишет, что version history не входит в
  wire-формат задачи; отдельного task-history инструмента нет.
- **SQLite-профиль**: `project_transitions_set` пишет метаданные в SQLite-проект, а
  `loadProjectWorkflow` читает файловые метаданные, поэтому на демо-SQLite кастомный граф переходов
  не применяется к `tasks_update` (на файловом профиле/CI тест зелёный). Это pre-existing разрыв
  профиля, не замаскирован; вынесен в ограничения и требует отдельного пункта.
- `tasks_dag` по умолчанию отдаёт страницу (до 200 узлов); рёбра/названия за её пределами не видны.
- UI-36 (быстрый просмотр) ещё не сделан: кнопка Edit с этой страницы в диалог не подключена, пока
  нет UI-36.
- Скриншоты сняты на локальном Chrome; в CI тест их перезаписывает, но не сравнивает.
