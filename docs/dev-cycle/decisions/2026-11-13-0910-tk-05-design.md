## Вопрос

Как должны работать youtrack-подобные команды (`for me State Done`), правила workflow поверх
графа переходов и work items, не зафиксировав в wire-формате догадки до реальных пользователей?

## Решение

`docs/design/tk-05-commands-workflow.md`:

- v1 команды — только `State <status>` и `for me State <status>`; фильтр + `dryRun=true` по
  умолчанию, `confirm:true` для записи, максимум 50 задач;
- переходы проверяются существующим `workflow.transitions`/`assertTransition`, без второго DSL;
- ошибки `COMMAND_SYNTAX`, `COMMAND_IDENTITY_REQUIRED`, `COMMAND_TOO_MANY`,
  `TRANSITION_NOT_ALLOWED`, `CONFLICT`; частичный успех возвращается списками `applied/failed`;
- work items — аддитивное `Task.workItems`, `durationMin` целым числом, сумма в `tasks_get`;
  без ставок/таймеров/отчётов в v1;
- открытые вопросы (identity без auth, selection, partial failure, округление, billing) — за
  владельцем/реальными пользователями.

## Почему не реализуем сейчас

Сам пункт говорит: дорогое начинается после первых реальных пользователей. Реализация сейчас
заморозила бы в контракте догадки про `for me` при выключенном auth, выбор задач и округление
времени. Поэтому **никакой tool не регистрируется**, клиенты ничего не ломают; статус остаётся
`blocked` до появления реального проекта с кастомными переходами.
