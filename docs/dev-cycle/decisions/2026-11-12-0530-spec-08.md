## Вопрос

MCP-клиент не может управлять уровнем логов сервера: `logging/setLevel` не принимался,
capability `logging` не объявлялась. Нужно прокинуть уровень в pino для отладки удалённых
подключений.

## Решение

- `src/core/logger.ts`: `mapMcpLogLevel` и `setLogLevel`; MCP→pino:
  `debug→debug`, `info/notice→info`, `warning→warn`, `error→error`,
  `critical/alert/emergency→fatal`; неизвестный уровень — ошибка.
- `src/register/setup.ts`: до регистрации обработчиков объявляется `logging: {}` (merge с
  `resources.subscribe`), `SetLevelRequestSchema` вызывает `setLogLevel` и возвращает `{}`.
  Capability регистрируется до `setRequestHandler`, иначе SDK бросает
  «Server does not support logging».
- `tests/logging-set-level.test.ts`: unit-маппинг + реальный stdio-клиент, capability и два
  `setLoggingLevel`.

## Почему

- Pino имеет меньше уровней; явная карта не даёт молча потерять `critical`.
- Уровень меняется на корневом логгере, поэтому затрагивает все child-логгеры.
- Реальный stdio-тест ловит ошибку порядка регистрации capability.

## Проверено

- `tests/logging-set-level.test.ts` — **2/2** (unit + stdio); тест был RED до переноса
  `registerCapabilities` перед handler.
- `npm run build` — чисто.
- `npm run test:types` — чисто.
- backlog:check **369/29**.

## Ограничения

- `setLogLevel` меняет только процесс; при multi-instance кластере — только текущий узел.
- Уровень не сохраняется между перезапусками и не пишется в конфиг.
- `logging` capability объявляется всегда, даже если pino уже инициализирован другим уровнем.
- Нет теста, что после `setLevel` реально исчезают/появляются строки в stderr (только уровень).

## Откат

Убрать импорт `SetLevelRequestSchema`/`setLogLevel`, capability `logging: {}` и handler;
вернуть `logger.ts` без `mapMcpLogLevel`/`setLogLevel`; удалить тест.
