## Вопрос

Мосту нужен выбор поверхности для клиента: отдавать все инструменты ядра (`full`) или только
мета-инструменты, через которые можно дотянуться до остальных (`meta`).

## Решение

- `ProxyConfig.toolsMode?: 'full' | 'meta'` (default `full`).
- `ProxyPassthrough` в режиме `meta`:
  - `tools/list` фильтрует до `tools_list`, `tool_schema`, `tool_help`, `tools_run`;
  - прямой `tools/call` не-мета инструмента отклоняется до форварда;
  - `probe` считает отфильтрованную поверхность.
- `bridge --tools full|meta` (env `MCP_PROXY_TOOLS`), неверное значение → exit 2 с usage.
- Инструкции downstream различаются: meta-режим объясняет `tools_run`-путь.

## Почему

- Маленький клиент получает 4 инструмента вместо 129 и всё равно может вызвать любой через
  `tools_run`; полный режим остаётся для клиентов с нормальным tool UI.
- Фильтр на bridge-стороне, ядро и wire-формат ядра не меняются.
- Прямой вызов не-мета инструмента в meta-режиме закрыт, иначе фильтр `tools/list` был бы
  косметическим.

## Ограничения

- Meta-режим всё ещё объявляет capabilities resources/prompts; они пробрасываются как раньше.
- `tools_run` в meta-режиме может вызвать любой инструмент ядра — это его назначение, но значит
  это не security boundary, а UX/размер поверхности.
- CLI-разбор `--tools` проверен сборкой и unit-тестом passthrough, не end-to-end спавном bridge.
- `MCP_PROXY_TOOLS` читается только CLI; config-файл для proxy не расширялся.

## Откат

Удалить `toolsMode` из `ProxyConfig`, вернуть старый `ProxyPassthrough`, `--tools` из bridge и
`tests/proxy-tools-mode.test.ts`; ядро не затрагивалось.
