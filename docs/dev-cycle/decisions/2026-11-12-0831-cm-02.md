# 2026-11-12 08:31 — CM-02: choose tools_batch for parallel calls

- **Пункт:** CM-02 (medium)
- **Ветка / sha:** `feat/cm-02-parallel-batch`, от `origin/master` `f598443`

## Вопрос

Гейт владельца: добавить `parallel` в `tools_run` или использовать уже существующий
`tools_batch`? Нужен один канонический путь для независимых вызовов.

## Решение

Выбран **`tools_batch`** (AI-015): он уже зарегистрирован, выполняет независимые вызовы через
`Promise.all`, возвращает `{count, results, parallel:true}` и проходит общие проверки
`TOOLS_ENABLED`/`TOOL_NOT_FOUND`/`validateNestedParams`, как `tools_run`.
`tools_run` остаётся последовательным (с `stopOnError`); второй флаг не добавляется, чтобы не
держать два конкурирующих API.

## Почему

- Меньше кода и один очевидный выбор для агента: последовательно — `tools_run`, параллельно —
  `tools_batch`.
- `tools_batch` уже покрыт контрактными тестами; дублирование флага в `tools_run` дало бы два
  пути с разной семантикой `stopOnError`.
- Гейт владельца закрывается явным решением, а не новым кодом.

## Проверено

- `tests/tools-batch.test.ts` + `tests/tools-run-batch-contract.test.ts` — **8/8**.
- `npm run build` — чисто.
- backlog:check **376/22**.
- Мутация не применима: продовый код не менялся; выбор зафиксирован решением.

## Ограничения

- `tools_batch` не поддерживает `stopOnError`: при ошибке одного элемента остальные выполняются.
- Защита от параллельных записей — на уровне отдельных tools; батч не сериализует write-вызовы.
- Compact-режим вывода (`fields`/`compact`) остаётся у самих tools, а не у батча.

## Откат

Удалить это решение; `tools_batch` остаётся как был. Если позже понадобится `parallel` в
`tools_run`, это будет отдельный пункт с собственным контрактом.
