# 2026-11-11 12:35 — TR-20: rate-limit redemption WS-тикетов по IP

- **Пункт:** TR-20 (medium), зависимость AUD-13
- **Ветка / sha:** `feat/tr-20-ws-ticket-rate-limit`, от `origin/master` `0c0963f`

## Вопрос

`/ws` принимает только одноразовый тикет, но подбор тикета ничем не ограничен: `WsTicketStore.redeem`
не знал remote address, поэтому brute-force с одного IP не упирался в бюджет.

## Решение

- `WsTicketStoreOptions.redeemRateLimit?: { maxAttempts; windowMs }` — per-IP бюджет попыток.
- `redeem(ticket, remoteAddress?)`:
  - при переданном IP и исчерпанном бюджете → `{ok:false, reason:'rate_limited'}`;
  - rate-limited попытка **не сжигает** тикет (можно повторить после окна);
  - без remote всё работает как раньше (юнит-вызовы/локальные сценарии).
- `RealtimeServer` передаёт `req.socket.remoteAddress` в `redeem`.
- HTTP-транспорт устанавливает бюджет `30 попыток / 60 секунд` на IP.

## Почему

- Бюджет живёт рядом с хранилищем тикетов: один источник правды, не нужен отдельный middleware.
- Успешные и неуспешные попытки считаются одинаково — иначе перебор «мусорных» тикетов остаётся
  бесплатным.
- `rate_limited` не расходует тикет: легитимный клиент после окна может использовать тот же тикет.

## Проверено

- `tests/ws-ticket.test.ts` — **14/14**, включая TR-20: два успешных redeem с IP, третий с тем же IP →
  `rate_limited`; другой IP проходит; после `windowMs` бюджет снова доступен.
- build/tsc.
- **Мутация RED:** `if (false && remoteAddress && !this.allowRedeemAttempt(...))` → 1 тест падает;
  восстановление → 14/14.

## Ограничения

- Счётчик in-memory; при нескольких инстансах бюджеты независимы (как и сам ticket store).
- Ключ — `remoteAddress`; за reverse-proxy без trusted-proxy настройки все клиенты могут делить IP.
- Бюджет общий для всех `redeem` с IP, включая валидные; при 30 reconnect/мин с одного IP возможен
  `rate_limited`.
- Константы не настраиваются env (30/60s в HTTP-транспорте).

`redeem`, передачу remote в realtime и настройку в HTTP; тест удаляется. Поведение — прежнее.
