# Тик цикла разработки

Один тик это один проход контролёра: прочитать состояние, сделать одно действие, записать итог.
Тик не пытается закрыть день. Если пункт большой, он всё равно делится на тики: диспетч, ожидание,
проверка, PR, merge.

Перед тиком контролёр держит в голове три вещи: очередь берётся из `BACKLOG.md`, результат
проверяется по первоисточникам, решения записываются в журнал.

## Шаги тика

### Время и хвост лога

Взять время для записи (`date -Iseconds`) и прочитать хвост лога прошлых тиков
(`tail -20 "$DEVCYCLE_STATE_DIR/log.md"`). Хвост нужен, чтобы не повторять действие, которое уже
сделано, и чтобы увидеть, на чём остановился предыдущий тик.

### Квота LoopX

Спросить квоту цели:

```
loopx --format json --registry "$DEVCYCLE_REGISTRY" quota should-run \
  --goal-id "$DEVCYCLE_GOAL_ID" \
  --agent-id "$DEVCYCLE_AGENT_ID" \
  --runtime-profile generic_cli \
  --turn-instance-id "cc-$(date +%Y%m%dT%H%M%S)"
```

Если решение не `run`, записать `skip: <причина>` и закончить тик без действий. Квота это
бюджет, а не совет: при исчерпанном бюджете контролёр не диспетчит и не мержит.

`node scripts/devcycle.mjs tick` квоту не спрашивает: он берёт lock, проверяет состояние, делает
`git fetch`, считает следующий пункт и пишет лог. Решение по квоте принимает контролёр и объясняет
его в логе.

### Состояние

Снять состояние командой `node scripts/devcycle.mjs status --fetch` (в тике fetch разрешён).
Секции и что в них смотреть:

- Цикл: включён ли, когда включён, есть ли `cronId`, когда был последний тик.
- LoopX: решение по квоте и число открытых todo.
- GitHub: открытые PR кроме `dependabot/*` и `imgbot`, итог CI по `headRefOid`, `mergeStateStatus`,
  sha `origin/master` и итог CI master по `gh run list`.
- OpenCode: сессии проекта и возраст последнего `part` из `DEVCYCLE_DB`. Без моста состояния
  `busy` и `idle` не различаются, показывается только тишина.
- Worktrees: грязные, впереди или позади `origin/master`.
- Решения: последние три файла `docs/dev-cycle/decisions/`.

При ручной проверке через `OC_BRIDGE status` пульс считается от времени доставки сообщения
контролёра. Сессия считается зависшей, если она `busy` и у неё нет нового `part` дольше 10 минут.
Это сигнал в лог, а не повод прерывать работу.

### Действие

Выбрать первый подходящий случай из списка A до F и сделать ровно одно действие. Если ни один
случай не подходит, записать наблюдение и закончить тик.

### Лог

Дописать итог: время, что увидел, что сделал, чего ждёшь. Для этого есть
`node scripts/devcycle.mjs log "<текст>"`. Последняя строка в чат повторяет итог одной фразой.

## Случаи действия

### A. Своя PR, CI зелёный и merge разрешён

Условия: CI зелёный по текущему `headRefOid`, `mergeStateStatus=CLEAN`, PR не `dependabot` и не
`imgbot`. Действие: `gh pr merge <N> --merge`, затем `git -C "$DEVCYCLE_REPO" fetch origin`,
запись в лог. Мержится одна PR за тик и вообще одна за раз.

Если после merge CI master красный, очередь останавливается целиком: блокер в лог и в журнал
решений, уведомление владельцу, больше ничего не диспетчится до его решения.

### B. Своя PR, CI красный

Прочитать причину (`gh run view <id> --log-failed` и хвост лога), а не пересказ агента. Если
сессия-владелец `idle` не меньше 60 секунд, отправить ей поручение исправить. Если эта же задача
красная второй раз подряд, диспетч этой задачи останавливается, в лог и журнал пишется блокер, а
очередь переходит к следующему пункту.

### C. Своя PR, ветка грязная или позади master

`mergeStateStatus` равен `DIRTY`, `BEHIND` или показывает конфликт. Действие: поручить
сессии-владельцу влить `origin/master` обычным merge и разрешить конфликты. В `BACKLOG.md` и
`CHANGELOG.md` при конфликте сохраняются обе стороны. Force-push и rebase опубликованной ветки
запрещены.

### D. Исполнитель закончил, PR ещё нет

Признак: сессия `idle` не меньше 60 секунд подряд, в конце есть отчёт с sha. Контролёр проверяет
сам, в worktree: `git status --short` пуст, файла `MERGE_HEAD` нет, `git rev-list --count
HEAD..origin/master` равен 0 после `git fetch origin`, в diff нет отладочных файлов (`.live-*`,
`.probe-*`, временных каталогов). Только после этого: `git push -u origin <ветка>`,
`gh pr create --base master` с телом по шаблону PR и номером PR и sha в логе.

Локальная ветка `master` в общем репозитории может отставать. Сравнивать нужно с `origin/master`
после fetch, иначе проверка «позади на 23» врёт.

### E. Свободных PR и сессий нет

Сначала проверить CI самого master для текущего `origin/master` после
`git -C "$DEVCYCLE_REPO" fetch origin`. Пока идут прогоны, ничего не диспетчить: в лог пишется
«ждём CI master». Если master красный, очередь останавливается, блокер идёт в лог и журнал,
владелец получает уведомление.

Только при зелёном master берётся следующий пункт очереди и отправляется поручение. Исполнитель
обязан влить свежий master обычным merge до отчёта.

### F. Сессия занята

Если сессия `busy` и пульс живой, не делать ничего, только запись в лог. Если сессия зависла
(`busy` и больше 10 минут без `part`), записать это в лог и не прерывать: остановка только по
явной просьбе владельца.

## Очередь в бэклог-режиме

Источник очереди это `BACKLOG.md` на свежем `origin/master` (`DEVCYCLE_BACKLOG`). Команда
`node scripts/devcycle.mjs next` считает следующий пункт по правилам ниже. Очередь LoopX может
отставать от git: она подсказка и зеркало, но не источник. Если LoopX и `BACKLOG.md` расходятся,
права `BACKLOG.md`.

`next` детерминированно выбирает пункт:

- Статус только `pending`.
- Приоритет: `critical`, затем `high`, затем `medium`, затем `low` (`critical` уже используется в BACKLOG как верхняя ступень).
- Внутри приоритета порядок появления строки в файле.
- Все зависимости из колонки «Зависимости» имеют статус `done`. ID, которого нет в файле,
  считается невыполненной зависимостью.
- Пропускаются пометки `Гейт владельца` и `Проработка` в колонке зависимостей, статусы `blocked`
  и `deferred`, а также буквенные суб-пункты.
- Вывод: ID, название, приоритет, причина выбора и список первых пропущенных пунктов с причиной.

### Порядок выбора у контролёра

Скрипт отдаёт кандидата, контролёр проверяет его по смыслу:

1. Если разметка бэклога ещё не сделана, сначала выполняется она: поручение проставить `blocked`
   с пометкой «Проработка: что нужно решить» для пунктов, которые нельзя начинать без ADR или
   решения. Затем обычные PR и merge.
2. Берутся `pending` с приоритетом `critical`, затем `high`, затем `medium`, затем `low`; внутри приоритета по
   номеру этапа сверху вниз; зависимости должны быть выполнены.
3. Пропускаются и не берутся: `blocked` и `deferred`, гейты владельца, необратимые операции над
   данными, пункты без ADR там, где ADR обязателен.
4. Пункт, которому нужна проработка, делается в два PR: сначала ADR или спецификация в docs,
   потом реализация. Решение по ADR принимает контролёр и записывает файлом в `docs/dev-cycle/decisions/`:
   вопрос, решение, почему, чем проверено, как откатить.
5. Основание решения берётся из замысла: вводные цитаты этапов, блоки «Решения владельца», ADR в
   `docs/adr`, `DESIGN.md`, `docs/features`, и только потом код. Решение ссылается на конкретное
   место замысла и не противоречит ему. Если замысел молчит или два места расходятся, это вопрос
   владельцу: в журнал пишется «жду владельца», берётся другой пункт.
6. Два красных подряд по одному пункту: диспетч пункта останавливается, блокер идёт в лог и в
   журнал решений, очередь берёт следующий пункт.
7. Нет подходящих пунктов: итог в лог, уведомление владельцу, расписание остаётся или удаляется по
   решению владельца.

### Критерии «нужна проработка»

Пункт требует ADR, отчёта или спецификации, если меняет контракт или формат данных, вводит новый
внешний интерфейс, мигрирует хранилище, затрагивает безопасность, назван «ADR», «аудит» или
«модель», либо не имеет DoD с исполняемой проверкой.

### Один пункт, один дом

Перед созданием нового пункта или этапа контролёр ищет пересечения по смыслу по всем этапам, а не
только по ID. У темы «ядро и режимы запуска» один владелец: ADR задаёт модель, пункты реализации
её выполняют, остальные ссылаются и не дублируют. Этапы MU и AA не сливаются.

## Проверка результата по первоисточникам

Слова исполнителя не являются доказательством. Проверяются CI по конкретному sha, git и
состояние ветки.

| Что проверяем | Как | Годится, когда |
|---------------|-----|----------------|
| CI по sha | `gh pr checks <N>`, `gh pr view <N> --json headRefOid,mergeStateStatus` | Все проверки успешны, sha совпадает с проверенной веткой, `mergeStateStatus=CLEAN` |
| Чистота worktree | `git -C <worktree> status --short` | Вывод пуст |
| Незавершённый merge | Проверить наличие `MERGE_HEAD` в git-каталоге | Файла нет |
| Отставание от master | `git -C <worktree> fetch origin`, затем `git rev-list --count HEAD..origin/master` | `0` |
| Состав diff | `git diff --stat origin/master..HEAD` | Совпадает с поручением, лишних файлов нет |
| Отладочный мусор | `git diff --name-only origin/master..HEAD` | Нет `.live-*`, `.probe-*`, tmp-файлов и секретов |
| CI master после merge | `gh run list --branch master --limit 6 --json headSha,status,conclusion` | Все прогоны для текущего `origin/master` успешны |

Если проверка не сходится, PR не открывается и не мержится. Расхождение фиксируется в логе
открыто: «отчёт говорит одно, git показывает другое» это нормальная запись, а не стыд.

## Worktree и резервные копии

Новый worktree создаётся от свежего `origin/master`:

```
git -C "$DEVCYCLE_REPO" fetch origin
git -C "$DEVCYCLE_REPO" worktree add -b <ветка> <каталог> origin/master
```

Чужие worktree не трогаются. Если в worktree есть незакоммиченная работа, перед диспетчем
делается резервная копия вне репозитория: архив с датой в имени. Каталог копий не коммитится.

Зависимости в новом worktree появляются симлинками на общий стенд, если он есть. Свои тестовые
серверы и UI поднимаются только на свободных портах из выданного диапазона через `MCP_PORT`, а не
`PORT`; порты 3000, 3001 и 3300 принадлежат стенду владельца и не трогаются. Свои процессы
останавливаются по PID.

Поручение пишется в файл и отправляется одним сообщением через `OC_BRIDGE`. В поручении: правила
из `rules.md`, состояние worktree, задание, путь к резервной копии, формат отчёта. После доставки
контролёр проверяет, что сессия стала `busy`.

Если после углублённой постановки агент встал на вопросе «Запустить это сейчас?» и постановка не
расширяет задачу и не теряет запреты, контролёр подтверждает: «Да, запускай. Моё предыдущее
сообщение приоритетнее; запреты и порядок шагов сохраняются; новых функций не добавлять». Иначе
отправляется поправка.

## Правила остановки

- Владелец попросил остановиться: удалить расписание, выключить цикл с причиной, напечатать отчёт
  и остановиться.
- Master красный после merge: остановить всю очередь, блокер в лог и журнал, уведомить владельца.
- Два красных подряд по одному пункту: остановить только этот пункт, взять следующий.
- CI master ещё идёт: ждать, писать в лог, ничего не диспетчить.
- Нет подходящих пунктов: записать итог и уведомить владельца; расписание остаётся до его
  решения.
- Любая необратимая операция или гейт владельца: остановиться и записать «жду владельца».

## Формат записи в лог

Одна-две строки на тик: время, что увидел, что сделал. Например:

```
2026-11-03T06:43+03:00 devcycle busy, pulse alive (part 06:42), 7 messages, worktree clean, PR нет, действий нет
2026-11-03T06:58+03:00 PR #262 CI green по 4ab12cd, CLEAN, merged, master 9f0c221, ждём CI master
```

Секреты, токены и приватные данные в лог не попадают. Ошибки и неожиданные находки пишутся
открыто: лог нужен для разбора, а не для отчётности.
