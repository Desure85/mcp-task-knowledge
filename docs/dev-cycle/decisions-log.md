Решение владельца: MCP разворачивается с одним из провайдеров хранения, он и есть источник
правды. Моя прежняя рекомендация («файлы остаются источником, индекс производный») отменяется как

1. В развёртывании один активный профиль; двойной записи в два хранилища нет. В файловом профиле

2. Смена профиля только через `migrate-storage` (Y-08) с dry-run, проверкой целостности и
   откатом; бэкап и восстановление (DX-16) работают по активному профилю.

4. Хранилище пользователей (T-01): интерфейс `UserStore` входит в тот же контракт профиля.

### 2026-11-05 — P-20261105-2a, доработка: relay не роняет сервер, completion снова проверяется строго

Основание: полный прогон в worktree падал на `misc-surface` с `McpError: Connection closed` (в логе `EADDRINUSE :::41235`): два e2e-сервера с `RELAY_ENABLED=1` на фиксированном порту, unhandled `error` у `WebSocketServer`; плюс ослабленная до `[-32001, -32601]` проверка `completion/complete` в AUD-01.
Решение: (а) `RelayManager` при ошибке bind логирует `warn` через общий логгер и выключает relay (`enabled: false`), сервер продолжает работать; порт читается из `RELAY_PORT` (default 41235, документирован в `docs/getting-started/configuration.md`); e2e берут свободный порт у ОС; (б) в AUD-01 тестовый сервер — фикстура с Completable-аргументом, чтобы SDK 1.32 установил обработчик completion и запрос дошёл до гейта; строгая проверка `-32001` возвращена.
Почему: relay — опциональная подсистема, её сбой не должен ронять MCP-сервер; ослабленное ожидание перестаёт доказывать AUD-01.
Проверено: юнит-тест `tests/relay-bind-failure.test.ts` красный без фикса (unhandled `EADDRINUSE`), зелёный с фиксом; мутация гейта (удаление `completion/complete` из tcp `MAIN_DISPATCH_METHODS`) даёт `-32601` и красный AUD-01 tcp; полный `vitest run` 3/3 зелёный; `e2e:full` зелёный.

### 2026-11-06 — P-20261106-1: атомарный захват lock в `/devcycle` (Q-016)

Вопрос: два тика `/devcycle`, запущенные одновременно, оба получают `ok: true` от
`acquireLock` и дают два merge. В P-3 (PR #271) на стенде измерено 36 двойных захватов на 836
попыток, там же записано «не сделано (вне разрешённого набора файлов)». Нужен отдельный пункт:
чинить продуктовую гонку, а не только тест.

Решение:

1. Создание lock атомарно вместе с содержимым: `fs.writeFile(tmp)` во временный файл рядом и
   `fs.link(tmp, target)`. `link` отдаёт `EEXIST` при занятом lock, а читатель видит либо
   отсутствие файла, либо целиком готовый payload. Для файловых систем без hard links — откат на
   `writeFile(..., {flag:'wx'})`, который безопасен только благодаря пункту 2.
2. Пустой или нечитаемый lock без владельца считается ЗАНЯТЫМ 5 с по mtime
   (`UNREADABLE_LOCK_GRACE_MS`), а не устаревшим. Раньше `holder === null` трактовался как
   `stale`, и чужой живой lock удалялся.
3. Reclaim (мёртвый/просроченный держатель) идёт под гвардией `lock.json.reclaim`, создаваемой тем
   же атомарным способом: только один процесс за раз перечитывает lock, удаляет устаревший и
   создаёт свой. Брошенная гвардия (reclaim-ер упал) снимается по тому же правилу stale, иначе
   reclaim заблокирован навсегда.
4. `release()` удаляет lock только если в файле всё ещё наш token владельца, а не просто наш pid:
   между чтением и удалением lock мог перейти к другому процессу.
5. Контракт сохранён: `{ok: true, release}` / `{ok: false, holder: {pid, startedAt, ageMs}}`,
   опции `pid`/`now`/`staleMs`, reclaim мёртвого и просроченного держателя, формат
   `.devcycle/state.json` и `log.md` не менялись.

Почему не «оставить как есть с более широким окном удержания»: окно удержания лечит симптом в
тесте, а не гонку; барьер в тесте из P-3 ждал читаемый `lock.json` именно потому, что нечитаемый
считался свободным — то есть тест обходил настоящий дефект. Почему не `rename` без проверки:
`rename` перезаписывает цель безусловно и не даёт exclusive create. Почему не блокировка через
`mkdir`: работала бы, но меняет протокол (lock как файл с pid/startedAt читают тесты и
`devcycle.mjs`), а `link` даёт ту же атомарность без смены формата.

Проверено (числа, стенд `/tmp/oc-lock-stand`, 8 процессов на раунд, все pinned на одно ядро плюс
6 busy-loop на нём же, победитель живёт до конца раунда):

- Корень подтверждён детерминированно: процесс A делает `open(target, 'wx')`, пауза, процесс B
  заходит в это окно — `lock.json` наблюдаем размером 0 байт, B получает `ok: true` (удалив живой
  lock), A тоже `ok: true` после записи в осиротевший inode. Наблюдение пустого файла в нагрузке:
  119 440 замеров размера 0 за прогон.
- Стенд, до правки: 70 раундов × 8 = 560 попыток — 7 раундов с более чем одним победителем, до 5
  победителей в раунде (110 раундов × 8 = 800 попыток — 17 таких раундов).
- Стенд, после правки: те же 70 раундов × 8 = 560 попыток — 0 двойных захватов, максимум один
  `ok: true` на раунд.
- Тесты: новый `devcycle lock atomicity` — 5 тестов (окно «файл есть, содержимого нет»; 6 процессов
  × 6 раундов на свежем lock; 6 процессов × 3 раунда на гонке за устаревший lock; grace для
  нечитаемого lock; release только своего lock по токену). Мутация (возврат старого модуля):
  регрессионный тест падает с `expected [true, true] to have a length of 1 but got 2`, grace и
  release-тесты тоже красные. На новом коде — 30 прогонов файла подряд зелёные.

сетевых FS (NFS/SMB), где `link` и mtime ведут себя иначе.

Остаточный риск: `release()` читает файл и затем удаляет его не одной атомарной операцией; по
контракту удаляется только lock со своим токеном, а удалить его между чтением и `rm` может лишь

startedAt, transport, version, token). Захват атомарный: tmp-файл + `fs.link(tmp, lock)`, то есть
файл появляется уже с содержимым; на ФС без hardlink — fallback `wx`. Владение проверяется по
token, поэтому release и снятие протухшего lock не могут удалить чужой файл. Захват — в
`AppContainer.init()` до schema-gate, потому что миграция тоже пишет. Второй процесс получает
`SERVER_LOCK_HELD` (pid, hostname, startedAt, путь, что делать) и exit 1. Протухший lock на Linux
снимается автоматически с warn: pid мёртв или переиспользован (starttime+btime из `/proc`); снятие
сериализовано guard-файлом и внутри перепроверяет классификацию. Чужой hostname не снимается
(`SERVER_LOCK_FOREIGN_HOST`). Вне Linux identity процесса недоступна, поэтому протухший lock
автоматически не снимается (`SERVER_LOCK_UNVERIFIABLE`) — решение владельца, чтобы не удалить lock
живого процесса с переиспользованным pid. Release: cleanup в `stop()`, `process.on('exit')`, а для
stdio (`handleSignals=false`) — собственные SIGINT/SIGTERM с переотправкой сигнала. Пропуск захвата:
proxy-режим (`--proxy-upstream` / `MCP_PROXY_UPSTREAM`, задел MU-08) и `doctor`, который выходит до
создания контейнера.

Почему: token вместо pid — файл мог быть пересоздан после снятия; `link` вместо exists+write —
иначе одновременные старты дают нескольких «победителей»; lock до schema-gate — иначе миграция идёт
без эксклюзивности; чужой hostname и отсутствие `/proc` — liveness доказать нельзя, автоудаление
рискует живыми данными; identity по starttime+btime, потому что pid переиспользуется; `writeSync(2, …)`
для сообщения об отказе — stderr в пайп асинхронный, и `process.exit` сразу после `write` обрезал
единственное объяснение (нашёл тест кейса a).

Проверено: проба до кода — два stdio-процесса на одном `DATA_DIR`, 60 раундов параллельного
`tasks_update` одной задачи: 56/60 потерянных обновлений (49/60 в первом прогоне). После — второй
процесс не стартует (exit 1, `SERVER_LOCK_HELD`), потерь 0. `tests/server-lock.test.ts`, 7 кейсов:
a) второй процесс, b) 20 одновременных захватов через барьер — ровно один победитель, c) `kill -9` →
следующий старт снимает протухший lock, d) переиспользование pid и отказ вне Linux, e) SIGTERM
снимает lock, f) чужой hostname, g) проба без потерь. Revert-check точечными мутантами: без захвата
в boot красные a, c, e, g; без проверки identity — d; чужой hostname как stale — f; без reclaim —
c, d; без release на сигнал — e; exists+write вместо link — b (пять победителей вместо одного).
Гейты (build, test:types, lint, lint:md, backlog:check, полный тест) — в отчёте сессии. Вне Linux и
на сетевых ФС поведение не проверялось: `/proc` там нет, автоснятия нет по решению выше.
