# Режим «прод-грейд»: критерии готовности и предложения улучшений

Документ описывает, что значит «репозиторий доведён до продакшн-уровня» и как контролёр
(подкоманды `/devcycle readiness` и `/devcycle proposals`) снимает готовность и оформляет улучшения. Он дополняет `README.md`, `tick.md` и
`rules.md` и не отменяет их: роли, лимиты и запреты там.

Принцип: «готово» определяют проверки, а не ощущение. Каждый критерий ниже имеет команду-пробу
и порог. Контролёр сам не объявляет прод-грейд достигнутым: он собирает отчёт, объявляет
владелец.

## Критерии готовности (gates)

Пробы только читают состояние. Тяжёлые пробы (`npm test`, `test:coverage`, `npm pack`)
запускаются в отдельном worktree от свежего `origin/master`, а не в рабочем каталоге владельца.

| Gate | Что проверяет | Проба | Порог «зелёный» |
|------|---------------|-------|-----------------|
| R1 CI master | Основная ветка собирается и проходит проверки | `gh run list --branch master --limit 5 --json conclusion,headSha` | Последний прогон для `origin/master` успешен |
| R2 Бэклог | Таблицы и счётчики согласованы | `npm run backlog:check` | Код выхода 0 |
| R3 Сборка и типы | Код компилируется, тесты типизированы | `npm run build`, `npm run test:types` | Оба с кодом 0 |
| R4 Линт | Стиль и markdown | `npm run lint`, `npm run lint:md` | Оба с кодом 0, число предупреждений не выросло к прошлому прогону |
| R5 Тесты | Поведение | `npm test`, затем `cd web-ui && npm test` | Все зелёные; падение из-за занятого порта 4001 чужим процессом это «не проверено», а не «зелёный» |
| R6 Покрытие | Порог проекта | `npm run test:coverage` | Не ниже порога в `vitest.config.ts` |
| R7 Безопасность: очередь | Нет открытых критичных и высоких пунктов аудитов | `node scripts/devcycle.mjs next --limit 50` и просмотр этапов M, O, P | Нет `pending` с приоритетом `critical` и `high` в этапах безопасности, кроме закрытых гейтом владельца |
| R8 Безопасность: зависимости | Известные уязвимости рантайма | `npm audit --omit=dev --audit-level=high` в worktree; в CI это же выполняет блокирующий шаг `npm audit (production deps, blocks on high or critical)` из `bulk-smoke.yml` | Нет находок high и critical, либо каждая есть в `decisions-log.md` с обоснованием и `overrides` с причиной |
| R9 Образ | Публикуемые образы не запускаются от root | Для каждой цели `runtime-*` из `.github/workflows/docker-build.yml` собрать образ и выполнить `docker run --rm --entrypoint id <образ>`; без Docker прочитать последнюю инструкцию `USER` в стадиях цели | Для каждой цели итоговый пользователь не root (`USER root` в промежуточных стадиях допустим) |
| R10 Пакет | Установленный пакет работает | `npm pack`, установка в пустой каталог, запуск `prompts_list` после `bulk_create` | Работает вне репозитория (проверка PH-001) |
| R11 Документация | Quickstart соответствует коду | Выполнить шаги `docs/quickstart-production.md` на чистом `DATA_DIR` | Шаги проходят без правок |
| R12 Данные | Резервная копия и восстановление | Пункт этапа N про backup/restore, если он `done`; иначе проба пропускается и фиксируется как пробел | Восстановление из копии даёт тот же `knowledge_list` |
| R13 Нагрузка | Масштабирование не деградировало | `npm run bench:scale` | Не хуже базовых чисел в `docs/benchmarks/` |
| R14 Входящие PR | Автообновления не копятся | `gh pr list --state open --json number,title,headRefName` | Открытых `dependabot/*` не больше трёх; мажорные обновления идут отдельными решениями, а не мержем по зелёному CI |

Если проба недоступна (нет сети, нет прав, нет данных), результат это `n/a` с причиной, а не
«зелёный». Пробел в проверке сам по себе кандидат в предложение.

Критерий «прод-грейд достигнут»: все gates зелёные или `n/a` с принятым решением, нет
`pending` с приоритетом `critical` и `high`, CI master зелёный по текущему sha. Отчёт об этом
контролёр отдаёт владельцу; вердикт остаётся за владельцем.

## Предложения улучшений

В процессе работы контролёр замечает вещи, которых нет в бэклоге: красный gate, повторяющаяся
хрупкость, дубли, устаревшая документация, отсутствующая проверка. Он не чинит это молча и не
копит в голове, а оформляет предложение.

### Правила

1. **Только с доказательством.** У предложения есть воспроизводимая проба: команда с выводом,
   `file:line` или ссылка на прогон CI. Предложение «стоит бы улучшить X» без пробы не
   записывается.
2. **Сначала поиск пересечений.** Перед записью искать по смыслу в `BACKLOG.md`, `docs/adr` и
   `decisions-log.md` (ключевые слова и просмотр этапов), а не только по ID. Если замысел
   уже есть, предложение превращается в ссылку на существующий пункт.
3. **Не больше трёх новых за тик.** Остальное ждёт следующего тика. Очередь не должна
   превращаться в поток шума.
4. **Одно предложение, один вывод.** Не смешивать несколько улучшений в одно.
5. **Контролёр не правит `BACKLOG.md` сам.** Принятое предложение оформляется поручением
   исполнителю: он добавляет пункт в отдельном worktree, контролёр проверяет и мержит.

### Формат записи

Предложения лежат в `.devcycle/proposals.md` (локально, в git не попадает). Одна запись:

```
### P-<YYYYMMDD>-<n> <краткое название>
- Проба: <команда или file:line, вывод одной строкой>
- Проблема: <что не так и для кого>
- Предложение: <что сделать>
- Польза: <какой gate или риск закрывается>
- Цена: S | M | L
- Риск: <что может сломаться, как откатить>
- Класс: auto | owner
- Статус: new | accepted | declined | merged | duplicate
- Решение: <кто и когда, ссылка на запись в decisions-log.md>
```

### Классы решения

| Класс | Что относится | Кто решает |
|-------|---------------|------------|
| `auto` | Тесты, документация, линт, пункты `pending` в бэклоге, обновления зависимостей без мажорных версий, новые пробы и CI-проверки без новых зависимостей | Контролёр: пишет решение в `decisions-log.md` (вопрос, решение, почему, чем проверено, как откатить) и ставит поручение |
| `owner` | Гейты владельца, мажорные обновления зависимостей (например, zod 3 → 4), новые архитектурные решения и ADR с выбором между вариантами, необратимые операции над данными, права и аутентификация, публикация вовне, YouTrack | Владелец: контролёр показывает предложение в отчёте и не ставит поручение до ответа |

Сомнение в классе решается в сторону `owner`.

### Сводка для владельца

В конце сессии и по запросу контролёр выдаёт список: что принято и поставлено в работу, что
ждёт решения владельца (с рекомендацией по каждому пункту, а не голым списком вариантов), что
отклонено и почему.
