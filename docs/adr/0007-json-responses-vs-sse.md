# ADR-007: JSON-ответы HTTP-транспорта и прогресс по SSE

- **Статус:** Accepted (2026-10-31, SC-01)
- **Область:** `src/transport/http-transport.ts`, `docs/getting-started/configuration.md`

## Контекст

Замеры (`docs/benchmarks/scale-2026-10.md` §3.2) показали, что обрамление сообщений в MCP SDK
квадратично по размеру: `ReadBuffer.append` (stdio) и SSE-парсер клиента накапливают чанки.
Эксперимент на одном и том же ответе 20 MB:

| Режим ответа | Время |
|---|---|
| `text/event-stream` (SSE) | 4 194 мс |
| `application/json` | 246 мс |

То есть SSE-режим сам по себе делал большие ответы в 17× дороже, независимо от того, что в них.
Для SC-01 транспорт переключён на `enableJsonResponse: true`.

У JSON-режима есть цена: `StreamableHTTPServerTransport.send()` в JSON-ветке пишет только
финальный ответ и **не отправляет** промежуточные `notifications/progress` — они доставляются
только по открытому SSE-стриму. В проекте есть AI-013 (`src/core/streaming.ts`,
`createProgressSender`/`withProgress`) — сейчас этими хелперами не пользуется ни один встроенный
инструмент (используются только в `streaming.spec.ts`), но внешние клиенты и будущие инструменты
могут запрашивать прогресс через `params._meta.progressToken`.

## Решение

Режим выбирается **на каждый запрос**, а не глобально:

1. По умолчанию — `application/json` (быстро, линейно).
2. Если в теле запроса есть `params._meta.progressToken` (одиночный вызов или batch),
   этот запрос обслуживается по SSE: у транспорта на время запроса снимается
   `_enableJsonResponse`, и клиент получает `text/event-stream` с прогрессом и финальным ответом.
3. `MCP_JSON_RESPONSES=0` возвращает SSE для всех запросов (аварийный/совместимый режим,
   например для клиента, который умеет только SSE).

Восстановление флага привязано к событию `finish`/`close` ответа, а не к возврату
`handleRequest`: SDK возвращается из `handleRequest` сразу после диспетчеризации сообщения,
а сам ответ пишется позже в `transport.send()`. Раннее восстановление приводило к гонке —
SSE-заголовки уже отправлены, а запись ответа шла по JSON-ветке, и клиент не получал ничего.

## Последствия

- Большие ответы (списки, документы) не платят квадратичную цену SSE.
- Клиент, которому нужен прогресс, получает его, просто передав `progressToken` — без
  дополнительной настройки сервера.
- Внутри одной сессии запросы обрабатываются последовательно (так работает MCP-клиент),
  поэтому флаг не «перетекает» между вызовами. Если два запроса одной сессии всё же
  пересекутся, SSE-запрос просто обслужит и второй — медленнее, но корректно.
- `memory_async_*` (submit/status/cancel) не используют progress-уведомления: это опрос
  по `jobId`, режим ответа на них не влияет. `tools_batch`/`tools_run` тоже не шлют
  прогресс — они возвращают агрегированный результат. Relay использует WebSocket, не MCP.

## Проверка

- `tests/e2e-full/http-response-mode.test.ts`: без токена — `application/json`;
  с `progressToken` — `text/event-stream`; `MCP_JSON_RESPONSES=0` — всегда SSE.
- `tests/e2e-full/http-sessions.test.ts` зелёный в обоих режимах (SSE-путь не сломан).
- Регрессионный замер 10k: `node scripts/bench/run-scale.mjs --n 10000 --only tasks_list`
  → медиана ~145 мс, ответ ~30 KB (было 897 мс / 5.9 MB).
