## Контекст

### Зачем это вообще

`BACKLOG.md:887` (DX-16) обещает ответ на два вопроса: «где мой бэкап» и «как переехать на другую
машину». Гейт R12 (`docs/dev-cycle/production-grade.md:29`) формулирует приёмку буквально:

`docs/getting-started/configuration.md:32-35` уже обещает пользователю: «Mount that one directory as
a volume in Docker and back it up as a unit». То есть контракт «архив = DATA_DIR целиком» уже
заявлен в документации; ADR должен либо подтвердить его, либо явно сузить.

## Решение

### 1. Формат архива

Архив — стандартный `tar.gz`: gzip поверх ustar/PAX без абсолютных путей. В корне архива лежит
`manifest.json`:

```json
{
  "format": "mcp-task-knowledge-backup",
  "formatVersion": 1,
  "createdAt": "2026-11-06T18:39:33.782Z",
  "createdBy": "mcp-task-knowledge@1.0.20",
  "profile": "files",
  "schemaVersion": 1,
  "scope": "full",
  "excluded": [".backups", ".embeddings", ".emb_cache", ".jwt-revoked.json", "auth.db", "audit.log"],
  "entries": [{ "path": "tasks/acme/t1.json", "type": "file", "size": 31, "sha256": "…" }],
  "stats": { "files": 14, "bytes": 12345, "archiveBytes": 6789 }
}
```

Правила:

- Пути в `entries` только относительные, разделитель `/`, без `.` и `..`, сортировка по `path` —
  архив детерминирован при одинаковом входе.
- `sha256` считается по распакованному содержимому файла; при restore проверяются все записи
  **до** первой записи на диск.
- `profile` и `schemaVersion` — сведения о том, из какого профиля и с какой схемой снят архив.
- Абсолютный `DATA_DIR` в архив не попадает: архив переносим, цель восстановления задаёт
  принимающая сторона.

**Альтернатива:** zip. **Почему нет:** в Node нет встроенного zip-писателя (нужна зависимость), а
tar.gz читается стандартными `tar`/`gzip` на любой машине без Node — это и есть «как переехать».
**Альтернатива:** собственный JSON-контейнер (файлы + base64). **Почему нет:** растёт размер,
нечем посмотреть глазами, ломается требование «стандартный архив».

### 2. Чем собирать и распаковывать

Свой writer/reader tar поверх `node:zlib` (`createGzip`/`gunzip`), без новых зависимостей. В
`package.json` нет ни `tar`, ни `zip`, ни `archiver`; `node:zlib` есть всегда.

**Альтернатива:** системный `tar` через `child_process`. **Почему нет:** зависит от наличия бинаря
и его диалекта (GNU/bsdtar/Windows), коды ошибок не нормализуются, а защиту от `../`, симлинков и
бомб всё равно нужно делать самим — то есть валидация пишется в любом случае, и тогда внешний
бинарь добавляет только вторую точку отказа. **Цена своего writer:** ~150 строк и тесты на
заголовки/выравнивание; читать чужой tar (legacy-архивы из будущих версий) сложнее — поэтому
формат фиксируется версией и reader поддерживает только `formatVersion: 1`.

**Альтернатива:** добавить `tar` в зависимости. **Почему нет:** запрещено правилами цикла
(`docs/dev-cycle/rules.md:91`).

### 3. Что входит в архив

| Путь в DATA_DIR | В архиве | Почему |
|---|---|---|
| `tasks/`, `knowledge/`, `projects/`, `prompts/`, `memory/` | да | пользовательские данные, ради них архив и нужен |
| `.state.json`, `stopwords.txt` | да | состояние и конфигурация, дёшево |
| `models/` | да (флаг `--exclude-models`) | установленные бандлы; по умолчанию fidelity важнее размера |
| `.schema-version` | да, но с особой политикой restore (п. 10) | совместимость формата |
| `.jwt-revoked.json` | **нет** (только `--include-secrets`) | состояние безопасности; откат списка отзывов оживляет токены (проба Д4) |
| `auth.db` | **нет** (только `--include-secrets`) | хеши паролей; `2026-11-03-0650-tk-01.md` прямо запрещает без флага |
| `audit.log` | нет | операционный журнал, а не данные; откат журнала стирает следы |
| `.embeddings/`, `.emb_cache/` | нет | производный кеш, пересобирается |
| `.backups/` | нет | рекурсия; снапшоты не пакуются в снапшот |

`--include-secrets` добавляет `.jwt-revoked.json` и `auth.db` и помечает архив
`containsSecrets: true`; восстановление такого архива требует отдельного подтверждения.
Исключённое всегда перечисляется в `manifest.excluded` — пользователь видит, что не в архиве, а не
узнаёт об этом при переезде.

**Альтернатива:** «исключать секреты всегда, без флага». **Почему нет:** переезд с переносом
пользователей иначе невозможен, а `2026-11-03-0650-tk-01.md` разрешает это «с явным флагом».

### 4. Контракт инструментов

Оба инструмента отвечают через `ok()`/`errWith()` (`src/utils/respond.ts`), коды стабильные,
входы — zod (`zod/v3`, как в соседних регистрациях).

`admin_backup`:

```ts
const backupInput = z.object({
  out: z.string().min(1).optional(),        // каталог для архива; по умолчанию DATA_DIR/.backups
  label: z.string().max(60).optional(),     // суффикс имени файла
  includeSecrets: z.boolean().optional(),   // .jwt-revoked.json + auth.db
  excludeModels: z.boolean().optional(),
});
```

Успех: `{ archivePath, bytes, files, manifest: { formatVersion, profile, schemaVersion, excluded } }`.
Архив пишется как `<out>/backup-<timestamp>-<label>.tar.gz.partial` и переименовывается в
`…tar.gz` только после записи манифеста и контрольных сумм.

`admin_restore`:

```ts
const restoreInput = z.object({
  archive: z.string().min(1),               // путь к .tar.gz (абсолютный)
  dryRun: z.boolean().default(true),        // по умолчанию только отчёт
  confirm: z.string().optional(),           // обязателен при dryRun=false: значение из dry-run
  prune: z.boolean().default(true),         // заменять scope целиком, а не накладывать
});
```

Успех dry-run: `{ dryRun: true, applyToken, entries, creates, overwrites, deletes, warnings }`;
`applyToken` — одноразовая строка (хеш плана + время), которую надо вернуть в `confirm`.

Коды ошибок:

| Код | Когда |
|---|---|
| `BACKUP_ARCHIVE_INVALID` | не gzip/tar, нет `manifest.json`, битый JSON |
| `BACKUP_FORMAT_VERSION_UNSUPPORTED` | `formatVersion` не 1 |
| `BACKUP_CHECKSUM_MISMATCH` | `sha256` записи не совпал |
| `BACKUP_PATH_ESCAPE` | абсолютный путь, `..`, NUL в имени |
| `BACKUP_SYMLINK_REJECTED` | запись типа symlink/hardlink/device |
| `BACKUP_TOO_LARGE` | распакованный объём или число записей выше лимита |
| `BACKUP_SCHEMA_TOO_NEW` | `schemaVersion` архива больше `CURRENT_SCHEMA` |
| `BACKUP_PROFILE_UNSUPPORTED` | архив снят не с файлового профиля |
| `RESTORE_CONFIRM_REQUIRED` | `dryRun=false` без валидного `confirm` |
| `RESTORE_TARGET_BUSY` | чужой процесс держит `.restore.lock` |
| `RESTORE_SNAPSHOT_FAILED` | не удалось снять автоснапшот перед записью |
| `BACKUP_NOT_FOUND` | архива нет или нет прав на чтение |

**Альтернатива:** один инструмент `admin_data` с `action`. **Почему нет:** разные права и разный
уровень опасности; отдельные имена читаются в `tools_list` и в аудите.

### 5. Семантика restore

`restore` = **замена в пределах scope**, а не наложение: после проверки всех записей файлы из
архива записываются, а файлы под теми же префиксами, которых в архиве нет, удаляются (`prune`).
Порядок: прочитать манифест → проверить версию/профиль/схему → проверить все контрольные суммы →
построить план (create/overwrite/delete) → dry-run отчёт → автоснапшот → применить.

**Альтернатива:** оставить наложение (текущее поведение). **Почему нет:** проба Д4 показала, что
после «восстановления» остаются документы, созданные после бэкапа, и отозванные токены оживают;
это не откат и не проходит R12 («тот же `knowledge_list`»).

**Альтернатива:** удалять весь DATA_DIR и распаковывать заново. **Почему нет:** снесёт файлы вне
scope (другие проекты, кеши, локальные логи) и сделает частичный сбой необратимым.

### 6. Безопасность распаковки

Проверка идёт одним проходом по заголовкам, **до** записи первого байта:

- имя записи: относительное, без `..`, без ведущего `/`, без `\`, без NUL, длина ≤ 4096;
- тип: только `file` и `dir`; symlink, hardlink, device, fifo — `BACKUP_SYMLINK_REJECTED`;
- целевой путь: `resolveUnder(DATA_DIR, ...segments)` (`src/fs.ts:153`), а не `path.join`;
- лимиты: распакованный объём ≤ `BACKUP_MAX_MB` (по умолчанию 512 МБ, тот же env, что у DX-19) ×
  коэффициент, число записей ≤ 200 000, коэффициент сжатия одной записи ≤ 200:1 — иначе
  `BACKUP_TOO_LARGE`;
- `..` в *manifest* (`entries[].path` и `paths[].from`) проверяется теми же правилами: манифест —
  недоверенный вход (дефект Д1).

**Альтернатива:** положиться на `tar -x` с `--no-same-owner`. **Почему нет:** поведение при
вредоносных именах различается между реализациями, а нам нужен стабильный код ошибки и запись
«ничего не изменено». **Альтернатива:** распаковывать во временный каталог и потом переносить.
**Почему нет:** это защита от частичной записи, но не от выхода за каталог; делаем и то, и другое:
валидация + запись в `<DATA_DIR>/.restore-tmp/` с последующим переносом и удалением.

### 7. Профили хранилища

Архив поддерживается только для файлового профиля (`profile: "files"`). Для SQLite/Postgres
`admin_backup` возвращает `BACKUP_PROFILE_UNSUPPORTED` с подсказкой: снимать средствами самой СУБД
(`pg_dump`/`.backup`) и переезжать через `migrate-storage` (Y-08), а пользователей — штатным
экспортом профиля.

**Почему так:** `2026-11-03-0720-y-09.md` фиксирует, что источник правды — активный провайдер, а
«в профилях SQLite и Postgres источник сама база, файлов задач и знаний на диске нет». Архив
DATA_DIR в этих профилях сохранит пустоту и создаст ложное чувство бэкапа.
**Альтернатива:** логический дамп по профилю внутри DX-16. **Почему нет:** это второй формат,
дублирование Y-08 и экспортных инструментов, рост скоупа; выносится отдельным пунктом, если
понадобится.

### 8. Атомарность и конкурентность

- Бэкап: пишется в `.partial`, переименовывается атомарно (`rename` в пределах одного каталога,
  как в `src/fs.ts:30-40`). Прерванный бэкап не оставляет валидного файла.
- Бэкап живого сервера **допустим, но не атомарен**: между файлами нет транзакции. Манифест
  помечает `live: true` и `warnings: ["files may have changed during copy"]`. Консистентный бэкап
  требует остановленных записей — это сказано в документации, а не подразумевается.
- Restore: берёт `withFileLock('restore')` (внутрипроцессно), ставит глобальный флаг
  «записи запрещены» (мутирующие инструменты отвечают `RESTORE_IN_PROGRESS`), ждёт завершения
  активных записей с бюджетом, затем применяет план.
- Между процессами: `DATA_DIR/.restore.lock` с `{ pid, startedAt, host }`. Живой чужой лок →
  `RESTORE_TARGET_BUSY`; лок старше 30 минут → `--force-stale-lock` (осознанное решение
  оператора). Своего межпроцессного lock-провайдера в проекте нет (`src/fs.ts:43-66` — только
  in-process), поэтому лок файловый и документированный, а не «как-нибудь».

**Альтернатива:** не блокировать и «просто копировать». **Почему нет:** restore поверх пишущего
сервера даёт смесь двух состояний, которую нельзя ни откатить, ни объяснить.

### 9. CLI-обёртка

`dev-cli backup [--out DIR] [--include-secrets] [--exclude-models]` и
`dev-cli restore <archive> [--dry-run] [--yes]` вызывают те же функции сервиса, что и инструменты
(один код-путь, без дублирования логики).

`dev-cli export` **не переиспользуется**: сегодня он не копирует файлы и работает с пустым
временным `DATA_DIR` (проба Д6, `scripts/dev-cli.mjs:46-59`, `:130-148`). Текущую команду
оставляем как есть в этом PR; в DX-16a она помечается deprecated в `usage()` и удаляется в DX-16b
после появления `backup`. CLI обязан брать `DATA_DIR` из окружения, а не подменять его `mkdtemp`,
иначе «где мой бэкап» снова отвечает пустотой.

### 10. Совместимость и версии

- `formatVersion` — версия контейнера; reader понимает только `1`, иначе
  `BACKUP_FORMAT_VERSION_UNSUPPORTED` (без попыток «угадать»).
- `schemaVersion` — значение `.schema-version` на момент бэкапа. При restore: архив новее текущей
  схемы → `BACKUP_SCHEMA_TOO_NEW` (зеркало `src/services/schema-version.ts:15-17`); архив старее →
  разрешаем, записываем значение из архива, миграции выполнятся при следующем старте.
- Старые каталог-снапшоты `.backups/<ts>-<label>/` остаются восстановимыми: `restoreBackup` с
  усиленной валидацией (DX-16b) читает и их. Архив — только для переноса и явного «где мой
  бэкап», а не замена автоснапшотам DX-19.

**Альтернатива:** один формат «каталог навсегда». **Почему нет:** «как переехать на другую машину»
требует одного файла; каталог из тысяч файлов для этого неудобен и не имеет контрольных сумм.

### 11. Откат restore

Перед применением автоматически снимается снапшот `DATA_DIR/.backups/<ts>-pre-restore/`
(каталог-формат DX-19, **включая** секреты — он локальный и никогда не покидает машину). Откат =
restore этого снапшота. Что откат **не** вернёт: записи, сделанные в БД при профилях SQLite/Postgres
(профили не поддерживаются), и внешние по отношению к DATA_DIR эффекты (вебхуки, уже отправленные
уведомления). Это записывается в отчёт `admin_restore` полем `irreversible`.

### 12. Что не входит в этот PR

Код, тесты, миграции, изменения `src/**`, инкрементальные бэкапы, дедупликация, шифрование архива,
remote-upload, дампы SQLite/Postgres, UI. В этом PR только этот ADR, строка DX-16 и подпункты
DX-16a/DX-16b в BACKLOG, запись в `docs/dev-cycle/decisions/`.

## Последствия

- `admin_backup` даёт один файл, который читается стандартным `tar` и переносится между машинами;
  секреты по умолчанию не уезжают.
- `admin_restore` перестаёт быть «наложением»: после него состояние совпадает с архивом в пределах
  scope, что и проверяет R12.
- Существующие автоснапшоты DX-19 и их формат не меняются; их дефекты (Д1-Д5) закрываются
  отдельным подпунктом, а не молчаливым патчем.
- Для SQLite/Postgres появляется явный отказ вместо ложного «бэкап есть».
- Свой tar-writer — единственная новая поверхность кода; она небольшая, но требует тестов на
  заголовки, выравнивание и враждебные имена.

## Поправка (2026-11-07)

Владелец принял одно отступление от текста выше: `stats.archiveBytes` **не хранится** в
`manifest.json` внутри архива. Финальный размер gzip до закрытия потока неизвестен, а манифест
лежит в том же архиве; размер готового файла возвращают `admin_backup` и `dev-cli backup` (по
`stat` после `rename`). Остальные поля `stats` (`files`, `bytes`, `dirs`) остаются в манифесте.

Следствие для порядка записей: `manifest.json` пишется последней записью tar-потока. Иначе хеши и
размеры файлов, которые он перечисляет, ещё неизвестны; «в корне архива» означает путь, а не
позицию в потоке. Reader находит манифест по имени, а не по порядку.

Решение, основание и откат: `docs/dev-cycle/decisions/2026-11-07-0040-dx-16a.md`
(«DX-16a: archiveBytes вне манифеста»).
