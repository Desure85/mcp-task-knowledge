# 0010 — Общее ядро и режимы запуска (agent core)

- **Статус:** Accepted
- **Дата:** 2026-11-10
- **Связанные:** [MU-01](../BACKLOG.md) (single-writer lock DATA_DIR), [MU-08](../BACKLOG.md)
  (stdio→http bridge), [ADR-009](0009-pluggable-storage-and-embeddings.md)

## Контекст

MCP-клиенты бывают двух видов: stdio-клиенты, которые спавнят процесс на сессию, и долгоживущие
клиенты, подключающиеся по сети. Если каждый stdio-клиент поднимает собственный сервер на одном
`DATA_DIR`, два процесса начинают read-modify-write один и тот же каталог: до MU-01 это давало
потерянные обновления (воспроизведено: 56/60). Если же пытаться «выбирать лидера» среди процессов,
получаем распределённую систему с split-brain, которую нельзя надёжно проверить в рамках одного
каталога. Нужна модель, которая явно отвечает: где живёт ядро, кто владеет `DATA_DIR`, что происходит
при втором ядре и как клиенты подключаются на разных платформах.

## Решение

### Режимы запуска

- **stdio (по умолчанию).** Один клиент, один процесс: `mcp-task-knowledge` (без подкоманд) поднимает
  `AppContainer` и обслуживает stdio. Ядро живёт ровно столько, сколько живёт клиентский процесс.
  Это режим, который клиенты вроде Claude Desktop используют «из коробки»; сеть не нужна.
- **HTTP-ядро (постоянный сервис).** `MCP_TRANSPORT=http` (порт `MCP_PORT`, по умолчанию 3001) —
  долгоживущий процесс; несколько клиентов подключаются к одному ядру. Ядро владеет `DATA_DIR` и
  векторами; клиенты не трогают файлы.
- **Bridge (тонкий прокси).** stdio-клиент, который не умеет HTTP, запускает
  `mcp-task-knowledge bridge --url <http(s)://core/mcp> [--token …]`. Это stdio→HTTP шим (MU-08):
  stdout остаётся протокольным, токен не печатается, человеческие сообщения идут в stderr. Bridge
  **не** владеет `DATA_DIR` и не открывает хранилище.
- **TCP / Unix-socket транспорты.** Для сред, где нужен локальный сокет/порт без HTTP-обвязки:
  TCP loopback и Unix-сокет зарегистрированы в `TransportRegistry` наравне с HTTP. Они не меняют
  модель владения: это тот же процесс-ядро с тем же `.server.lock`.

### Время жизни

- Ядро живёт **дольше клиента**: HTTP-процесс не завершается при отключении одного клиента. stdio-
  процесс живёт ровно столько, сколько клиент держит stdin открытым.
- `DATA_DIR` принадлежит **ровно одному процессу-ядру**. Владение фиксируется `.server.lock`
  (MU-01): атомарная запись с токеном, reclaim только по мёртвому pid/start-time, чужая hostname —
  никогда автоматически. Второй процесс на том же `DATA_DIR` получает `SERVER_LOCK_HELD` и
  завершается с понятной подсказкой (остановить первый, либо подключиться bridge'ом к живому ядру).
- Векторы и производные индексы (FTS/metadata) принадлежат тому же владельцу: их пишет только ядро,
  поэтому «второй писатель» невозможен по построению, а не по договорённости.

### Windows

- Unix-сокеты на Windows **не поддерживаются** транспортом (тесты UnixTransport помечены как
  платформенные); named pipe в этой версии **не реализован** — это кандидат на отдельный инкремент,
  а не скрытая возможность. Рабочие варианты на Windows: stdio (по умолчанию), HTTP/TCP loopback и
  bridge к HTTP-ядру.
- Проверки владельца (`kill(pid,0)`, start-time) на Windows не имеют `/proc`; lock трактуется
  консервативно (мёртвость не доказывается автоматически для чужого hostname/нечитаемого файла),
  поэтому пользователю показывается путь к `.server.lock` и инструкция проверить процессы вручную.
- Пути и сравнение hostname регистронезависимы; формат lock-файла одинаков на всех платформах.

### Сигналы

- Не-stdio ядро ставит обработчики `SIGTERM`/`SIGINT` (AppContainer, `handleSignals` по умолчанию
  включён для не-stdio): graceful shutdown закрывает транспорт, дожидается in-flight запросов,
  освобождает `.server.lock` и завершает процесс.
- stdio-режим не ставит «серверные» обработчики (клиент управляет жизнью процесса); отдельный
  signal-hook освобождает lock, чтобы аварийное завершение не оставляло вечный lock.
- Повторный `stop()`/`shutdown()` идемпотентен: несколько клиентов/повторные сигналы не приводят к
  двойному освобождению или удалению чужого lock (release сверяет токен).
- При нескольких клиентах HTTP-ядра сигнал завершает **ядро**, а не клиентов: bridge-процессы
  получают разрыв соединения и завершаются по своим правилам (exit 3 upstream).

### Почему не выбираем лидера среди процессов

Выбор лидера решает «кто главный» для распределённой системы, но здесь ресурс — **один локальный
каталог**, а не кластер. Любой алгоритм (raft, lease-сервер, консенсус) добавил бы сетевую
зависимость и новый класс отказов ради задачи, которую решает атомарный файловый lock: два ядра на
одном `DATA_DIR` — это ошибка конфигурации, а не состояние, которое нужно автоматически «лечить».
Поэтому MU-01 фиксирует **владение**, а не консенсус: второй процесс честно отказывается работать,
пользователь выбирает — остановить первое ядро или подключиться к нему bridge'ом.

## Последствия

- Один `DATA_DIR` — одно ядро; горизонтальное масштабирование записи через несколько процессов на
  одном каталоге не поддерживается (и не будет маскироваться).
- stdio-клиенты, которым нужен общий сервер, используют bridge; это документированная, а не
  «подразумеваемая» схема.
- Windows-путь ограничен stdio/HTTP/TCP/bridge; named pipe и Unix-сокеты — записанные ограничения,
  а не обещания.
- Ошибки владения (`SERVER_LOCK_HELD`, `SERVER_LOCK_FOREIGN_HOST`, `SERVER_LOCK_UNVERIFIABLE`)
  являются частью контракта запуска; их тексты должны оставаться actionable.
- Тесты MU-01/MU-08 остаются источником истины для lock и bridge; этот ADR фиксирует модель и
  ссылается на них, а не переизобретает.
