# UX/UI-аудит админки (web-ui), октябрь 2026

> Дата: 2026-10-30. Объект: `web-ui/` на `master` (`3c24d04`, стенд `localhost:3000` + MCP `:3001`).
> Метод: живой обход в Chromium (Playwright), измерения по DOM/CSS, три сквозных сценария, прогон отказов
> (просроченный токен, недоступный сервер), сверка с `BACKLOG.md`.
> Цель: ответить на вопрос «сможет ли этим спокойно пользоваться человек, который не писал этот код».
> Код не менялся. Единственный артефакт — этот файл.

## 1. Вердикт

Админка **уже годится для одного технического пользователя**, который знает, что за страницы и как включить
realtime. Для «других людей» есть **два блокера P0** (раздел «Знания» падает в белый экран на двух обычных
действиях) и системный слой P1: пользователь не отличает «нет данных» от «нет связи», не понимает, почему его
выкинуло на логин, и видит два разных продукта в одном меню (3 страницы в новом стиле, 8 — в старом).

Оценка по осям (1–5, где 5 — «можно отдать коллеге без объяснений»):

| Ось | Оценка | Что решает |
|-----|--------|------------|
| Корректность основных путей | 2 | F-01, F-02 (падения в «Знаниях»), F-03 (выкидыш без объяснения) |
| Предсказуемость состояний | 2 | F-04…F-06 (нет связи ≠ нет данных), F-07…F-08 (вечный «Connecting…») |
| Визуальная целостность | 2 | F-16 (3 страницы нового стиля против 8 старых) |
| Доступность (WCAG 2.2 AA) | 2 | F-11…F-15 (skip-link, подписи полей, клавиатура, контраст) |
| Мобильная версия | 3 | нет горизонтального overflow, но навигация и цели нажатия (F-26) |
| Задачи как трекер | 2 | только канбан, без списка, массовых действий и сохранённых фильтров (F-17) |
| Насыщенность данными (Overview/Analytics) | 2 | F-18, F-20: страницы обещают больше, чем показывают |

Что работает хорошо и трогать не надо: каркас (`AppShell`), логин, `PageHeader`-страницы (`/`, `/tasks`,
`/access`), канбан с drag&drop, страница `/search` (быстрая, с оценками релевантности), генерация setup-link
на `/access` (DX-29 уже реализован), отсутствие горизонтального скролла на 390 px на всех 11 маршрутах.

## 2. Что проверялось и как

- **Маршруты (11)**: `/`, `/tasks`, `/knowledge`, `/prompts`, `/search`, `/analytics`, `/graph`, `/memory`,
  `/projects`, `/system`, `/access` + `/login`. Каждый — на 1440×900 и 390×844.
- **Измерения по DOM** (скрипты Playwright, результаты в `/tmp/.../scratchpad/audit/metrics.json`,
  `probe.json`, `contrast.json`): overflow, дубли `h1`, landmark-роли, порядок Tab-остановок, видимость фокуса,
  подписи полей, доступные имена кнопок, `role="alert"`, контраст вычисленных стилей (нормализация через canvas).
- **Состояния**: загрузка (в т.ч. медленный ответ), пустой проект, наполненные данные, ошибка сервера,
  просроченный/поддельный JWT.
- **Сценарии** (как новый пользователь): A — проект → задача → документ; B — поиск; C — токен для агента.
- **Код**: `app/*/page.tsx`, `components/*`, `lib/api-client.ts`, `lib/realtime.ts`, `app/globals.css`.

Не проверялось (см. §8): скринридеры, Firefox/Safari, планшет, реальный WS-сервер, Docker-образ, нагрузка.

## 8. Ограничения аудита

- Не тестировались скринридеры (NVDA/VoiceOver) — выводы по доступности сделаны по DOM/ARIA и вычисленным стилям.
- Только Chromium; Firefox и Safari не проверялись (различия в `outline`, `:focus-visible`, нативных `select`).
- Только 1440×900 и 390×844; планшет 768×1024 не проверялся.
- Реальный WebSocket-сервер недоступен (`/ws` не проксируется Next dev) — поведение realtime оценено по коду и
  по «залипшему» бейджу; исправление требует проверки на живом WS.
- Docker-образ не собирался: вывод про отсутствие `ARG` для `NEXT_PUBLIC_*` сделан по Dockerfile.
- Многопользовательские сценарии и роли не проверялись: сейчас один админ (`MCP_LOGIN_USER`), пользователей и
  ACL в продукте нет (`T-01`, `T-02`).
- Нагрузка не проверялась: 78 сессий и 116 инструментов — данные стенда; поведение на 10 000 задач неизвестно.
- Локализация: интерфейс полностью английский, слоя i18n нет. Это не дефект, но требует решения владельца,
  если админкой будут пользоваться не-англоязычные коллеги.
